## 1. MVP 概述

### 1.1 背景

供应商拥有多个品牌和多个洗化品类货源，目前需要建立自有微信私域交易阵地。终端消费者应能在微信小程序内完成从浏览、搜索、选购、下单到售后的完整过程；供应商应能通过电脑后台独立维护商品、库存、订单、客户和核心经营数据。

### 1.2 核心验证目标

MVP 首先验证以下业务假设：

1. 私域客户愿意通过供应商自有小程序完成商品浏览和自主下单。
2. 供应商团队可以在不依赖开发人员的情况下完成商品上架、库存调整、订单发货和售后处理。
3. 系统能够可靠完成价格确认、30 分钟库存锁定、模拟支付、库存结转和退款处理，不出现超卖或重复退款。
4. 核心交易数据能够被统一统计，为后续会员、优惠券、积分和分销能力提供可信的数据基础。

### 1.3 北极星指标

北极星指标为“有效支付订单数”。定义如下：

- 订单至少存在一笔成功支付记录；
- 订单当前剩余实付金额大于 0；
- 已全额退款的订单不计入有效支付订单数；
- 统计日期以 Asia/Shanghai 自然日为准，数据库时间统一保存为 UTC。

### 1.4 MVP 原则

- 完整交易闭环优先于营销玩法。
- 运营可自助优先于批量工具和自动化。
- 数据准确和库存一致性优先于复杂促销。
- 第三方支付、物流轨迹和微信正式资质未就绪时，通过 Provider 接口与 Mock 实现保持可运行、可替换。

### 2.2 首期明确不启用

以下能力不进入 MVP 页面和业务计算，仅在架构层预留可替换接口或扩展点：

- 会员价格和多级会员价格；
- 优惠券和新用户优惠；
- 积分获取、抵扣和积分商城；
- 分销、代理商和佣金结算；
- 拼团、秒杀和复杂营销活动；
- 商品视频；
- AI 客服；
- 第三方物流实时轨迹；
- Excel 导入导出；
- 完整独立销售报表中心和自定义报表；
- 多商户、多仓库、多包裹和拆单；
- 正式微信支付、退款及真实微信授权登录。

### 2.3 首期业务边界

- 单商户、单仓库。
- 一个订单只能形成一个包裹。
- 全场包邮，订单运费固定为 0。
- 一个商品可以有多个 SKU；价格和库存以 SKU 为准。
- 首期仅使用零售价成交，会员价字段不参与展示和计价。
- 商品和核心交易记录采用软删除或归档，不允许破坏历史订单快照。
- 消费者可游客浏览和维护本地购物车，但提交订单前必须登录。

## 3. 角色与核心任务

| 角色 | 核心目标 | 主要权限 |
|---|---|---|
| 游客 | 快速了解商品并完成选购 | 浏览、搜索、查看详情、维护本地购物车 |
| 已登录消费者 | 完成购买并跟踪履约、售后 | 收藏、地址、订单、支付、物流、确认收货、售后 |
| operator | 处理日常商城运营 | 商品与库存、内容配置、订单发货、售后处理、客户查看、看板查看 |
| owner | 管理业务和后台权限 | operator 全部权限，加管理员管理、完整审计和关键配置权限 |

## 4. 核心用户旅程

### 4.1 首次购买

~~~text
进入首页
  → 浏览 Banner / 分类 / 热销 / 新品
  → 搜索或进入商品详情
  → 选择 SKU 和数量
  → 加入购物车或立即购买
  → 进入结算时触发 Mock 微信登录
  → 选择或新增地址
  → 提交订单并锁定库存 30 分钟
  → 模拟支付成功
  → 后台录入发货信息
  → 用户查看物流并确认收货
  → 订单完成
~~~

### 4.2 未支付订单

~~~text
提交订单
  → 库存被锁定
  → 30 分钟内支付：转为待发货并扣减实物库存
  → 主动取消或超时未支付：关闭订单并释放锁定库存
~~~

### 4.3 售后

~~~text
用户选择订单项和售后类型
  → 提交原因、数量、凭证
  → 运营审核
  → 仅退款：模拟退款 → 完成
  → 退货退款：用户填写退货单号 → 后台确认收货 → 模拟退款 → 完成
~~~

## 5. 核心功能集

### 5.1 消费者端

1. 首页通过后台配置内容展示 Banner、一级分类、热销和新品。
2. 分类默认提供护肤品、洗发水、沐浴露、防晒产品、香水、彩妆、男士护理、家庭清洁，并允许后台增删改排序。
3. 搜索支持商品名称关键词、品牌和分类筛选。
4. 商品详情以 SKU 为可购买单元，清晰展示选中 SKU 的价格、可售库存和规格。
5. 游客购物车保存在本地；登录后与服务端购物车合并，同 SKU 数量相加但不得超过可售库存。
6. 创建订单前必须重新校验商品状态、价格、地址和库存；发现变化时阻止提交并提示用户确认。
7. 订单创建成功后锁库存 30 分钟；到期自动关闭并释放库存。
8. 支付采用可配置 Mock Provider，支持成功、失败和取消结果，用于完整演示和自动化测试。
9. 用户可查看订单状态、发货信息和物流状态时间线，可对已收货订单确认收货。
10. 用户可在售后有效期内发起仅退款或退货退款；默认收货后 7 天，后台可配置天数。

### 5.2 管理后台

1. owner 和 operator 通过管理员账号密码登录，停用账号不得登录。
2. 首页看板展示今日、本月、累计净销售额，今日下单量、有效支付订单数、客户总数、新增客户数、商品销量排行和运营待办。
3. 商品管理覆盖品牌、分类、商品资料、图片、SKU、价格、库存、上下架、新品和热销推荐。
4. 库存调整必须填写原因并记录调整前后数量，不允许调整为负数。
5. 订单管理支持组合筛选、详情查看、发货、物流状态维护、备注和异常查询。
6. 售后管理支持审核、退货信息查看、确认收货、退款和拒绝原因记录。
7. 客户管理展示交易汇总和最近购买商品，不提供营销触达功能。
8. owner 可管理 operator 账号并查看所有关键写操作的审计日志。

## 6. 关键业务规则

### 6.1 价格

- 使用 SKU 零售价作为首期成交价。
- 服务端是最终计价来源，客户端传入金额不得被信任。
- 创建订单时保存商品、SKU、单价、数量和名称快照。
- 金额使用 DECIMAL(12,2) 保存，API 以十进制字符串返回。
- 运费为 0，订单应付金额等于商品小计之和。

### 6.2 库存

- 可售库存 = 实物库存 - 锁定库存。
- 加入购物车不锁库存。
- 创建订单成功时增加锁定库存。
- 支付成功时减少实物库存并同步减少锁定库存。
- 未支付订单取消或超时时减少锁定库存。
- 仅退款默认不回补库存；退货退款由后台确认货物可再次销售后手工回补并生成库存流水。
- 所有锁定、释放、扣减和调整必须在数据库事务内执行并可追溯。

### 6.3 订单和售后

- 用户可取消待付款订单；已支付订单通过售后流程退款。
- 发货必须录入承运商和运单号，成功后订单进入运输中。
- 用户确认收货后订单完成；后台可作为异常兜底手工完成，但必须填写原因并记录审计。
- 默认售后有效期为确认收货后 7 个自然日，可由 owner 配置。
- 未发货订单仅允许仅退款；已发货或已完成且在有效期内可申请仅退款或退货退款。
- 退款金额不得超过对应订单项剩余可退实付金额。

## 7. 技术方案摘要

### 7.1 技术栈

| 层级 | 选型 |
|---|---|
| 小程序 | uni-app + Vue 3 + TypeScript |
| 管理后台 | Vue 3 + Vite + Element Plus + TypeScript |
| 后端 | Node.js 22 LTS + NestJS + TypeScript |
| 数据库与 ORM | MySQL 8.4 + Prisma |
| API | REST + OpenAPI/Swagger |
| 本地基础设施 | Docker Compose；MySQL、Redis、MinIO |

### 7.2 关键技术点

- 模块化单体优先，按用户、商品、库存、订单、支付、物流、售后、后台权限和分析事件划分领域模块。
- 支付、退款、发货和库存调整接口支持幂等键。
- 订单创建、库存锁定、支付结转和释放库存使用事务和条件更新防止超卖。
- 微信登录、支付、退款、文件存储采用 Provider 抽象；本地默认启用 Mock 实现。
- 数据库保存 UTC，业务报表按 Asia/Shanghai 转换和分组。

## 8. 指标与埋点

### 8.1 核心指标

| 指标 | MVP 定义 |
|---|---|
| 有效支付订单数 | 成功支付且剩余实付金额大于 0 的去重订单数 |
| 净销售额 | 成功支付金额减成功退款金额 |
| 今日订单数量 | Asia/Shanghai 当日创建的全部订单数 |
| 客户总数 | 已成功登录并创建客户记录的用户数 |
| 新增客户数 | 统计周期内首次注册客户数 |
| 商品净销量 | 成功支付数量减已成功退款数量 |

### 8.2 最小事件集

- 首页曝光、Banner 点击、分类点击；
- 搜索提交、商品详情曝光、SKU 选择；
- 加入购物车、立即购买、进入结算；
- 登录成功、订单创建、模拟支付成功或失败；
- 物流查看、确认收货；
- 售后申请、售后审核、退款成功。

## 10. 风险与应对

| 风险 | 影响 | MVP 应对 |
|---|---|---|
| 微信 AppID、支付商户号和资质未提供 | 无法完成真实登录与支付 | Provider 接口隔离，首期使用 Mock，真实接入作为上线门禁 |
| 并发下单导致超卖 | 财务与履约损失 | 事务、条件更新、锁库存、幂等和并发集成测试 |
| 订单价格或商品状态变化 | 用户投诉或金额错误 | 下单前服务端重新计价和校验，订单保存快照 |
| 退款重复回调或重复操作 | 重复退款 | 幂等键、退款流水唯一约束、状态机校验 |
| 售后商品无法再次销售 | 库存虚高 | 退货不自动回补，后台验货后手工调整 |
| 商品图片过大 | 小程序体验下降 | 上传校验、生成缩略图、懒加载和对象存储 |
| MVP 范围持续增加 | 延误交易闭环 | 延期清单作为变更门禁，新增需求单独评估 |
| 缺少真实用户数据 | 无法证明商业效果 | 试运行后用埋点和订单数据验证，不在文档中虚构市场结论 |

## 11. MVP 完成标准

以下条件全部满足，MVP 才视为完成：

1. 游客可完成浏览、搜索、选规格、加购物车，并在结算时登录。
2. 用户可使用购物车或立即购买创建订单，模拟支付后进入待发货。
3. 未支付订单 30 分钟后自动关闭，锁定库存全部释放。
4. 两个并发请求争抢最后一件库存时最多一个订单创建成功。
5. 后台可独立完成商品上架、库存调整、订单发货、售后审核和退款。
6. 用户可查看物流、确认收货，并完成仅退款和退货退款两种流程。
7. owner/operator 权限符合矩阵，关键后台写操作存在审计记录。
8. 看板指标能由订单、支付、退款和客户事实数据复算一致。
9. 375px、414px 小程序视口和 1024px、1440px 后台视口无关键内容遮挡或横向溢出。
10. 核心 API 在约定测试负载下 P95 响应时间小于 500ms，库存不出现负数。
