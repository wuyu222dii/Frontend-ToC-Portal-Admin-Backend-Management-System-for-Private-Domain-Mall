## 1. 产品概述

### 1.1 产品定位

洗化产品私域商城是供应商面向终端消费者运营的自有微信交易系统。产品由微信小程序、PC 管理后台、后端 API 和 MySQL 数据库组成，覆盖商品展示、购物车、下单、模拟支付、履约、售后及运营管理。

### 1.2 业务问题

当前需要解决的核心问题是：

1. 消费者缺少一个可随时自主查看品牌、品类、规格和库存并直接下单的微信入口。
2. 供应商缺少统一管理多品牌商品、SKU 库存、订单、发货、客户和售后的运营工具。
3. 商品、订单、支付、库存与退款数据缺少统一口径，无法稳定支撑后续会员和营销扩展。

### 1.3 产品目标

- 打通消费者从浏览到收货、售后的完整闭环。
- 让 owner/operator 可在后台独立完成日常运营，不依赖研发修改数据。
- 建立可审计的价格、库存、支付、退款和经营数据事实来源。
- 通过 Provider 接口保留真实微信登录、支付和退款的替换能力。

### 1.4 非目标

MVP 不以拉新增长、复杂促销、渠道分佣、多仓履约或自动化报表为目标。会员价、优惠券、积分、新用户优惠、分销、代理商、拼团、秒杀、视频、AI 客服、Excel 导出和完整报表中心均不进入首期。

## 2. 成功指标

### 2.1 北极星指标

北极星指标为有效支付订单数：存在成功支付且剩余实付金额大于 0 的去重订单数。全额退款订单自退款成功时起不再计入该统计周期的有效订单存量；历史趋势按事件事实可复算。

### 2.2 经营指标

| 指标 | 定义 | 时间口径 |
|---|---|---|
| 今日净销售额 | 今日成功支付金额减今日成功退款金额 | Asia/Shanghai 自然日 |
| 本月净销售额 | 当月成功支付金额减当月成功退款金额 | Asia/Shanghai 自然月 |
| 累计净销售额 | 全部成功支付金额减全部成功退款金额 | 截至查询时刻 |
| 今日订单数量 | 今日创建的全部订单数，包括未付款和关闭订单 | Asia/Shanghai 自然日 |
| 今日有效支付订单数 | 今日完成有效支付且当前剩余实付大于 0 的订单数 | Asia/Shanghai 自然日 |
| 客户数量 | 已创建客户账户的去重人数 | 截至查询时刻 |
| 新增客户数量 | 周期内首次创建账户的客户数 | 查询周期 |
| 商品净销量 | 成功支付数量减已成功退款数量 | 查询周期 |

### 2.3 MVP 工程验收指标

- 核心 API 在约定的 50 并发测试负载下 P95 小于 500ms。
- 库存不得出现负数，最后一件库存的并发下单最多成功一单。
- 支付、退款、发货和库存调整重复请求不得产生重复业务结果。
- 关键流程 E2E 全部通过。
- 小程序 375px、414px 与后台 1024px、1440px 视口无关键遮挡和横向溢出。

## 4. 产品范围

### 4.1 MVP 范围内

- 小程序：首页、分类、搜索、商品详情、收藏、购物车、结算、Mock 登录、地址、订单、Mock 支付、物流、确认收货、售后、个人中心。
- 后台：登录、看板、品牌、分类、商品、SKU、图片、推荐位、库存、订单、发货、售后、客户、管理员和审计。
- 后端：REST API、OpenAPI、Prisma 数据层、库存事务、状态机、幂等、定时关闭订单、埋点接收。
- 数据：单商户、单仓、单包裹、全场包邮、UTC 保存、Asia/Shanghai 报表。

### 4.2 MVP 范围外

- 真实微信支付、真实微信退款、真实微信授权登录；
- 优惠券、新用户优惠、积分、会员等级和会员价格；
- 分销、代理商、多级价格、拼团、秒杀；
- 商品视频、直播、评价、问答和 AI 客服；
- 第三方物流实时轨迹和电子面单；
- Excel 导入导出、独立完整报表中心；
- 多商户、多仓库、拆单、合单和一个订单多包裹；
- 发票、税务、跨境、运费模板和按地区限售。

### 4.3 依赖与上线门禁

- 本地和演示环境默认启用 Mock 微信登录、Mock 支付和 Mock 退款。
- 生产环境不得误启用允许用户任意选择支付结果的 Mock 页面。
- 正式上线前必须取得微信小程序 AppID、AppSecret、支付商户号、证书及所需类目资质，并完成真实 Provider 验收。
- 正式上线前必须补齐隐私政策、用户协议、售后规则和实际可配送区域。

## 6. 核心流程

### 6.1 浏览到支付

~~~text
首页/分类/搜索
  → 商品详情
  → 选择 SKU 和数量
  → 加入购物车 或 立即购买
  → 确认订单
  → 未登录则 Mock 微信登录
  → 选择地址
  → 服务端校验商品、价格、库存
  → 创建待付款订单并锁库存 30 分钟
  → Mock 支付
  → 成功：待发货；失败/取消：保留待付款直到取消或超时
~~~

### 6.2 购物车登录合并

~~~text
游客本地购物车
  → 用户登录
  → 获取服务端购物车
  → 同 SKU 数量相加
  → 数量截断至当前可售库存和单项上限
  → 下架/失效 SKU 保留为失效项
  → 返回合并结果及提示
~~~

### 6.3 发货与收货

~~~text
支付成功
  → 后台待发货列表
  → operator 录入承运商和运单号
  → 订单进入运输中
  → operator 可维护物流状态文本
  → 用户确认收货
  → 订单完成并开始 7 天售后倒计时
  → 异常情况下后台填写原因后兜底完成
~~~

### 6.4 售后

~~~text
选择订单项和可退数量
  → 选择仅退款或退货退款
  → 提交原因、说明和凭证
  → operator 审核
  → 仅退款：退款处理中 → Mock 退款 → 完成
  → 退货退款：待用户退货 → 用户提交单号 → 待商家收货
                 → operator 确认收货 → Mock 退款 → 完成
~~~

## 9. 页面与交互规范

### 9.1 视觉方向

- 风格：高端、简洁、品牌商城感，适合洗化、美妆和家庭清洁商品。
- 基础色：白色、炭黑和低饱和植物绿；蓝色用于信息，珊瑚色用于重要促销或风险提醒。
- 不使用大面积渐变、装饰性光斑和过度圆角；常规卡片圆角不超过 8px。
- 商品实拍图是首屏主要视觉资产，不用纯装饰插画替代真实商品。
- 页面标题、价格、库存和操作层级清楚，避免营销文案占据核心操作空间。

### 9.2 小程序交互

- 底部主操作区尺寸固定，商品名称和按钮文案不能导致布局跳动。
- SKU、地址、删除、取消订单和确认收货等关键操作提供明确选择或二次确认。
- 购物车、订单和售后页面必须包含加载、空、失败、失效和无权限状态。
- 列表滚动加载时保留筛选状态；返回上一页后尽量恢复滚动位置。
- 价格统一显示人民币符号和两位小数；库存为 0 时使用“已售罄”，不显示负数。

### 9.3 后台交互

- 以 1024px 以上桌面宽度为主，表格支持横向区域滚动但页面整体不得横向溢出。
- 高频筛选和操作放在列表首屏；危险操作需要确认，批量操作不在 MVP 范围。
- 编辑页离开时若有未保存内容，应提示用户。
- 所有表单错误显示在对应字段附近；服务端冲突错误同时保留用户已填写内容。
- 图标按钮使用 Element Plus 已集成图标并提供 tooltip。

## 10. 状态模型

### 10.1 订单主状态

| 内部状态 | 用户文案 | 可进入状态 | 触发条件 |
|---|---|---|---|
| PENDING_PAYMENT | 待付款 | PENDING_SHIPMENT、CLOSED | 支付成功；用户取消；30 分钟超时 |
| PENDING_SHIPMENT | 待发货 | SHIPPED、CLOSED | 后台发货；未发货订单全额退款成功 |
| SHIPPED | 运输中 | COMPLETED | 用户确认收货；后台兜底完成 |
| COMPLETED | 已完成 | 无主状态后继 | 收货完成，售后状态独立变化 |
| CLOSED | 已关闭 | 无 | 未支付取消/超时，或未发货全额退款完成 |

说明：售后不是订单主状态。订单列表“退款/售后”筛选由售后记录叠加生成；已完成订单后续退款时主状态仍保留 COMPLETED，支付和售后状态反映资金结果。

### 10.2 支付状态

| 状态 | 说明 |
|---|---|
| UNPAID | 未成功支付 |
| PAID | 已成功支付且未全额退款 |
| PARTIALLY_REFUNDED | 已完成部分退款 |
| REFUNDED | 已全额退款 |
| PAYMENT_EXCEPTION | 过期回调或数据不一致，需后台追踪 |

### 10.3 物流状态

| 状态 | 用户文案 | 说明 |
|---|---|---|
| NOT_SHIPPED | 未发货 | 尚未录入发货信息 |
| IN_TRANSIT | 运输中 | 已录入承运商和运单号 |
| DELIVERED | 已送达 | 后台手工追加的物流节点，不自动完成订单 |
| RECEIVED | 已收货 | 用户或后台确认后写入 |

### 10.4 售后状态

| 状态 | 用户文案 | 可进入状态 |
|---|---|---|
| PENDING_REVIEW | 待审核 | WAIT_RETURN、REFUND_PROCESSING、REJECTED、CANCELLED |
| WAIT_RETURN | 待退货 | WAIT_MERCHANT_RECEIVE、CANCELLED |
| WAIT_MERCHANT_RECEIVE | 待商家收货 | REFUND_PROCESSING、REJECTED |
| REFUND_PROCESSING | 退款处理中 | COMPLETED、REFUND_FAILED |
| REFUND_FAILED | 退款失败 | REFUND_PROCESSING |
| COMPLETED | 售后完成 | 无 |
| REJECTED | 已拒绝 | 无；符合条件时用户可重新发起新申请 |
| CANCELLED | 已撤销 | 无；符合条件时用户可重新发起新申请 |

### 10.5 状态转换约束

- 所有状态转换由服务端状态机校验，客户端不能直接写状态。
- 每次转换记录操作者、前状态、后状态、原因和时间。
- 终态不得被普通接口恢复；异常修复必须走 owner 授权的运维流程并保留审计。
- 支付和退款状态由交易流水事实驱动，管理员不得直接编辑为成功。

## 11. 业务规则

### 11.1 商品与分类

- 默认一级分类：护肤品、洗发水、沐浴露、防晒产品、香水、彩妆、男士护理、家庭清洁。
- 后台可自由增加一级分类；数据结构可保留 parentId，但 MVP 前台仅展示一级。
- 商品必须关联一个品牌和至少一个一级分类。
- 商品至少包含一个启用 SKU 和一张主图才可上架。
- 商品下架后不出现在搜索、分类和推荐列表；通过历史链接访问时可查看基础信息但不可购买。
- 商品销量是计算结果，不允许后台直接修改。

### 11.2 图片与文本

- 商品图支持 JPEG、PNG、WebP；单图上限 10MB，最多 9 张，第一张默认为主图。
- Banner 必须有图片；跳转目标为商品或分类时，目标必须有效。
- 商品名称、品牌、介绍、成分和使用方法均按纯文本或受控富文本保存，禁止不受信任脚本。

### 11.3 价格

- 首期成交价只取 SKU 零售价。
- 金额数据库类型为 DECIMAL(12,2)，API 输入输出使用十进制字符串，禁止浮点计算。
- 服务端计算商品小计和应付金额；客户端金额仅用于展示。
- 创建订单时保存成交单价和商品信息快照。
- 全场包邮，运费固定为 0；无优惠、积分和会员价抵扣。

### 11.4 库存

- 实物库存 stockOnHand 为仓库可计数商品；锁定库存 lockedStock 为未支付订单预占数量。
- 可售库存 availableStock = stockOnHand - lockedStock。
- 创建订单时使用事务和条件更新增加 lockedStock；任何 SKU 不足则整个订单创建失败。
- 支付成功时同一事务内执行 stockOnHand -= quantity、lockedStock -= quantity。
- 订单取消或超时同一事务内执行 lockedStock -= quantity。
- 退货是否回补库存由后台验货后决定；回补必须是独立库存调整流水。
- 所有库存变化记录业务来源标识，如订单 ID、售后 ID 或后台调整 ID。

### 11.5 购物车合并

- 合并键为 SKU ID。
- 同 SKU 数量相加，并截断至可售库存和单项最大数量中的较小值。
- 本地存在、服务端不存在的有效 SKU 新增到服务端。
- 下架、删除、禁用或不存在的 SKU 保留为失效项，以便用户识别和删除。
- 合并完成后，以服务端购物车为准覆盖本地登录态购物车。

### 11.6 订单创建与过期

- 创建订单要求已登录、有有效地址、至少一个有效订单项且全部 SKU 库存充足。
- 购物车与立即购买均调用同一创建订单能力。
- 订单创建请求必须携带 Idempotency-Key；相同用户和键重复请求返回原订单。
- 支付截止时间 = 服务端创建时间 + 30 分钟。
- 定时任务关闭过期订单；用户访问已过期订单时也触发一次惰性校验，避免界面继续允许支付。
- 用户主动取消和系统超时使用不同 closeReason。

### 11.7 Mock 支付与退款

- 非生产环境通过 PAYMENT_PROVIDER=mock 启用 Mock Provider。
- Mock 支付页面允许测试成功、失败和取消；成功会生成唯一支付交易号。
- Mock 退款仅由审核后的售后流程发起，不允许消费者直接调用。
- 支付和退款接口使用业务幂等键，交易号和 providerRequestId 建唯一约束。
- 生产构建若检测到交互式 Mock Provider，启动必须失败。

### 11.8 发货与物流

- 一个订单只能有一个 Shipment 记录和一个运单号。
- 仅 PENDING_SHIPMENT 且不存在阻断发货的售后时允许发货。
- 发货必须填写承运商名称、承运商编码和运单号。
- 首期物流轨迹由后台追加状态节点，不调用外部物流查询服务。
- 修改错误运单信息须追加更正记录并保留原值审计，不直接擦除历史。

### 11.9 确认收货

- 用户仅能对本人 SHIPPED 订单确认收货。
- 确认操作二次确认并幂等。
- 后台兜底完成仅限 SHIPPED 订单，操作人必须填写原因。
- 完成时间是售后有效期的起算时间。
- MVP 不设置自动确认收货定时任务。

### 11.10 售后资格

- 售后以订单项和数量为申请单位。
- 可申请数量 = 已支付数量 - 已完成退款数量 - 处理中占用数量。
- 未发货订单只允许仅退款；已发货订单和售后期内已完成订单允许仅退款或退货退款。
- 默认售后有效期为完成后 7 个自然日，owner 可配置为正整数天。
- 已发货但未完成订单不受“完成后 7 天”限制，直到确认收货后进入倒计时。
- 拒绝或用户撤销的申请释放占用数量；处理中和已完成申请占用对应数量。
- 单次退款金额按订单项成交单价乘申请数量计算；全场包邮，无运费退还分摊。
- 累计退款不得超过订单实付金额。

### 11.11 售后处理

- 仅退款批准后直接进入退款处理中。
- 退货退款批准后进入待退货；用户提交物流后进入待商家收货。
- 后台确认收货后进入退款处理中；是否回补库存由运营验货决定，默认不回补。
- 拒绝必须填写对消费者可见的原因。
- Mock 退款失败保留失败原因并允许后台重试。

### 11.12 经营统计

- 数据库时间统一保存 UTC，报表按 Asia/Shanghai 转换。
- 净销售额基于支付交易和退款交易，不基于可编辑订单字段。
- 客户消费金额为其全部成功支付减成功退款金额。
- 客户消费次数为当前剩余实付金额大于 0 的去重订单数。
- 商品净销量为支付成功订单项数量减已成功退款数量。
- 看板查询失败时显示错误和最后成功更新时间，不用 0 覆盖未知数据。

- 后台 API 前缀：/api/v1/admin。
- 所有写请求进行 DTO 校验；关键写接口支持 Idempotency-Key。
- 列表统一采用 page、pageSize、total、items 分页结构。
- 错误响应至少包含 code、message、requestId；库存不足、价格变化、状态非法、重复请求和权限不足使用稳定错误码。
- OpenAPI 是接口契约来源，前端类型可由契约生成或统一 contracts 包复用。

## 14. 非功能需求

### 14.1 性能

- 核心读写 API 在 50 并发、正常数据规模的基准环境下 P95 小于 500ms。
- 商品列表和订单列表必须分页，默认 pageSize 不超过 20，后台可配置上限不超过 100。
- 图片使用对象存储、合理尺寸和懒加载，列表不加载原始大图。
- 看板聚合允许使用缓存，但缓存失效时间和最后更新时间必须可见或可追踪。

### 14.2 一致性与可靠性

- 订单、库存、支付和退款关键操作使用数据库事务。
- 支付、退款、发货、库存调整和订单创建实现幂等。
- 定时关闭订单任务可重复执行且不重复释放库存。
- 外部 Provider 调用失败保留可重试记录，不以修改状态字段绕过流程。
- 每次请求生成 requestId 并贯穿日志、错误响应和关键交易记录。

### 14.3 安全

- 管理员密码使用成熟密码哈希算法和随机盐存储，不保存明文。
- 后台鉴权和 RBAC 必须在服务端执行。
- 登录、支付、退款、上传和后台写操作设置速率限制与审计。
- 富文本和上传文件进行类型、大小和恶意内容校验。
- 客户手机号和地址在日志中脱敏；生产密钥仅通过环境变量或密钥服务注入。
- Mock Provider 不得在生产环境运行。

### 14.4 隐私与合规

- 仅在结算、地址和订单履约需要时收集必要信息。
- 登录前展示用户协议和隐私政策入口并记录同意版本与时间。
- 后台列表默认脱敏手机号，订单履约详情仅向授权管理员展示完整收货信息。
- 正式上线前由业务方提供有效协议文本、售后政策和资质材料；本文不构成法律意见。

### 14.5 可用性与兼容性

- 小程序适配 375px 与 414px 常见视口及微信支持的当前主流基础库版本。
- 后台最低适配 1024px，重点验证 1440px；表单和表格键盘操作可用。
- 所有页面提供加载、空、错误、禁用和成功反馈。
- 文案使用简体中文，金额、时间和状态格式统一。

### 14.6 可维护性

- 采用 TypeScript，领域模块边界清晰，共享契约集中管理。
- 数据库变更只通过 Prisma migration；种子数据可重复执行。
- OpenAPI 与实际 DTO 同步生成，接口变更需更新契约和测试。
- 复杂库存、状态机和幂等代码添加解释性注释，避免对显然代码做冗余注释。

### 14.7 可观测性与备份

- 记录结构化应用日志、管理员审计、定时任务结果和 Provider 调用结果。
- 对支付异常、退款失败、库存不一致和定时任务失败提供可查询告警入口或日志标记。
- 生产数据库执行每日备份并定期验证恢复；具体保留周期在部署方案中确定。

## 15. 错误与边界处理

| 场景 | 系统行为 | 用户/管理员反馈 |
|---|---|---|
| 商品下架或 SKU 失效 | 阻止购买，购物车标记失效 | 提示删除或返回选购 |
| 价格变化 | 阻止按旧价下单，返回新旧价格 | 用户确认后重新提交 |
| 库存不足 | 事务回滚，不创建订单 | 指明不足 SKU 和当前可售数量 |
| 地址被删除 | 结算校验失败 | 引导重新选择或新增地址 |
| 重复提交订单 | 返回原幂等结果 | 不生成第二个订单 |
| 支付时订单已过期 | 拒绝支付并记录异常 | 显示订单已关闭，支持重新购买 |
| 发货重复提交 | 返回首次成功结果 | 页面保持已发货状态 |
| 售后数量超限 | 拒绝申请 | 显示剩余可申请数量 |
| 退款 Provider 失败 | 保持退款失败可重试状态 | 后台显示原因和重试入口 |
| 看板查询失败 | 不用 0 覆盖未知值 | 显示失败和最后更新时间 |
| 上传失败 | 不写入残缺媒体关联 | 保留表单内容并允许重试 |

## 16. 验收标准与测试场景

### 16.1 消费者浏览与购物

1. AC-MP-001：游客进入首页时，无登录弹窗且可查看 Banner、分类、热销和新品。
2. AC-MP-002：后台新增并启用一级分类后，小程序刷新即可展示，无需发版。
3. AC-MP-003：按商品名、品牌和分类组合搜索时，仅返回符合条件的已上架商品。
4. AC-MP-004：商品有多个 SKU 时，未选完整规格不能购买；切换 SKU 后价格和库存同步更新。
5. AC-MP-005：游客加入购物车并重启小程序后，购物车仍存在。
6. AC-MP-006：游客在结算时登录，登录成功返回结算页且选中商品不丢失。
7. AC-MP-007：本地和服务端存在同 SKU 时合并数量，超过库存时截断并提示。

### 16.2 订单、库存与支付

1. AC-ORD-001：购物车和立即购买都能创建结构一致的订单。
2. AC-ORD-002：创建订单时价格变化会阻止提交，用户确认新价格后可重新创建。
3. AC-ORD-003：创建订单后锁定库存增加，商品可售库存同步减少。
4. AC-ORD-004：30 分钟内 Mock 支付成功后订单进入待发货，实物库存和锁定库存按规则结转。
5. AC-ORD-005：支付失败或取消后订单仍待付款，可在过期前重试。
6. AC-ORD-006：用户取消待付款订单后订单关闭，锁定库存立即释放。
7. AC-ORD-007：订单超过 30 分钟后自动关闭并释放库存；任务重复运行不重复释放。
8. AC-ORD-008：相同 Idempotency-Key 重复创建订单返回同一订单。
9. AC-ORD-009：两个请求并发购买最后一件库存时最多一个成功，库存最小为 0。
10. AC-ORD-010：同一支付成功结果重复提交只生成一条成功交易并扣减一次库存。

### 16.3 履约与售后

1. AC-FUL-001：后台仅能对待发货订单发货，必须填写承运商和运单号。
2. AC-FUL-002：发货后用户可查看承运商、运单号和手工物流时间线。
3. AC-FUL-003：用户确认收货后订单完成，重复确认不产生额外变化。
4. AC-FUL-004：后台兜底完成必须填写原因，审计日志包含操作前后状态。
5. AC-AS-001：未发货订单只显示仅退款；运输中和售后期内已完成订单显示两种售后类型。
6. AC-AS-002：同一订单项申请数量不能超过剩余可售后数量。
7. AC-AS-003：仅退款批准后完成 Mock 退款，支付状态和经营统计同步更新。
8. AC-AS-004：退货退款批准后，用户必须提交退货物流，后台确认收货后才能退款。
9. AC-AS-005：退款请求重复提交不会重复退款。
10. AC-AS-006：确认收货超过默认 7 天后不能新建售后；owner 修改配置后按新配置计算新申请资格。

### 16.4 后台运营

1. AC-ADM-001：operator 能管理商品、库存、订单、售后和客户，但不能访问管理员管理。
2. AC-ADM-002：owner 停用 operator 后，该账号现有会话和新登录均失效。
3. AC-ADM-003：无主图、无启用 SKU 或无品牌分类的商品无法上架。
4. AC-ADM-004：库存调整必填原因，且流水可查、前后值正确。
5. AC-ADM-005：商品归档后前台不可购买，历史订单详情仍完整。
6. AC-ADM-006：看板销售额可由支付和退款流水复算一致。
7. AC-ADM-007：待发货、待审核售后待办点击后打开正确筛选列表。
8. AC-ADM-008：关键后台写操作均生成包含操作人、对象、结果和 requestId 的审计记录。

### 16.5 响应式与质量

1. AC-UI-001：375px、414px 小程序页面中商品名称、价格、规格和底部操作不重叠。
2. AC-UI-002：1024px、1440px 后台页面无整体横向溢出，表格操作可访问。
3. AC-UI-003：加载、空、网络错误、售罄、下架、支付失败、退款失败和无权限状态均有可执行反馈。
4. AC-NFR-001：核心 API 通过性能基准，P95 小于 500ms。
5. AC-NFR-002：单元、集成和 E2E 测试通过，Prisma migration 可在空库完整执行。

## 17. 测试策略

### 17.1 单元测试

### 17.2 集成测试

- 数据库迁移、唯一约束和软删除引用。

### 17.3 E2E 测试

- 游客浏览 → 加购 → 结算登录 → 地址 → 下单 → Mock 支付成功；

- 未支付订单超时 → 库存释放 → 再次下单；
- 后台上架商品 → 前台发现 → 下单 → 后台发货 → 用户收货；
- 仅退款完整流程；
- 退货退款含用户退货单号、后台收货和退款完整流程；
- owner 创建并停用 operator；
- 看板数字与测试交易明细核对。

## 18. 延期需求清单

| 需求 | 延期原因 | 预留方式 |
|---|---|---|
| 优惠券、新用户优惠 | 增加资格、核销、叠加和退款分摊复杂度 | PromotionProvider 接口 |
| 积分 | 需要积分账本和过期规则 | LoyaltyProvider 接口 |
| 会员等级、会员价、多级价格 | 需要等级成长和价格优先级 | PricingProvider 接口 |
| 分销、代理商 | 涉及关系链、佣金和结算合规 | 独立渠道领域边界 |
| 拼团、秒杀 | 涉及活动库存、并发和超时成团 | CampaignProvider 接口 |
| 商品视频 | 增加上传、转码、审核和流量成本 | FileAsset 保留媒体类型 |
| AI 客服 | 需要知识库、模型、隐私和人工转接 | 独立客服集成边界 |
| Excel 导入导出 | 首期运营量可通过页面处理 | 后台任务和导出任务接口预留 |
| 完整销售报表 | MVP 先验证基础交易事实 | 基于支付/退款事实表扩展 |
| 第三方物流轨迹 | 依赖服务商选择和成本 | LogisticsProvider 接口 |
| 多仓、多包裹 | 显著改变库存和履约模型 | Shipment 和仓库领域后续扩展 |

延期功能不得创建对用户可见但不可用的入口。接口预留是代码边界，不代表提前创建完整业务表或空页面。

## 19. 发布与回滚原则

- 本地开发通过 Docker Compose 启动 MySQL、Redis 和 MinIO，种子数据包含八个分类、演示管理员和演示商品。
- 环境配置明确区分 development、test、staging、production。
- 数据库发布先执行可向后兼容 migration，再发布 API 和前端。
- 订单、支付、库存和售后迁移必须有备份与回滚验证，禁止直接手改生产交易表。
- 发布前运行单元、集成、E2E、migration 和构建检查。
- 若交易一致性指标异常，应立即停止新建订单入口，保留查询与后台排查能力。
