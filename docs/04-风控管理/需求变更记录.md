## 三、CH-001 变更详情

### 3.1 变更申请

- **申请日期**：2026-08-10
- **申请来源**：业务负责人明确调整
- **变更类型**：新增需求与原有需求修改
- **紧急程度**：高，必须在开发前完成范围纠偏

变更前产品只有消费者小程序和总部管理后台，后台采用两类内部权限，渠道推广与结算能力尚未纳入当前范围。

变更后产品为三个终端和三类人员：

1. 总部管理后台，角色 `SUPER_ADMIN`。
2. 一级代理工作台，角色 `AGENT_ADMIN`，属于外部推广合作方。
3. 消费者微信小程序，角色 `CUSTOMER`。

游客仍为未登录状态，不新增人员角色。原总部最高权限映射为 `SUPER_ADMIN`，原总部内部普通操作角色从当前范围移除。

### 3.2 业务边界

- 代理严格单层，由超级管理员创建，不存在下级代理。
- 总部统一商品、零售价、库存、收款、发货、退款和售后。
- 代理仅推广和只读查看本人脱敏客户、订单、售后进度、佣金与提现。
- 代理不能改价、改库存、代客下单、发货、退款或处理售后。
- 未绑定游客保存最后一个有效邀请码，TTL 30 分钟；登录后确认成功才建立长期绑定，拒绝则清空候选并保持直营。
- 超级管理员可转移到其他 ACTIVE 代理或 DIRECT，但只影响转移后提交的新订单，历史订单与佣金快照不变。
- 提交订单只记录归因候选，支付成功时复核代理 ACTIVE 后最终冻结；支付前停用转 DIRECT，支付后停用不影响已冻结 EXPECTED。
- 佣金按订单项净商品实付金额和支付时有效比例计算；具体比例来源由后续已批准的 CH-002 统一商品规则定义。
- 确认收货或总部兜底完成后，佣金立即转为可提现，不设置额外等待期。
- 完成前全退将 EXPECTED 标记为 CANCELLED；完成后保留 AVAILABLE 并追加 REFUND_DEBIT；余额可为负并阻止提现。
- 提现由代理申请、总部审核、线下银行转账、上传凭证并标记已支付；完整收款账号默认掩码，仅付款环节二次验证后短时查看/复制并全量审计。
- 代理默认授权全部当前及未来在售商品，超级管理员可切换自定义白名单。
- ADM-16 配置默认 100 元最低提现与默认 7 天售后申请期；ADM-02 纳入日/月销售、商品销量和客户消费排行。

## 四、CH-002 变更详情

### 4.1 变更申请

- **申请日期**：2026-08-11
- **申请来源**：用户明确提出并批准的业务规则调整
- **变更类型**：修改现有佣金配置与计算需求
- **影响程度**：重大
- **执行时机**：设计阶段立即实施，开发前完成基线替换

变更前，佣金比例配置在代理档案上，同一个代理推广的全部商品使用同一比例。这不能表达不同品类、商品规格的毛利和推广策略差异。

变更后，所有一级代理共用一套由商品维度决定的百分比佣金规则：

1. 平台默认比例提供兜底。
2. 商品所属一级分类可配置分类默认比例。
3. SKU 可配置覆盖比例。
4. 解析优先级固定为 `SKU 覆盖 > 商品一级分类默认 > 平台默认`。
5. 空值表示继承，`0%` 表示明确无佣金并终止继承。
6. 现有商品一级分类直接作为佣金分类来源，不另建运营分类体系。
7. 不再在代理档案维护佣金比例，所有一级代理在同一规则版本下推广相同 SKU 时采用相同比例。

### 4.2 业务边界

- 佣金基数继续使用订单项净商品实付金额，首期不含运费。
- 单个订单项佣金 = 订单项净商品实付金额 × 支付时有效比例；订单佣金为各订单项佣金之和。
- 支付成功时逐订单项冻结规则版本、命中来源、一级分类、商品、SKU、比例、基数和佣金金额。
- 待付款订单按支付成功时有效规则结算；规则修改、商品移动分类或 SKU 覆盖清空不追溯已支付订单。
- 常规退款按原订单项支付快照比例和实际成功退款金额冲减。
- 同一订单项累计冲减不得超过原佣金；最后一笔使订单项全额退清时，直接冲减剩余佣金以消除舍入尾差。
- 保留 `EXPECTED`、`CANCELLED`、`AVAILABLE`、`REFUND_DEBIT` 生命周期，以及不可变流水、负余额、提现限制和线下付款规则。
- 当前版本排除代理专属比例、“代理 × SKU”、固定金额、销量/金额阶梯和限时活动佣金。

### 4.3 影响评估

| 影响维度 | 级别 | 具体影响 |
|---|---|---|
| 产品规则 | 重大 | 佣金从代理维度改为平台/分类/SKU 商品维度，并增加继承和 0% 语义 |
| 信息架构 | 重大 | 总部新增 ADM-22 佣金规则管理，代理页面移除独立比例并增加 SKU 预计佣金/订单项快照 |
| 数据概念 | 重大 | 新增规则版本、规则目标、命中来源和订单项佣金快照；代理档案不再承担比例真相 |
| API 边界 | 重大 | 新增规则查询/写入/版本解释；支付与退款必须逐订单项使用快照，拒绝客户端比例 |
| 用户体验 | 中 | 总部增加继承、0%、影响预览和版本审计；代理看到当前预计值与支付快照 |

审计发现 v2.1 在商品白名单计佣语义、SKU 购物车、待付款订单、支付超时并发、未发货退款、售后并发额度、账户手机号来源、邀请码轮换、软删除、账号删除和高风险操作交互上存在未决或缺失。若直接进入接口与数据库设计，将导致交易状态、库存、佣金和隐私模型出现不可兼容分支。

用户批准以下五项核心决策：

1. 自定义商品白名单只限制代理查看和生成推广物料；已绑定客户购买全店任意 SKU 均按统一商品佣金规则计佣。
2. 客户账户手机号独立、可空且由消费者自愿授权，不从收货地址手机号提取。
3. 未发货退款成功后自动回补对应 SKU 库存；全额退款终止履约。
4. 订单超时后的迟到支付自动原路退款，不恢复订单、库存、履约或佣金。
5. 售后申请提交时立即占用订单项可退数量和金额。

### 5.2 业务边界

- 购物车、订单项、库存预占、发货、售后和退款统一以 `sku_id` 为最小单位；同商品不同 SKU 不合并。
- 提交订单即创建 `PENDING_PAYMENT`、库存预占和 `pay_expires_at`；稍后支付、支付失败或取消均保留订单，可在未过期时继续支付。
- 超时任务先关闭支付意图和订单，再释放库存。关单后支付成功记录为迟到支付并自动原路退款；失败进入人工财务异常，绝不恢复履约和佣金。
- 订单、支付、退款和履约采用独立状态轴，接口统一返回四状态、`close_reason` 和 `display_status`。
- 未发货部分退款自动回库退款数量并只发剩余数量；未发货全额退款后订单 `CLOSED`、`close_reason=FULL_REFUND_BEFORE_SHIPMENT`、履约 `CANCELLED`。
- 售后申请事务性占用可退数量/金额，待处理数量不得发货；驳回或允许阶段取消释放占用，`REFUND_FAILED` 保留占用供幂等重试。
- 原订单项佣金快照和正向流水不可修改；完成前退款追加预计减少/取消流水，完成后退款追加 `REFUND_DEBIT`。
- 白名单撤权、商品下架或邀请码轮换后，旧推广链接可打开普通商品页但不得建立新候选；已有绑定、历史订单和全店计佣资格不变。
- 已登录未绑定消费者打开有效代理链接时立即确认；邀请码支持轮换、停用和有效期，旧码立即失效但不影响既有绑定。
- 账户手机号保存验证来源、时间和协议版本；支付脱敏快照只保存当时账户手机号尾号且不追溯补写。
- 品牌、分类、商品和 SKU 采用软删除；存在在售商品的分类禁止停用，须先迁移或下架。
- 消费者可申请删除账号；有未完成订单或售后时阻断，满足条件后撤销会话、结束绑定并去标识化资料，交易与审计按合规策略保留。
- 代理停用、客户转移、邀请码轮换、提现/售后拒绝、退款和佣金规则变更必须包含原因、影响预览、二次确认、防重复和审计反馈。
- 完整收款账号仅在 `APPROVED` 提现显示；二次验证签发绑定管理员与申请的 60 秒单次授权，连续失败 5 次锁定 15 分钟。

## 六、CH-004 变更详情

### 6.1 变更申请

- **申请日期**：2026-08-11
- **申请来源**：用户明确调整数据库技术选型
- **变更类型**：基础设施与数据库引擎选型修改

- **执行时机**：业务代码开发和首次数据库迁移前，形成 v2.3 技术基线

用户决定将当前设计中的 MySQL 改为 Supabase 托管 PostgreSQL。该变更只调整数据库引擎和托管方式，不改变三端业务范围、人员角色、页面、交互、功能需求、用户故事或验收标准。

### 6.2 选型与使用边界

- 数据库采用 Supabase 托管的 PostgreSQL，Prisma 继续作为后端 ORM 和迁移入口。
- Supabase 仅提供 PostgreSQL 托管能力；当前不采用 Supabase Auth、Supabase Storage、Realtime 或面向客户端的 Data API/PostgREST。
- 消费者小程序、一级代理工作台和总部管理后台只能访问 NestJS 后端 API，不得持有数据库连接、匿名 key、service role key 或其他可直接访问 Supabase 数据面的凭据。
- 微信授权登录、管理员/代理账号登录、会话、RBAC、代理数据范围和高风险操作授权继续由既有后端认证授权模块承担。
- 商品图片、Banner、售后凭证和付款凭证继续使用既有对象存储抽象，不因 CH-004 切换至 Supabase Storage。
- 业务事实、状态、金额精度、幂等、Inbox/Outbox、审计、软删除和隐私规则保持 CH-002/CH-003 口径，不因托管平台改变。

### 6.3 影响评估

| 影响维度 | 级别 | 具体影响 |
|---|---|---|
| 业务功能 | 无 | 三端功能、用户故事、FR、AC、页面与原型统计不变 |
| 数据库引擎 | 重大 | MySQL 方言、枚举、生成列、唯一约束和迁移 DDL 需改为 PostgreSQL 语义 |
| ORM | 中 | Prisma 保留，但 datasource、字段映射、索引和 migration 需按 PostgreSQL 复核 |
| API | 低 | 三端 API 业务契约不变；不得新增客户端直连 Supabase 的旁路 |
| 认证与权限 | 无业务变化 | 不采用 Supabase Auth；服务端 RBAC 与行级数据范围继续作为唯一授权入口 |
| 文件存储 | 无 | 不采用 Supabase Storage，现有对象存储边界不变 |
| 部署与运维 | 中 | 增加 Supabase 项目、区域、连接池、备份恢复、密钥和网络访问配置 |
