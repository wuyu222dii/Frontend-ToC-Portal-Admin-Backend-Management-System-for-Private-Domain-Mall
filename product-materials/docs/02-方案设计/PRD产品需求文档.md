## 1. 产品概述

### 1.1 产品定位

洗化产品私域商城是由供应商总部统一经营、由一级代理推广、由终端消费者购买的私域交易系统。系统包含：

1. 消费者微信小程序：商品浏览、下单、履约与售后。
2. 一级代理工作台：推广、归属数据查询、佣金核对与提现申请，支持 PC 和移动 H5。
3. 总部管理后台：商品、价格、库存、订单、收款、履约、售后、客户、代理和提现的统一管理。
4. 后端 API 与 Supabase 托管 PostgreSQL 数据层：提供三端权限、交易、归属和账务事实来源。

系统采用单商户、单仓、总部统一履约模式。一级代理不是商户、供应商或仓库，只是单层推广合作方。

### 1.2 业务问题

1. 消费者缺少可在微信内自主查看多品牌、多品类商品并完成购买的入口。
2. 总部缺少统一维护商品、SKU 库存、订单、发货、客户和售后的经营工具。
3. 一级代理缺少标准推广物料、渠道归属、订单与佣金核对工具。
4. 客户归属、佣金计算、退款冲正和线下提现若依靠人工表格，容易产生争议和账务错误。
5. 客户隐私和渠道数据需要严格按代理隔离，避免越权访问。

### 1.3 产品目标

- 打通消费者从浏览到收货、售后的交易闭环。
- 让总部可独立完成商城和一级代理的日常经营管理。
- 让代理可自助推广并查看本人渠道数据，不获得经营和履约权限。
- 建立 30 分钟归因候选、首次确认绑定、支付时最终归因快照、全代理统一商品佣金规则、不可变佣金流水与可审计提现闭环；商品白名单只限制推广，绑定客户购买全店任意 SKU 均按统一规则计佣。
- 以 `sku_id` 为交易最小单位，建立待付款订单、可恢复支付意图、主动取消/超时串行、迟到支付自动退款、订单/支付/退款进度/退款处理/履约独立状态、单包裹发货门禁、退货验货与退款回库闭环。
- 在不增加首次下单阻力的前提下，提供可选已验证账户手机号、账号注销资格预览/同步确认和高风险操作审计保护。
- 为真实微信登录、支付、退款及未来营销能力保留替换边界。

### 1.4 非目标

当前版本不建设多级分销、二级代理、团队佣金、代理进货、代理独立店铺、代理定价、代理库存或自动打款；也不支持代理独立比例、“代理 × SKU”、固定金额、阶梯或限时活动佣金。优惠券、积分、会员等级、多级会员价格、拼团、秒杀、视频、AI 客服、Excel 导出、多仓、多包裹以及消费者订单留言/买家备注亦不进入当前版本；总部内部审计备注仍保留。

## 2. 成功指标

### 2.1 北极星指标

北极星指标为有效支付订单数：存在成功支付且当前剩余实付金额大于 0 的去重订单数。全额退款订单自退款成功后不计入当前有效订单存量，历史趋势由支付与退款事件重算。

### 2.2 经营与渠道指标

| 指标 | 定义 | 展示端 |
|---|---|---|
| 今日净销售额 | 今日成功支付金额减今日成功退款金额 | 总部 |
| 本月净销售额 | 本月成功支付金额减本月成功退款金额 | 总部 |
| 累计净销售额 | 全部成功支付金额减全部成功退款金额 | 总部 |
| 有效支付订单数 | 成功支付且剩余实付大于 0 的订单数 | 总部、代理本人 |
| 商品净销量 | 成功支付数量减成功退款数量 | 总部 |
| 今日创建订单数 | `created_at` 落入 Asia/Shanghai 当日的全部去重订单，含待付款和已关闭 | 总部 |
| 今日有效支付订单数 | Asia/Shanghai 当日首次支付成功且当前剩余实付大于 0 的去重订单 | 总部 |
| 客户总数 | 当前未删除的消费者账户去重人数，与代理绑定无关 | 总部 |
| 新增注册客户数 | 周期内首次注册事件数；之后删除不回写历史周期 | 总部 |
| 新增绑定客户数 | 周期内首次形成有效代理绑定的消费者数 | 总部、代理本人 |
| 周期活跃代理数 | 当前 `ACTIVE` 且周期内至少有一笔成功归属支付订单的去重代理数 | 总部 |
| 代理归属净销售额 | 有代理快照订单的支付金额减退款金额 | 总部、代理本人 |
| 预计佣金 | 已支付未完成订单的当前佣金预计值 | 总部、代理本人 |
| 可提现余额 | 已入账佣金、冲正和提现冻结/释放后的当前可用余额 | 总部、代理本人 |
| 已支付提现 | `PAID` 提现申请金额合计 | 总部、代理本人 |

所有经营日期按 Asia/Shanghai 计算；数据库时间使用 UTC。金额指标必须可由支付、退款、佣金与钱包流水复算，不允许后台直接修改汇总值。

### 2.3 设计与工程验收基线

- 小程序 375px、414px；代理工作台 390px、1024px、1440px；总部后台 1024px、1440px 无关键遮挡和横向页面溢出。
- 三端页面覆盖加载、空、错误、禁用、成功和权限拒绝状态。
- 最后一件库存并发下单最多成功一单，库存不出现负数。
- 同商品不同 SKU 的购物车、订单、库存、退款和发货数据不得串项或错误合并。
- 支付、退款、发货、佣金结转、提现审核和付款标记均须幂等。
- 商品售后客户端不得提交金额；并发申请不得超出订单项剩余可退数量或金额。任一活动售后占用必须阻断整单发货，不能先发未占用商品。
- 订单支付意图必须通过稳定 `intent_no` 从 `CREATING/OPEN/CLOSE_PENDING` 查询恢复；主动取消、支付与超时按订单锁串行，确认 Provider 不可支付前不得关单释放库存。迟到支付成功不得恢复订单、履约或佣金，自动退款失败必须进入人工财务异常。
- 代理不能通过修改请求参数访问其他代理或完整客户隐私。
- 订单提交的归因候选和支付成功逐订单项冻结的代理、佣金规则版本/来源、分类、商品、SKU、比例、佣金基数与金额快照均可追溯，且不可被后续配置覆盖。

## 6. 核心业务流程

### 6.1 代理开通与账户安全

~~~text
超级管理员创建代理并设置账号与状态
  → 代理统一继承平台商品佣金规则，无独立比例
  → 系统生成唯一账号、临时密码、邀请码
  → 代理使用临时密码登录
  → 强制修改密码
  → 修改成功后签发正常会话并进入概览
  → 代理维护本人银行卡
~~~

约束：临时密码会话只能访问改密和退出；停用代理不得登录；总部重置密码后再次强制改密。

首个超级管理员只允许通过受控部署命令创建。超级管理员首次进入 ADM-16 绑定 30 秒 TOTP 并取得只展示一次的恢复码；密码或 TOTP 重置后撤销全部旧会话。TOTP 接受当前时间步前后各一个窗口、拒绝同一码重放，连续失败 5 次锁定 15 分钟；密码与 TOTP 均丢失时只允许双人审批的离线恢复并写入不可变审计。

### 6.2 推广与首次绑定

~~~text
代理在 AGT-03 选择商城主页或授权商品
  → 系统生成包含有效邀请码的二维码/链接
  → 未登录且未绑定消费者打开小程序
  → 系统校验邀请码、代理 ACTIVE、邀请码启停和有效期
  → 保存待确认码并签发候选 token，TTL 30 分钟；仅携带有效旧 token 时新码替换旧候选
  → 消费者浏览并在受保护动作时登录
  → 候选仍有效：展示代理名称与明确的确认/拒绝选择
  → 用户确认：创建长期绑定并返回原操作
  → 用户拒绝：清空待确认码，按直营身份继续购物
~~~

已绑定消费者打开其他代理链接时，系统忽略新邀请码并维持原关系。过期、无效或停用代理的邀请码不能覆盖当前有效待确认码。

已登录但未绑定的消费者打开有效代理链接时不再等待下一次登录，立即展示同一服务关系确认层，并在确认或拒绝后返回原页面。邀请码轮换或停用后旧码立即失效；旧商品推广链接仍可打开总部商城普通商品页，但不得设置新的代理候选。

同一消费者并发确认两个代理时，绑定记录按事务锁/版本号串行，首个成功提交者胜出，后到请求返回当前绑定且不覆盖。无效、停用或过期代理统一降级为 `DIRECT`，不得阻断消费者浏览、下单或支付。

### 6.3 浏览、下单与归属快照

~~~text
首页/分类/搜索 → 商品详情 → 选择 SKU
  → 购物车结算或立即购买
  → 登录并选择地址
  → 服务端按 sku_id 校验商品、规格、价格、库存和客户绑定
  → 提交订单：按 SKU 保存快照；ACTIVE 绑定记录代理归因候选；无有效绑定记录 DIRECT 候选
  → 创建 PENDING_PAYMENT 订单、库存预占和 pay_expires_at（30 分钟）
  → 订单创建阶段不创建支付意图，也不调用任何支付 Provider
  → 用户首次或再次点击支付：先落库稳定 intent_no 和 CREATING，再调用 Provider
  → Provider 结果未知：按 intent_no 查询恢复为 OPEN/FAILED，不盲目新建
  → 用户稍后支付或支付取消/失败；订单均保留到过期或主动取消
  → Mock 支付成功时再次复核候选代理 ACTIVE
  → 复核通过：逐订单项按 SKU 覆盖、商品一级分类默认、平台默认顺序解析支付时有效比例
  → 冻结代理及规则版本/来源、一级分类、商品、SKU、比例、基数和预计佣金
  → 复核失败或提交时无候选：最终冻结为 DIRECT，不产生佣金
  → 订单待发货；仅成功冻结的佣金进入 EXPECTED
~~~

每单最多一个活动支付意图，`CREATING/OPEN/CLOSE_PENDING` 均为活动状态。用户主动取消、支付确认和超时任务使用同一订单锁/版本号串行；活动意图先进入 `CLOSE_PENDING`，按稳定 `intent_no` 查询/关闭并确认 Provider 不可支付后，才原子关单和释放库存。创建/关闭结果未知时保持活动状态和库存预占，由对账任务查询、重试或转人工财务异常。关单后的迟到支付成功回调记录真实支付事实，但不得恢复订单、库存、履约或佣金；系统立即发起原路退款，失败时转人工财务异常并持续告警。

### 6.4 履约与佣金入账

~~~text
支付成功并冻结归因 → 总部待发货
  → 系统确认所有活动售后占用均已解决，并给出最终可发订单项
  → 超级管理员录入承运商和运单号，创建唯一包裹
  → 运输中
  → 消费者确认收货 或 总部填写原因兜底完成
  → 订单完成
  → 当前预计佣金转为可提现
~~~

同一订单的“支付成功与最终归因”“订单完成与佣金入账”分别须在同一业务事务或可靠事件处理中实现，重复请求不得重复冻结或重复入账。代理在支付成功后停用，不影响已经冻结的 `EXPECTED`，订单完成时仍正常入账。订单完成与退款成功并发时按订单项佣金快照锁/版本号串行：退款先提交则只结转退款后的剩余预计佣金，完成先提交则追加 `REFUND_DEBIT`，两种顺序净结果一致。

### 6.5 售后与佣金冲正

~~~text
消费者选择可退订单项、数量、类型、原因和凭证，不填写退款金额
  → 服务端按订单项成交/优惠分摊快照试算金额并展示确认
  → 提交仅退款或退货退款
  → 事务性占用订单项剩余可退数量和金额；任一活动占用阻断整单发货
  → 用户可在待审核，或尚未填写退货物流的待寄回阶段取消并释放占用
  → 总部审核；拒绝释放占用；退货同意时冻结 ADM-16 当前退货地址快照
  → 消费者填写退货物流；总部逐订单项记录实收数量、批准退款数量、验货 PASS/ABNORMAL、证据、处置和回库数量
  → PASS 必须全量实收/批准且可零证据；少件、0 件或退回客户必须走 ABNORMAL 且至少一份证据；两类清单均封存
  → PASS 直接退款；ABNORMAL 仅一次选择 CONTINUE_REFUND/REJECT_AFTER_RETURN，继续退款原因必填并使用冻结批准数量
  → 退款失败保留占用并进入 REFUND_FAILED，允许总部重试
  → 退款成功后更新订单项剩余实付和退款状态
  → 未发货数量按 SKU 自动回补库存；部分退款在全部占用解决后只发最终剩余数量，全额退款关闭履约
  → 已发货全额退款：订单 COMPLETED + completion_reason=FULL_REFUND_AFTER_SHIPMENT，保留原履约事实
  → 完成前退款：追加预计佣金减少/取消流水
  → 完成后退款：新增负向可用佣金流水
  → 重算代理钱包；余额可为负
~~~

原正向佣金流水不得修改或删除。每笔负向流水必须关联退款、订单、订单项和原佣金记录。纯金额补偿只能由总部以独立 `AMOUNT_COMPENSATION` 售后类型发起：占用可退金额但不占数量、不回库，成功后仍按原订单项佣金快照冲正。

分次退款按原订单项支付快照冲正，累计不得超过该订单项原佣金；最后一笔使订单项全额退清时，直接冲减剩余未冲佣金以清除舍入尾差。

### 6.6 提现

~~~text
代理在 AGT-07 选择银行卡并输入金额
  → 校验代理 ACTIVE、无负余额、金额达最低门槛、余额充足
  → 校验无其他 PENDING/APPROVED 提现
  → 提交后：可提现减少，冻结增加，状态 PENDING
  → 超级管理员审核
     → REJECTED：记录原因，可提现恢复，冻结减少
     → APPROVED：等待线下银行转账
  → 总部上传付款凭证并标记 PAID
  → 冻结减少，申请完成
~~~

### 6.7 客户归属转移

~~~text
超级管理员进入客户详情
  → 选择新的 ACTIVE 一级代理或转为直营
  → 查看影响提示并填写原因
  → 二次确认
  → 结束原有效绑定并创建新绑定记录
  → 仅转移后提交的新订单记录新归因候选

~~~

原代理的当前客户列表和客户详情立即移除该客户；原代理只可通过历史归属订单查看支付时冻结的脱敏客户快照，不能看到客户后续资料变化。

### 6.8 账户手机号与同步账号注销

~~~text
消费者自愿触发微信手机号授权
  → 服务端验证授权凭证
  → 保存独立账户手机号、来源、验证时间和协议版本
  → 不读取、不覆盖任何收货地址手机号

消费者发起账号注销 preview（acknowledged=true）
  → 检查是否存在待付款/履约中订单、进行中售后、未结清支付/退款或财务异常
  → 有阻断：200 返回 blockers/impacts，token/hash/expiry 为 null，不开放确认
  → 无阻断：签发 5 分钟 preview token/confirmation hash，展示影响并二次确认
  → 同步 confirm 携带 If-Match、新幂等键和确认能力，事务内重新检查阻断
  → 无新阻断：原子撤销全部会话、结束当前代理绑定、去标识化账户资料与代理侧历史客户快照
  → 交易、财务和审计记录按外部合规保留策略保存；不提供异步 current 查询
~~~

## 10. 状态模型

### 10.1 订单状态

| 状态 | 含义 | 允许下一状态 |
|---|---|---|
| `PENDING_PAYMENT` | 已锁库存，等待支付 | `PENDING_SHIPMENT`、`CLOSED` |
| `PENDING_SHIPMENT` | 已支付，存在可履约数量并等待总部发货 | `SHIPPING`、`CLOSED`（未发货全额退款） |
| `SHIPPING` | 唯一包裹已发货 | `COMPLETED` |
| `COMPLETED` | 已确认收货、总部兜底完成，或已发货后全额退款完成 | 售后子流程，不回退主状态 |
| `CLOSED` | 未支付取消/超时，或未发货全额退款后关闭履约 | 终态 |

`CLOSED` 必须同时保存 `close_reason`，至少区分 `USER_CANCELLED`、`PAYMENT_TIMEOUT` 和 `FULL_REFUND_BEFORE_SHIPMENT`。`COMPLETED` 必须保存 `completion_reason`，至少区分 `CUSTOMER_CONFIRMED`、`ADMIN_FORCED`、`FULL_REFUND_AFTER_SHIPMENT`；非完成订单返回 `null`。订单主状态只表达订单生命周期，不代替支付、退款或履约事实；“退款售后”是聚合视图，不覆盖订单主状态。

### 10.2 支付、退款与履约状态

订单级支付状态：`UNPAID` → `PROCESSING` → `PAID`；用户取消支付或明确失败后回到 `UNPAID`。支付意图状态固定为 `CREATING`、`OPEN`、`CLOSE_PENDING`、`CLOSED`、`SUCCEEDED`、`FAILED`、`CANCELLED`、`EXPIRED`，其中前三者为活动状态；同一订单最多一个活动意图。`intent_no` 在调用 Provider 前生成并稳定不变，用于创建结果未知、关闭结果未知和对账查询恢复。关单后的支付成功保存支付尝试 `SUCCEEDED_LATE` 和真实收款事实，订单保持 `CLOSED`，订单级 `payment_status=PAID`，退款处理随即进入 `REFUNDING`。

退款不再使用单一混合状态。退款进度 `refund_progress_status` 固定为 `NONE/PARTIAL/FULL`，只根据成功退款累计金额派生；退款处理 `refund_processing_status` 固定为 `IDLE/REFUNDING/FAILED`，表达是否有活动尝试或失败待处理。失败不得推进退款进度、更新成功退款金额、库存或佣金；同一时刻可出现 `PARTIAL + FAILED`，界面优先提示失败待处理。

履约状态：`NOT_STARTED` → `READY_TO_SHIP` → `SHIPPED` → `IN_TRANSIT` → `DELIVERED`；未发货全额退款时从 `NOT_STARTED`/`READY_TO_SHIP` 转 `CANCELLED`。首期物流节点由总部手工维护，一个订单只允许一个包裹；任一活动售后占用阻断整单创建/确认发货，包裹项在所有占用解决后保存最终实际发货数量。已发货后的退款、退货或全额退款不得回退或改写履约事实。

订单接口必须同时返回 `order_status`、`payment_status`、`refund_progress_status`、`refund_processing_status`、`fulfillment_status`、`close_reason`、`completion_reason` 和由服务端计算的 `display_status`。客户端不得自行根据单一字段猜测“待发货”或“退款完成”。

`display_status` 采用固定优先级，首个命中即返回：支付人工异常 → 退款失败待处理 → 迟到支付退款中/退款中 → 全额退款完成 → 部分退款 → 已关闭 → 待付款 → 待发货 → 运输中 → 已完成。`close_reason` 与 `completion_reason` 必须始终出现在接口响应中，不适用时返回 `null`。

### 10.3 售后状态

| 状态 | 含义 |
|---|---|
| `PENDING_REVIEW` | 等待总部审核 |
| `REJECTED` | 审核拒绝，终态 |
| `REFUNDING` | 仅退款已通过，等待退款 |
| `WAITING_RETURN` | 退货退款已通过，等待消费者寄回 |
| `WAITING_RECEIPT` | 已填退货物流，等待总部收货 |
| `RETURN_EXCEPTION` | 已收货但验货异常，等待总部记录证据并选择继续退款或验货后拒绝 |
| `REFUNDING_AFTER_RETURN` | 验货通过或异常后决定继续退款，等待退款 |
| `REJECTED_AFTER_RETURN` | 验货后拒绝，终态；保存实收、异常证据和处置，释放未消耗占用 |
| `COMPLETED` | 退款成功，终态 |
| `CANCELLED` | 用户在允许阶段取消，终态 |
| `REFUND_FAILED` | 售后退款调用失败，额度占用保留，等待受控重试或人工处理 |

商品售后创建时必须在同一事务内占用订单项剩余可退数量和服务端计算金额，客户端不提交金额。`REJECTED`、`REJECTED_AFTER_RETURN` 和允许阶段的 `CANCELLED` 释放未消耗占用；`REFUND_FAILED` 不释放占用。用户只可在 `PENDING_REVIEW`，或未提交退货物流的 `WAITING_RETURN` 阶段取消。`AMOUNT_COMPENSATION` 为总部专属类型，只占金额、不占数量且不产生回库。

退货验货结果与异常解决是两个独立、不可覆盖的事实：`inspection_result` 仅为 `PASS/ABNORMAL`；`PASS` 直接进入退货后退款且 `resolution=null`，`ABNORMAL` 初始 `resolution=null`，之后只允许一次把类型化 `resolution` 写为 `CONTINUE_REFUND` 或 `REJECT_AFTER_RETURN`。选择 `CONTINUE_REFUND` 时 `resolution_reason` 必填；选择拒绝时原因按 HR-08 必填。`resolution`、原因、处理人和时间写入后不可改写，不能仅由售后当前状态反推。

### 10.4 代理与绑定状态

代理状态：`ACTIVE`、`DISABLED`。停用后禁止登录和新绑定；支付时不得为停用代理冻结新佣金，支付成功前不存在最终佣金快照，支付成功后已冻结的 `EXPECTED` 则继续按订单生命周期处理。

待确认邀请码属于游客会话候选，TTL 30 分钟。服务端不采集设备标识；只有请求携带有效旧候选 token 时，才将该 token 定位的候选替换为新有效码，未携带时旧候选自然过期。登录后确认成功才创建长期绑定，拒绝或过期即清空。

绑定通过有效期表示为当前长期绑定或已结束历史绑定。代理停用只暂停该绑定的未来归因资格，不结束绑定；重新启用后，未被超级管理员转移的绑定恢复未来归因资格。绑定转移只能由超级管理员执行，且不物理删除历史。

### 10.5 佣金状态与流水

订单项佣金状态；订单层状态与金额由各订单项汇总，不使用一个比例覆盖整单：

| 状态 | 进入条件 | 退出条件 |
|---|---|---|
| `NONE` | 最终为 AGENT，但归属订单项基数为 0 或支付时有效比例为 0% | 终态；0% 订单项仍保留规则来源和比例快照，但不生成正向佣金流水；DIRECT 订单不创建佣金快照或 position |
| `EXPECTED` | 支付成功且归因复核通过，最终佣金快照已冻结 | 订单完成转 `AVAILABLE`；完成前部分退款减少预计额；完成前全退转 `CANCELLED` |
| `CANCELLED` | 订单项完成前全额退款，预计佣金归零 | 终态；不产生可提现入账；全单所有有佣订单项均取消时订单汇总为 `CANCELLED` |
| `AVAILABLE` | 订单完成且该订单项佣金已入钱包 | 状态和原正向记录永久保留；完成后退款追加 `REFUND_DEBIT` |

佣金/钱包流水为不可变追加记录，至少区分：`EXPECTED_CREATED`、`EXPECTED_REDUCED`、`EXPECTED_CANCELLED`、`AVAILABLE_CREDIT`、`REFUND_DEBIT`、`WITHDRAWAL_FREEZE`、`WITHDRAWAL_RELEASE`、`WITHDRAWAL_PAID`。任何修正均新增流水，不更新历史金额。

### 10.6 提现状态

| 状态 | 操作者 | 允许下一状态 |
|---|---|---|
| `PENDING` | 代理提交 | `APPROVED`、`REJECTED` |
| `APPROVED` | 超级管理员审核通过 | `PAID` |
| `REJECTED` | 超级管理员拒绝 | 终态，金额已解冻 |
| `PAID` | 超级管理员上传凭证并确认付款 | 终态 |

当前版本不支持代理撤回、部分通过、部分付款或自动打款。

### 10.7 并发裁决状态

| 并发组合 | 串行化对象 | 默认裁决 |
|---|---|---|
| 两个代理绑定确认 | 当前消费者绑定行/版本号 | 首个提交胜出，后到返回现有绑定，不覆盖 |
| 客户转移与订单提交 | 当前消费者绑定行/版本号 | 先提交订单保留旧候选；先转移则新订单使用新归属 |
| 代理停用与支付确认 | 代理状态行/版本号 | 支付先提交冻结代理快照；停用先提交则归因降级 DIRECT，支付仍可完成 |
| 主动取消/超时与支付确认 | 订单行/版本号及活动支付意图 | 支付先提交则关单失败；关单先提交则后到成功为迟到支付并退款 |
| 订单完成与退款成功 | 订单/订单项佣金快照行 | 退款先提交只结转剩余佣金；完成先提交追加退款冲正，净结果一致 |

所有裁决必须保存资源版本、幂等键和结果事件；禁止依赖前端点击顺序或仅用最终状态覆盖并发事实。

## 11. 业务规则

### 11.1 商品、价格与库存

- 默认分类：护肤品、洗发水、沐浴露、防晒产品、香水、彩妆、男士护理、家庭清洁；总部可新增、排序和停用。
- 消费者首页、分类、搜索和商品详情仅使用 Store 专用目录投影，只返回生命周期为 `ACTIVE` 的商品及全部 `ACTIVE` SKU 和消费者展示/交易字段；零库存 SKU 保留并返回 `is_salable=false`，商品摘要在任一 ACTIVE SKU 可售时为 true。软删除、内部状态/版本、成本、锁定库存、预占、管理备注和审计字段不得下发后再由前端隐藏。
- 公开品牌和分类接口均返回全部 ACTIVE 记录，不带 pagination，固定按 `sort_order ASC,id ASC`。商品名称搜索在 trim 后校验 1–200 字符并进行大小写不敏感匹配，不得扩大到 SPU/SKU code、品牌、分类、描述或成分。
- 商品综合排序固定为 `is_hot DESC,is_new DESC,sales_count DESC,published_at DESC NULLS LAST,product_id ASC`；HOT 使用成功支付数量减成功退款数量，NEWEST 使用首次启用写入且不覆盖的 `published_at`，价格排序使用 ACTIVE SKU 最低零售价，所有排序最后使用商品 ID 稳定收口。
- 首页 Banner、分类、热销、新品上限分别为 10、8、4、4，各区状态闭合为 `READY/UNAVAILABLE`。任一区失败时对应数组为空且整体仍为 200，四区全部失败才返回 500；PRODUCT Banner 目标无法解析为当前公开商品时自动排除。
- 5 个匿名 Store GET 共享 Redis 固定窗口限流：以服务端 HMAC 后的来源 IP 为键，每 60 秒 120 次；不保存原始 IP，超限返回 429 与准确 `Retry-After`，Redis 异常采用 fail-closed，不得绕过限流。
- 品牌和一级分类创建时 `initial_status` 固定为 `DRAFT`，品牌创建必须提交非负 `sort_order`，品牌更新可修改排序；分类继续使用同一排序约束。品牌、分类列表固定 `sort_order ASC,id ASC`，不采用创建时间作为默认排序。
- 品牌/分类状态机固定为：非删除 `DRAFT/INACTIVE -> ACTIVATE -> ACTIVE`；非删除 `ACTIVE -> DEACTIVATE -> INACTIVE`；非删除 `DRAFT/INACTIVE -> SOFT_DELETE -> ARCHIVED + deleted_at`。非法或同状态的新请求返回 409，ACTIVE 不得直接软删除。
- ACTIVATE、DEACTIVATE、SOFT_DELETE 均要求原因、影响预览、二次确认、新幂等键和 `If-Match`。存在 ACTIVE 商品时，停用/软删除预览仍成功列出影响，确认以 `ACTIVE_PRODUCT_DEPENDENCY` 422 阻断。
- restore 仅适用于软删除 ARCHIVED，保留原因、幂等和 `If-Match`，成功后清除 `deleted_at`、状态固定为 DRAFT、版本递增；恢复不复用 preview，启用必须另走 ACTIVATE。默认列表排除归档，显式 `status=ARCHIVED` 返回归档记录，详情允许读取归档以支持恢复。
- Product 创建固定 `DRAFT`，SKU 创建固定 `INACTIVE`；普通编辑不得修改状态。Product 只允许 `DRAFT/INACTIVE -> ACTIVATE -> ACTIVE`、`ACTIVE -> DEACTIVATE -> INACTIVE`、`DRAFT/INACTIVE -> SOFT_DELETE -> ARCHIVED`，恢复固定 DRAFT；SKU 只允许 `INACTIVE -> ACTIVATE -> ACTIVE`、`ACTIVE -> DEACTIVATE -> INACTIVE`、`INACTIVE -> SOFT_DELETE -> ARCHIVED`，恢复固定 INACTIVE。状态变化不级联修改子 SKU，SKU 可在非归档 DRAFT/INACTIVE Product 下先启用，但仅 Product 与 SKU 同时 ACTIVE 才公开可售。
- Product/SKU 的 ACTIVATE、DEACTIVATE、SOFT_DELETE 均要求原因、preview-confirm、新幂等键与 `If-Match`；restore 只要求原因、新幂等键与 `If-Match`，不新增 preview。原因写入审计；409 后必须刷新并重新预览，不能复用旧 token。
- Product ACTIVATE 必须同时具备 ACTIVE 品牌、ACTIVE 分类、至少一张 `READY/PUBLIC/PRODUCT_IMAGE` 和至少一个 ACTIVE SKU；分别缺少图片或 ACTIVE SKU 时返回 `PRODUCT_PRIMARY_IMAGE_REQUIRED`、`PRODUCT_ACTIVE_SKU_REQUIRED` 422。首次启用写 `published_at`，重新启用不得覆盖。
- ACTIVE Product/SKU 不得直接软删除。Product 存在 ACTIVE SKU 时 confirm 返回 `ACTIVE_SKU_DEPENDENCY` 422；Product 任一 SKU 或目标 SKU 存在活动库存预占时返回 `ACTIVE_INVENTORY_RESERVATION` 422。preview 仍以 200 返回影响，失败 confirm 不消费 preview。
- Product 列表固定 `published_at DESC NULLS LAST,id DESC`；无 ACTIVE SKU 时 `minimum_active_price=null`。Product 详情返回全部 SKU，包括 ARCHIVED，固定按 `created_at ASC,id ASC`；活动图集最多 8 张，固定按 `sort_order ASC,id ASC`。
- SPU/SKU code 创建后永不可改且软删除后继续保留。SKU 创建与零值 `inventory_balance` 同事务完成，初始物理/锁定/可售库存均为 0；B4 商品编辑只读展示库存摘要，不提供库存调整入口。
- Banner 创建固定 DRAFT，普通资料更新不接收状态。状态机固定为 `DRAFT/INACTIVE -> ACTIVATE -> ACTIVE`、`ACTIVE -> DEACTIVATE -> INACTIVE`、`DRAFT/INACTIVE -> DELETE -> ARCHIVED + deleted_at`；ACTIVE 不得直接归档，restore 固定回 DRAFT 并清空 `deleted_at`。POST 使用新幂等键，PATCH/DELETE/restore 使用新幂等键与 `If-Match`；DELETE/restore 原因 2-500 字符，Banner 不纳入高风险 preview。
- Banner 默认列表排除 ARCHIVED，仅显式归档筛选返回；固定按 `sort_order ASC,id ASC`。公开投影只返回 ACTIVE、未归档，且满足 `(starts_at 为空或 starts_at <= now) AND (ends_at 为空或 now < ends_at)` 的记录；起止均非空时 `ends_at > starts_at`。启用及公开读取重查 `READY/PUBLIC/BANNER` 文件；PRODUCT/CATEGORY 目标必须存在且 ACTIVE，目标失效后自动排除；URL 最长 500 字符，必须为 HTTPS 且命中服务端 origin allowlist，allowlist 为空时不开放 URL。
- 库存列表不提供 `low_stock` 或每 SKU 预警值。统一公式为 `available_qty=physical_qty-locked_qty`；`active_reservation_qty` 只复核锁定事实，不再二次扣减售后占用。ARCHIVED SKU 只读和可查流水，恢复为 INACTIVE 后才可调整。
- 库存人工调整只修改 physical，接收非零 PostgreSQL INTEGER 范围 `physical_delta` 与 2-500 字符原因。preview 绑定 actor、session、`INVENTORY.ADJUST`、`INVENTORY`、SKU、规范化请求和余额版本；即使调整后实物低于 locked 仍返回 200 warning，confirm 以 `STOCK_INSUFFICIENT` 422 阻断且不消费 preview；整数溢出返回 `INVENTORY_QUANTITY_OUT_OF_RANGE` 422。
- 库存 confirm 需要相同业务字段、未过期 token/确认哈希、新幂等键和 `If-Match`；成功原子消费 preview、递增余额版本、插入一条 `MANUAL_INCREASE/MANUAL_DECREASE` 流水、写审计/幂等/outbox。同 token 换键、并发确认或同键重放不得产生第二条流水；流水按 `occurred_at DESC,id DESC`，B4 零余额不补写 INITIAL。
- 七类文件 purpose 只接受 `image/jpeg`、`image/png` 且最大 5 MiB。上传意图声明 64 位小写 SHA-256，完成请求的 SHA-256/size 必须与 intent 及服务端 MIME、魔数、大小、哈希实测一致；不一致返回 `FILE_CONTENT_MISMATCH` 422。
- 上传签名有效 15 分钟，私有下载签名有效 5 分钟；PENDING/staging 满 24 小时仅成为清理候选，删除前仍须复核无 READY 和业务引用。bucket 默认私有，仅 `public/*` 可匿名 GET；售后、提现、推广 QR 等私有素材只能位于 `private/*`。
- 品牌、一级分类、商品和 SKU 只允许软删除。已被订单、库存流水、售后或佣金规则引用的记录必须永久保留历史可读性。
- 一级分类或品牌存在在售商品时禁止停用或删除；页面返回阻断商品数量和清单入口，超级管理员必须先迁移或下架商品。商品/SKU 存在活动库存预占时禁止软删除。
- SKU 零售价为当前唯一成交价，会员价和代理价不展示、不参与计算。
- 服务端重新计价，客户端传入金额不得作为事实。
- 可售库存 = 实物库存 - 锁定库存，始终满足 `实物库存 >= 锁定库存 >= 0`；加入购物车不锁库存，库存调整通过条件更新校验调整后不变量。
- 购物车行和订单项以 `sku_id` 为最小单位，同一商品不同 SKU 不合并；服务端报价返回 SKU 规格、当前价格、可售库存和可售状态。
- 每个 SKU 单笔订单数量上限固定为 `min(99, 服务端可售库存)`，首期不提供后台配置。
- 创建订单增加锁定库存；数据库强制生成 `pay_expires_at = created_at + interval '30 minutes'`，订单创建后任何角色、配置或更新接口均不得修改该值。支付成功同时减少实物与锁定；主动取消或支付意图关闭后才释放锁定。
- 普通下架阻止新加入购物车和新结算；在下架前已创建且预占仍有效的待付款订单可以在 `pay_expires_at` 前继续支付。软删除比下架更严格，任何活动预占均阻断删除。
- 未发货退款成功按退款订单项数量自动回补对应 SKU 实物库存并生成退款回库流水；部分退款只回补成功退款数量。已发货退货不自动回补，由总部验货后手工决定并生成库存流水。

### 11.2 订单归属快照

- 提交订单时读取消费者当前长期绑定和代理状态；有效绑定指向 `ACTIVE` 代理时记录 `AGENT` 归因候选，否则记录 `DIRECT` 候选。
- 归因候选至少记录候选代理、绑定关系和提交时间，但此时不冻结最终渠道、商品佣金规则、比例或金额。
- 支付成功时对提交时的 `AGENT` 候选再次复核同一代理是否 `ACTIVE`。复核通过后，逐订单项解析支付时有效佣金规则、计算基数与金额，并最终冻结渠道、代理及规则版本、命中来源、一级分类、商品、SKU、比例、基数和佣金快照。
- 支付时代理已停用、候选无效或提交时已记录 `DIRECT`，最终渠道均为 `DIRECT`，不产生佣金；该降级不阻断购买或支付，重新启用不追溯已经直营支付的订单。
- 归属转移只作用于转移后提交的新订单。支付前转移不替换既有待付款订单的候选；支付后转移、代理停用、分类移动或规则修改不得修改已冻结快照。
- 支付归因快照同时保存服务端生成的客户脱敏昵称、当时已验证账户手机号后四位（可空）和该订单收货城市快照。不得把原始昵称交给代理端自行掩码，不得使用收货地址手机号；手机号后续授权不得追溯补写。客户转出后，原代理只能通过这些历史订单快照查看历史信息；账号删除完成后昵称替换为不可逆客户代号并清空手机号尾号。
- 订单项保存商品、SKU、名称、规格、单价、数量、净商品实付和可退金额快照；代理订单还保存对应佣金规则快照。

### 11.3 佣金计算

- 所有一级代理共用同一套商品佣金规则，不在代理档案保存独立比例，也不支持“代理 × SKU”规则。
- 比例解析优先级固定为：`SKU 覆盖比例 > 商品一级分类默认比例 > 平台默认比例`。解析到首个非空值即停止。
- SKU 覆盖或分类默认比例为空表示继承；`0%` 是明确无佣金的有效配置，不得继续向下继承。
- 现有商品一级分类直接作为佣金分类来源。一个商品必须且只能归属一个有效一级分类；新增一级分类默认继承平台比例，商品移动分类只影响移动后支付的订单。
- 平台、分类和 SKU 百分比范围均为 `0.0000%` 至 `100.0000%`（含边界），使用 `DECIMAL(7,4)`、展示为百分比；超范围必须拒绝。当前版本不支持固定金额、销量/金额阶梯或限时活动佣金。
- 佣金基数 = 归属订单项净商品实付金额；首期无运费、优惠券或积分分摊。
- 单个订单项预计佣金 = `该订单项佣金基数 × 支付时有效比例 / 100`；每个订单项按 `HALF_UP` 保留两位后汇总订单预计佣金，不保存或展示虚构的订单平均比例。
- 支付成功时为每个归属订单项保存：规则版本、命中来源 `SKU`/`CATEGORY`/`PLATFORM`、一级分类、商品、SKU、有效比例、佣金基数和佣金金额。规则版本只追加，不覆盖历史。
- 待付款订单在支付成功时使用当时有效规则；代理推广页展示的比例和金额均为预计值。规则、商品分类或 SKU 配置后续变更只影响未来支付，不追溯历史。
- 支付成功且归因复核通过后创建 `EXPECTED`；支付前候选不向代理展示为订单或预计佣金。
- 消费者确认收货或总部兜底完成后立即入账，不设置额外结算等待期。

### 11.4 退款冲正

- 退款佣金影响基于退款订单项的实际成功退款金额，不以申请金额或审核金额为准。
- 完成前部分退款：按原订单项支付快照比例计算并追加 `EXPECTED_REDUCED`，剩余预计不得低于 0。
- 完成前订单项全额退款：追加 `EXPECTED_CANCELLED`，对应订单项佣金状态转为 `CANCELLED`，不产生可提现入账；全单有佣订单项均取消时订单汇总为 `CANCELLED`。
- 完成后退款：保留原 `AVAILABLE` 和 `AVAILABLE_CREDIT`，追加 `REFUND_DEBIT` 负向可用佣金流水。
- 常规部分退款冲减额 = 本次该订单项实际成功退款金额 × 原订单项支付快照比例，并按统一金额规则舍入。
- 同一订单项累计佣金冲减不得超过该订单项原始佣金。最后一笔使该订单项剩余可退实付归零时，本次冲减额直接取“原订单项佣金 - 该订单项累计已冲减佣金”，清除分次舍入尾差。
- 多 SKU 退款必须逐订单项计算后汇总，不得使用订单总额或平均比例分摊；全单退清后累计冲减必须等于原订单佣金。
- 退款失败不冲正；重试成功后只冲正一次。
- 冲正导致余额为负时保留真实负值，不从历史提现追改；阻止新提现，未来佣金先抵扣。
- 原始订单项佣金快照和正向流水均不可修改。完成前退款也必须通过 `EXPECTED_REDUCED`/`EXPECTED_CANCELLED` 追加流水表达，不得把原佣金金额改为负数或覆盖为退款后金额。
- 售后申请时占用可退数量和金额，但只有退款成功事实才触发佣金冲正、订单净额变化和库存回补。
- 商品售后的退款金额只由服务端按订单项成交/优惠分摊快照、已成功退款和活动金额占用计算；客户端不得提交金额。尾笔退清时直接使用剩余可退金额消除分摊/舍入尾差。
- `AMOUNT_COMPENSATION` 纯金额补偿由总部发起，不占数量、不回库，但占用订单项剩余可退金额；成功退款与普通售后相同，按原订单项佣金快照冲正。

### 11.5 提现与银行卡

- 默认最低提现金额 100 元，由 ADM-16 业务规则设置配置；修改只影响之后提交的申请，首期手续费为 0。
- 提现金额不得超过可提现余额，余额小于等于 0 时不可提交。
- 每个代理同时最多一笔 `PENDING` 或 `APPROVED` 申请。
- 申请提交时保存代理、金额、银行卡掩码/密文引用和申请时余额快照。
- 银行卡包括开户名、开户银行和卡号；卡号加密存储，保存后的常规读取、页面和日志只返回掩码。
- 只有 `SUPER_ADMIN` 可在 `APPROVED` 待付款详情中使用本人 TOTP 发起二次身份验证。验证通过后获得绑定当前管理员与当前提现申请的 60 秒单次授权，可查看或复制该申请冻结的完整收款账号；连续失败 5 次锁定 15 分钟。
- 查看或复制即消费授权；离页、消费或超时立即清除前端明文并恢复掩码。查看、复制、失败、锁定和清除均写入审计；授权不得跨申请复用，其他状态和其他页面不得返回完整账号。
- `PENDING` 通过后保持冻结，拒绝则释放；`PAID` 后扣减冻结并保存付款凭证。
- 付款凭证属于受控文件，只允许相关代理查看摘要、超级管理员查看原件。

### 11.6 代理停用

- 使当前会话失效并阻止新登录。
- 暂停全部邀请码使用，不再建立新绑定；邀请码记录自身启停状态和有效期不被停用动作覆盖。
- 超级管理员可独立轮换、停用或设置邀请码有效期；轮换生成新码并立即使旧码失效，不结束已有长期绑定，也不修改历史订单和佣金。
- 长期绑定不结束，但未来订单提交时只能记录 `DIRECT` 候选；支付前被停用的既有 `AGENT` 候选在支付时转为 `DIRECT`。
- 支付后停用不影响已经冻结的 `EXPECTED`，订单完成时仍正常转为 `AVAILABLE`。
- 重新启用只影响未来提交/支付：未被转移的长期绑定恢复归因资格；只有自身仍启用且未过期的邀请码恢复；停用期已直营支付订单不追溯。
- 历史订单、佣金、负余额和提现永久保留。
- 已提交提现仍可审核；是否通过由总部结合实际结算政策决定。
- 停用与支付确认使用代理状态行/版本号串行：支付先提交则冻结有效快照，停用先提交则该支付最终 `DIRECT`；两种路径均不得阻断消费者完成支付。

### 11.7 隐私与审计

- 代理查询由服务端基于登录身份限定代理 ID，列表和详情都需验证。
- 三端列表与详情使用角色专用投影，禁止用一个宽字段 DTO 同时服务消费者、代理和总部。消费者聚合限定当前账号；代理客户聚合限定当前有效绑定和当前归属期，代理订单限定支付成功时冻结的本人代理快照；总部聚合可覆盖全生命周期，但必须标注聚合口径并按目标 ID 服务端过滤。
- 消费者账户手机号独立于收货地址手机号，字段可空；只有消费者自愿授权并经服务端验证后才保存来源、验证时间和协议版本，未授权不阻断下单。
- 代理只能查看已验证账户手机号后四位，未授权显示“未绑定”；地址只显示城市。完整字段和地址手机号不得先返回前端再遮盖。
- 客户转出后从原代理当前客户列表移除，原代理不得继续访问客户详情或后续资料变化，只能查看历史订单内冻结的脱敏客户快照。
- 密码使用安全哈希，临时密码和重置密码只展示一次。
- 银行卡号使用字段级加密，密钥不得写入数据库或源码；付款短时解密必须采用本人 TOTP 和最小授权。
- 完整地址只允许三类最小授权响应：消费者读取本人收货地址/订单；消费者在本人已通过退货审核的售后详情读取冻结的总部退货地址快照；总部在可履约状态下通过用途绑定的履约地址接口读取订单冻结快照。三类响应均禁止缓存；总部读取还要求 `ORDER_FULFILLMENT_PII_READ` 并逐次审计。列表、代理端、错误、日志、审计摘要和自动化产物始终使用掩码或省市级摘要。
- 登录、佣金规则版本、代理状态、归属、退款、佣金、银行卡写入、完整账号查看/复制、业务规则与提现关键动作写入审计。
- 审计和错误日志必须脱敏，不记录密码、完整卡号、完整手机号或详细地址。
- 消费者先提交账号注销 preview；存在待付款、待发货、运输中订单、进行中售后、未结清支付/退款或财务异常时以 200 返回 blockers/impacts 且不签发能力。满足条件时才签发 5 分钟 token，confirm 使用 If-Match、新幂等键并重检；通过后在同一事务撤销全部会话和 refresh 凭据、结束当前绑定并使候选失效，清空微信主体标识、登录凭据、昵称、头像和城市，硬删除账户手机号验证、收货地址、收藏和购物车项中的密文/HMAC/尾号/密钥标识，代理侧历史客户投影替换为稳定不可逆代号并清空昵称/手机号尾号/城市。交易、退款、佣金、提现、协议版本和审计记录仅按上线前批准的外部合规保留策略保存，且不能再通过当前客户资料接口关联原主体；不提供异步 current 查询或完成响应重放。
- 高风险动作的原因、影响预览、二次确认、TOTP/凭证、版本控制、幂等和审计要求仅以 13.4“高风险操作唯一控制矩阵”为准，其他章节不得另造一套笼统规则。
- 临时密码、TOTP 绑定 URI/恢复码、邀请码明文、银行卡完整账号查看授权、预览/确认能力令牌和受控文件签名 URL 等短时凭据/能力只能在签发响应中展示一次；所有此类响应必须发送 `Cache-Control: no-store`，不得写入页面持久状态、埋点、日志或普通详情响应。刷新、离页、消费或到期后必须重新走受控签发流程，不能从浏览器缓存、接口缓存或历史响应恢复。

### 11.8 售后申请期与佣金关系

- 消费者默认可在确认收货或总部兜底完成后的 7 个自然日内发起售后，具体天数由超级管理员在 ADM-16 配置并在订单完成时确定。
- 售后申请期是消费者申请资格，不是佣金结算等待期；订单完成时佣金立即转为可提现。
- 在有效售后期内退款成功时，系统按 11.4 追加负向佣金流水；不得延迟初始入账来规避冲正。
- 未发货订单仅允许仅退款；已发货或已完成且在有效期内可按规则申请仅退款或退货退款。
- 创建商品售后时必须事务性占用订单项剩余可退数量与服务端计算金额；同一订单项所有进行中申请的占用总和不得超过剩余可退范围。首期为单包裹，任一活动占用阻断整单创建或确认发货，不允许按未占用数量先发一包。
- 驳回或用户在允许阶段取消时释放占用；退款失败进入 `REFUND_FAILED` 并保留占用供重试，退款成功后将占用转为已退款事实。
- 未发货部分退款成功后只履约剩余数量；未发货全额退款成功后订单转 `CLOSED`，`close_reason=FULL_REFUND_BEFORE_SHIPMENT`，履约转 `CANCELLED`，用户显示“退款完成”。
- ADM-16 只允许一个当前有效总部退货地址；退货审核通过时保存不可变地址快照。消费者提交退货物流后，总部一次提交并精确覆盖该售后的全部售后项，每个订单项恰好一次；逐项记录实收数量、批准退款数量、验货 `PASS/ABNORMAL`、原因/证据，以及回库、损坏、报废、退回客户四类处置数量。必须同时满足 `批准退款 + 退回客户 = 实收`、`批准退款 = 回库 + 损坏 + 报废`，因此四类处置之和严格等于实收，不允许形成“总部留货但不退款也不退回”的无归属数量。`PASS` 必须全量实收、全量批准退款且退回客户数量为 0，可提交零份证据；少件、0 件或其他不符必须 `ABNORMAL` 且至少一份证据。验货结果、处理人、时间和证据提交后不可改写；`ABNORMAL` 只允许一次受版本控制的类型化解决，`resolution=CONTINUE_REFUND` 或 `REJECT_AFTER_RETURN`，其中继续退款原因必填且只使用冻结批准数量。未实收和退回客户部分在继续退款或验货后拒绝的终态事务释放占用；已发货退货不得在验货前自动回库。
- 验货事务同时冻结按文件 ID 排序的证据清单和数量，并在提交时与证据关联精确核对；`PASS` 的空清单也作为已封存事实保存，`ABNORMAL` 的清单数量必须至少为 1。任一结果提交后均不得追加、删除、替换或改绑证据。
- 已发货全额退款成功时订单保持/转为 `COMPLETED` 且 `completion_reason=FULL_REFUND_AFTER_SHIPMENT`；已发货、物流、签收和包裹项事实永久保留，不转 `CLOSED` 或 `CANCELLED`。

### 11.9 代理商品授权

- 新代理默认采用“全部在售商品”模式，自动包含当前和未来新上架商品，无需逐项授权。
- 超级管理员可在 ADM-19 切换为“自定义白名单”；切换后仅白名单中且当前已上架的商品可在代理推广中心展示或生成物料。
- 商品白名单只控制推广范围，不控制商城购买或佣金资格。已绑定客户购买白名单外 SKU 时，仍按支付时统一商品佣金规则计佣；白名单模式和值不保存到佣金快照。
- 从白名单移除、邀请码轮换或商品下架后，既有推广链接可退化为总部商城普通商品页，但不得再设置代理候选；已有长期绑定、历史订单和全店计佣资格不受影响。
- 授权模式切换与白名单增删必须记录操作人、时间和前后值。

### 11.10 支付时限与迟到支付

- 提交订单只创建待付款订单、订单快照、归因候选和库存预占，不创建支付意图、不调用 Provider；数据库以订单 `created_at + interval '30 minutes'` 固定生成并约束不可变 `pay_expires_at` 后返回。客户端倒计时仅作展示，是否可支付以服务端为准，任何后台配置或写接口均不能延长/缩短既有订单截止时间。
- 首次支付和重试支付是独立接口调用：在订单行锁下复用尚有效的唯一活动意图，或先创建 `CREATING` 本地意图及稳定 `intent_no` 后再调用 Provider；数据库必须阻止同一订单并存两笔 `CREATING/OPEN/CLOSE_PENDING` 意图。Provider 创建结果未知时必须按 `intent_no` 查询恢复，禁止直接发起第二笔。
- 支付失败、用户取消或选择稍后支付均保留 `PENDING_PAYMENT`；用户可在有效期内从订单详情重新发起支付。
- 用户主动取消、支付确认和超时任务使用同一订单锁/版本号串行。存在活动意图时先进入 `CLOSE_PENDING` 并按 `intent_no` 关闭/查询 Provider；只有确认不可支付后才原子关单并释放库存。关闭结果未知时保持占用等待对账，不得假设成功。
- 关单后收到支付成功回调时，保存支付回调和真实收款事实，将该支付标记为 `SUCCEEDED_LATE`，订单与履约保持关闭，不创建归因或佣金快照，并自动发起原路退款。
- 迟到支付自动退款失败时进入人工财务异常、保留告警和重试记录；不得通过“库存尚有余量”恢复订单。
- 定时对账扫描长期 `CREATING/OPEN/CLOSE_PENDING`、缺失回调及 Provider/本地状态差异，自动补记、重试关闭或补偿退款；无法自动收敛时转可审计人工财务异常。

### 11.11 销售分析

- ADM-02 通过概览、日销售、月销售、商品排行、客户排行标签承载当前版本销售分析，不新增 Excel 导出。
- 日/月销售报表至少展示周期净销售额、创建订单数、有效支付订单数和退款金额，并支持日期范围切换。创建订单按 `created_at` 计入含待付款/关闭的全部订单；有效支付订单按周期内首次支付成功且当前剩余实付大于 0 计。
- 商品销量排行以订单项成功支付数量减成功退款数量统计；客户消费排行以客户成功支付金额减成功退款金额统计。
- 报告数据以 Asia/Shanghai 分组，覆盖加载、空、错误和刷新状态；筛选条件返回页面时保留。
- 客户总数是当前未删除消费者账户数；新增注册按注册事件统计且删除不回写历史；新增绑定与注册分开；周期活跃代理是当前 `ACTIVE` 且周期内至少有一笔成功归属支付订单的代理。

### 11.12 并发裁决与管理员身份生命周期

- 两个绑定确认、客户转移与订单提交、代理停用与支付、主动取消/超时与支付、订单完成与退款均按 10.7 指定对象加锁或使用乐观版本，先成功提交者决定业务事实；后到请求返回最新状态而非静默覆盖。
- 首个超级管理员只由受控部署命令创建，禁止公开注册或默认口令。首次登录必须在 ADM-16 绑定 TOTP 并生成一次性恢复码。
- TOTP 周期 30 秒，接受当前时间步前后各一个窗口，记录已消费时间步防重放；连续失败 5 次锁定 15 分钟。恢复码只展示一次、逐个使用、以安全哈希保存。
- 密码或 TOTP 重置撤销该管理员全部会话；密码、TOTP 和恢复码全部丢失时，仅允许双人审批的离线恢复。创建、绑定、恢复、失败、锁定、重置和会话撤销均审计。

### 11.13 CH-016 消费者身份、服务代理与同步注销

- 小程序匿名读取服务端当前 `USER_AGREEMENT`、`PRIVACY_POLICY`、`PHONE_AUTHORIZATION` 三份快照。登录同意必须前两类各一次、`accepted=true` 且版本精确匹配；手机号授权单独匹配第三份。不匹配返回 409，不能创建错误的账户、资料、协议记录或会话。
- Store token 固定校验 `role=CUSTOMER`、`assurance=WECHAT`、`audience=qingxu-store`；管理端继续校验 `role=SUPER_ADMIN`、`assurance=MFA`、`audience=qingxu-admin-web`。Provider 不进入 token claim，只用于服务端 Adapter 选择和持久化来源。登录、refresh、logout、手机号与注销能力响应均 no-store，敏感命令只保存 `HASH_ONLY` 幂等事实。
- B7 固定一个消费者微信 AppID，以 `(AppID, openid)` 作为身份语义。现有 `account.wechat_open_id` 唯一约束仅在该 AppID 范围内有效；`wechat_union_id` 仅作可空元数据，不作为唯一登录键且不得自动合并账户。未来支持多个 AppID 必须另提变更并执行数据库迁移。
- profile 和账户手机号写入要求 `If-Match` 与新幂等键。客户端不能选择手机号 Provider；服务端按环境选择，Mock 只允许 development/test，production 缺真实微信配置时启动失败。
- 候选创建只提交 1-128 字符邀请码和 26 字符 ULID 推广物料 ID，目标由服务端解析。匿名 candidate token 仅首次返回，服务端只存与幂等/IP 不同 domain 的用途隔离 HMAC，30 分钟有效；GET 查询不消费，候选替换或登录迁移时原子失效 token hash；确认/拒绝消费迁移后的候选事实。各环节均验证当前主体绑定，不匹配返回 409。
- 服务代理响应只包含 `agent_id/display_name/bound_at`。长期绑定仍为 `BOUND` 时，即使代理停用也继续返回该投影；停用只阻止新候选、新绑定和未来订单归因，只有绑定结束或不存在时返回 null。账号注销 preview 始终 200；不合格时返回 blockers/impacts 且不签发能力，合格时才签发 5 分钟 token。同步 confirm 重检阻断并在单事务完成去标识化、全部会话撤销、候选失效、绑定结束与代理历史投影匿名化；新阻断返回 422，失败不得留下部分结果。
- B7 只准入 MP-07/18/19/20/21 的身份与隐私部分；收藏、服务端购物车、地址、结算、订单和资金链路继续关闭。

### 11.14 CH-018 登录后收藏、购物车与地址

- 收藏列表使用专用 `FavoriteProductView`，按 `created_at DESC,id DESC` 稳定分页；仅按 trim 后商品名称执行 1–200 字符大小写不敏感搜索。失效收藏继续可见，图片和最低活动价允许为空。
- 服务端购物车 GET 在无事实时返回 `cart_id=null,items=[]` 且不得写库；首次写入懒创建。项目状态闭合为 `SALEABLE/INSUFFICIENT_STOCK/OUT_OF_STOCK/INACTIVE/DELETED`，只汇总已选且可售项。
- 游客合并一次最多 100 个不同 SKU，全部已存在 SKU 才能原子提交；数量相加后封顶 99，选择状态采用 `existing OR incoming`。客户端保存固定幂等键和精确 journal，响应丢失时必须同键重试。
- 地址手机号和详细地址以 AES-256-GCM 保存并绑定字段级 AAD，手机号哈希使用独立 `qingxu:store-address-phone:v1` domain。列表只返回脱敏摘要；完整详情仅本人读取，写入不缓存 PII，PATCH/DELETE 要求 If-Match。
- 全部 B8 个性化响应使用 `no-store, private` 和 `no-cache`；8 个写操作使用 HASH_ONLY，不缓存响应正文。13 个接口共享 CUSTOMER 与来源 IP 组合 HMAC 的 120/60 秒 Redis 固定窗口，Redis 异常 fail closed。
- B8 不调用结算报价、库存预占、订单或支付接口；这些交易能力进入 B9 及后续阶段。

### 11.15 CH-020 结算报价、待付款订单与库存预占

- B9 保持既有 5 个 Store Checkout/Order operation，CH-020 实测 173 paths / 198 operations / 198 unique operationId / 325 schemas / 703 schema refs / 2,665 local refs / 0 dangling refs，Redocly 0 warning；不开放支付、物流或售后 operation。`CheckoutQuoteRequest` 接受 source、本人 ULID 地址和 1-100 个不重复 SKU；BUY_NOW 恰好一项，CART 必须精确匹配当前服务端已选购物车项。
- 报价返回脱敏地址摘要、当前商品/SKU/图片/价格/库存与金额。blocker 闭合为 `CART_SELECTION_CHANGED | ITEM_UNAVAILABLE | INSUFFICIENT_STOCK`；阻断报价仍返回 200 和 `can_submit=false`，但不签发确认凭证。首期运费固定 `0.00`。
- 可提交报价签发 5 分钟无状态 HMAC 凭证，使用现有幂等密钥环按 `qingxu:store-checkout-quote:v1` 域派生，绑定 CUSTOMER、auth session、规范请求、地址版本、商品/SKU/价格/库存事实、quote ID 和过期时间；不得落数据库、Redis、日志或审计。
- `OrderSubmitRequest` 重复精确 source/address/items 并携带 `quote_id`、`quote_token` 和 `confirmation_hash`。任一绑定或当前事实不匹配都返回 409 并要求重新报价，不留下部分订单/预占事实。
- 下单在 Serializable 事务中保存订单、订单项快照、重新加密的地址快照、归因候选、ACTIVE 预占和 `ORDER_RESERVE` 流水；数据库固定 `pay_expires_at=created_at+30 分钟`。首次下单没有既有 order 且 B9 不创建 payment intent，按 `idempotency -> account/customer -> CART/cart items -> address -> binding/agent -> brand -> category -> product -> SKU ASC -> balance ASC -> insert order/reservation/snapshots -> ledger -> audit/outbox` 加锁重验。CART 成功后只删除本次已选项，BUY_NOW 不修改购物车。
- 订单列表/详情仅本人可见，跨客户统一 404。主动取消必须携带 `If-Match` 和幂等键，仅适用未过期、待付款且无任何 payment intent 的订单；用户取消写 `RELEASED/USER_CANCELLED`，超时 Worker 写 `EXPIRED/PAYMENT_TIMEOUT`。
- 主动取消与超时 Worker 共用原子关闭逻辑，候选 reservation/SKU ID 仅无锁定位，锁内按 `idempotency（Worker 跳过） -> order -> payment_intent -> SKU ASC -> balance ASC -> reservation ASC -> ledger -> audit/outbox` 重验；使用数据库时间和 `FOR UPDATE SKIP LOCKED`，减少 `locked_qty`、写唯一 `ORDER_RELEASE` 流水、审计与 Outbox。发现任何 payment intent 时 fail closed 并留给 B10；下单/取消/超时须分别与 Product/SKU lifecycle confirm、库存调整通过无死锁并发验收。
- 新增 409 `CHECKOUT_QUOTE_EXPIRED | CHECKOUT_QUOTE_MISMATCH | CHECKOUT_REQUOTE_REQUIRED | ORDER_NOT_CANCELLABLE`。五个 B9 operation 共享 CUSTOMER+IP 120/60 fail-closed 限流与 no-store/private/no-cache；创建/取消使用 `HASH_ONLY` 并不缓存 PII。
- 两份原始 `0001_initial` 逐字节不变。新增事务型 `0002_b9_inventory_fact_indexes`，包含 `inventory_reservation_item(sku_id,reservation_id)` 与非空 business ID 的 ledger 事实条件唯一索引，不新增表、列或枚举。
- B9 不创建 payment intent、不调用 Provider、不冻结最终代理/佣金、不开放支付、物流、售后或 Admin/Agent 订单。

### 11.16 CH-022 支付、对账与迟到支付退款

- OpenAPI 升级为 `2.4.8-ch022`，本地解析实测为 173 paths / 198 operations / 198 unique operationId / 326 schemas / 705 schema refs / 2,678 local refs / 0 dangling refs；所有 order_id、payment_intent_id、refund_id 路径参数统一为 ULID。
- 服务端按环境选择 `MOCK | WECHAT` Provider，支付请求不得由客户端选择 Provider。Mock result 只在非 production 的 `development|test + MOCK` 注册，其中 `test` 仅服务 B10.6 真实 HTTP 纵向；production 配置 Mock 必须拒绝启动，production/WECHAT 不注册 Mock result，真实微信回调虽保留契约但不注册路由。
- 创建/继续支付使用 `Idempotency-Key` 和 `If-Match`，先在订单锁下保存稳定 `intent_no + CREATING`，再于事务外调用 Provider。同键重放返回同一 intent 当前投影；已有活动 intent 必须复用查询，只有失败终态且订单仍可支付时才可新建。
- Mock 结果只允许 `SUCCEEDED | FAILED | CANCELLED`，只验证并写 Inbox 后返回 202；交易号和事件号由服务端稳定生成，客户端不得提交交易号或 `SUCCEEDED_LATE`。支付尝试状态必须与数据库闭合集一致。
- Worker 在 Serializable 事务中消费支付结果：唯一写 attempt、更新 intent/订单、消费预占、同时扣减实物与锁定库存、写唯一 `ORDER_PAID_DEDUCT`，再冻结最终归因和佣金规则快照。可重建的 `product.sales_count` 仅在结算收敛时递增，首次进入 `MANUAL_REQUIRED` 不递增、补偿成功只递增一次，并在 PostgreSQL `integer` 上限饱和。不可修复的支付后配置异常保留成功收款事实并进入 `MANUAL_REQUIRED`，不得由销量缓存异常否认支付、静默发货或释放库存。
- 用户取消/超时遇到 `CREATING/OPEN` 时先写 `CLOSE_PENDING`，再于事务外 query/close。Provider 返回 UNKNOWN 时保持库存锁定；消费者取消返回 `202` 和 `CLOSE_PENDING` 当前投影。稳定游标必须遍历全部到期候选，不能只为异常订单翻页。
- 已关闭订单的支付成功写唯一 `SUCCEEDED_LATE`，订单保持关闭，不恢复库存、履约、归因或佣金，并创建唯一全额 `LATE_PAYMENT` 退款；退款尝试从 `INITIATED` 开始，失败或未知进入 `MANUAL_REQUIRED` 对账待办。
- MP-09 通过服务端查询确认支付结果，不信任客户端成功参数；journal 仅保存订单 ID、订单版本和幂等键，capability 只驻留内存。ADM-10 待办类型闭合为 `PAYMENT_INTENT | PAYMENT_SETTLEMENT | LATE_PAYMENT_REFUND`，只读展示并允许幂等 reconcile；200 表示已收敛，202 表示仍待 Provider 确认，列表及两类响应均不得包含 capability，也不提供直接状态修改。
- 支付个性化响应统一 `Cache-Control: no-store, private` 与 `Pragma: no-cache`；写操作使用 `HASH_ONLY`，不得缓存 Provider payload、支付 capability 或响应正文。
- 新增闭合错误 `ORDER_PAYMENT_EXPIRED | PAYMENT_NOT_ALLOWED | PAYMENT_RESULT_CONFLICT`（409）和 `PAYMENT_PROVIDER_UNAVAILABLE | PAYMENT_CONFIGURATION_UNAVAILABLE`（503）。
- 新增事务型 `0003_b10_payment_fact_indexes`：每个 intent 最多一个成功 attempt、每个订单最多一个 `origin_type=LATE_PAYMENT` 退款；创建前先检查历史重复事实，既有迁移逐字节不变。

| 交易 | SKU 购物车、地址、订单、订单项、库存预占、归因候选、支付归因快照、订单项佣金快照、支付意图/尝试/回调、退款项 | 服务端计价、稳定 intent_no、可恢复活动意图、库存事务、提交候选与支付最终冻结分离 |
| 履约售后 | 唯一包裹/包裹项、物流节点、退货地址版本/审核快照、售后/售后项、可退额度占用、退货物流、实收与验货处置、退款记录 | 消费者只提交商品数量；任一活动占用阻断整单发货，退款失败可重试，回库由事实决定 |
| 代理 | 代理档案、邀请码及轮换历史、商品推广授权 | 严格单层，不存在父代理字段业务含义；旧码失效不影响已有绑定 |
| 归属 | 游客待确认邀请码、消费者长期绑定、绑定变更记录 | 30 分钟候选、明确确认/拒绝、历史不可删除 |
| 佣金 | 平台默认规则、一级分类规则、SKU 覆盖规则、规则版本、订单项佣金快照、佣金流水、钱包余额 | 全代理共用；空值继承、0% 明确无佣金；版本与账本不可变、可复算、支持负数 |
| 提现 | 银行卡、提现申请、TOTP 二次验证短时查看授权、审核与付款凭证 | 银行卡加密、默认掩码、最小解密授权和线下付款审计 |
| 经营分析 | 日/月销售汇总、商品销量排行、客户消费排行 | 由支付、退款、订单项和客户事实聚合，不可手工编辑 |
| 风控 | 审计日志、幂等记录、支付/退款回调收件箱、事务 Outbox、文件权限、财务异常 | 可追溯、可重试且敏感信息脱敏 |

### 12.2 数据真相来源

- 商品当前展示以商品/SKU 数据为准；历史成交以订单快照为准。
- 购物车、订单项、库存、发货、售后和退款数量均以 `sku_id` 为最小关联键，不以商品 ID 替代 SKU。
- 销售额以成功支付与成功退款事实为准。
- 待付款订单的候选以提交时归因候选为准；已支付订单归属以支付成功冻结的代理快照为准，不根据当前绑定反推历史。
- 当前商品预计佣金比例以当前有效佣金规则版本按 `SKU > 一级分类 > 平台默认` 解析；历史佣金比例、来源和金额只以支付成功时的订单项佣金快照为准。
- 佣金以不可变佣金/钱包流水为准，缓存余额仅作加速且必须可复算。
- 提现状态以申请状态和审计事件为准，不以人工备注代替。
- 账户手机号只以已验证手机号记录为准，不从地址簿或订单收货手机号推导。
- 代理当前客户归属以当前长期绑定和代理 ACTIVE 资格为准；昵称脱敏只能由服务端生成，当前城市取最近归属已支付订单，历史订单可见信息以支付时脱敏客户快照为准。
- 退款进度只以成功退款事实累计；退款处理以当前退款尝试/异常为准，两者不得合并成一个可覆盖字段。
- 退货地址以审核通过时快照为准，退货实收、验货与回库以售后处置事实/库存流水为准，不能用当前地址或主订单状态反推。
- 日/月报表与排行以支付、退款、订单项和客户事实为准，不以页面缓存或手工汇总为准。

### 12.3 三端接口边界

- Supabase 仅作为 PostgreSQL 托管服务；消费者小程序、代理工作台和总部后台不得直连 Supabase Data API、PostgREST 或 Realtime，只能访问 NestJS 后端 API。
- 当前不采用 Supabase Auth 或 Supabase Storage。微信/账号登录、会话、RBAC、对象存储和文件鉴权继续由既有后端边界承担，数据库连接与服务端凭据不得下发三端客户端。
- 小程序接口只可访问公开商品和当前消费者本人数据。
- 代理接口仅可访问当前登录代理的授权商品、归属数据、账本和提现。
- 总部接口仅 `SUPER_ADMIN` 可访问，承担经营配置、履约、售后、代理和财务写操作；消费者可写本人购物、订单与售后数据，代理可写本人账户、银行卡和提现申请。
- Store、Agent、Admin 的商品、客户、订单、售后、代理、佣金、钱包和提现列表/详情分别使用终端专用 DTO；不得因字段名相同复用会泄露字段或混淆聚合范围的响应。Store 订单列表必须含商品/SKU 摘要、售后摘要和服务端可用动作；Agent 客户列表只接受当前有效绑定范围，Agent 订单列表固定为支付成功时 `final_agent_id=当前代理`；Admin 代理详情下钻必须携带并校验目标代理过滤条件。
- 佣金规则查询接口必须同时返回配置值、有效比例、命中来源和规则版本，并保持 `null`（继承）与 `0`（明确无佣金）的语义差异。
- 佣金规则写接口仅 `SUPER_ADMIN` 可调用，按平台、一级分类或 SKU 目标保存新版本；不得接收代理 ID、固定金额、阶梯或活动条件。保存需幂等并写审计。
- 支付接口内部逐订单项调用规则解析并原子保存订单项佣金快照；代理和小程序传入的比例、来源、版本或佣金金额一律忽略。
- 商品售后创建接口只接受订单项、数量、类型、原因、说明和凭证，不接受客户端金额；服务端使用订单项快照、成功退款和活动占用计算申请金额。后台纯金额补偿使用独立类型和接口，不得伪造数量。
- 退款接口必须携带可核验的退款订单项/补偿明细，并使用原订单项快照计算冲减；不得读取当前规则反算历史退款佣金。
- 购物车和订单创建接口使用 `sku_id` 与数量作为输入，服务端返回 SKU 当前报价和最终订单项快照；客户端价格、库存和商品 ID 不构成结算事实。
- 订单创建接口必须在幂等边界内返回已生成的 `PENDING_PAYMENT` 订单、`pay_expires_at` 和库存预占结果，且不得创建支付意图或调用 Provider；“稍后支付”不调用删除订单接口。
- 首次/重试支付接口必须在订单锁下创建或复用唯一活动支付意图；先落库稳定 `intent_no + CREATING`，再调用 Provider。Provider 意图 ID 按 `provider + provider_intent_id` 唯一，创建/关闭未知结果按 intent_no 查询恢复，不得并发创建第二笔活动意图。
- 主动取消和超时关单接口与支付确认按同一订单锁/版本号串行；活动意图进入 `CLOSE_PENDING` 后查询/关闭，确认不可支付前不得释放库存。
- 订单查询接口统一返回 `order_status`、`payment_status`、`refund_progress_status`、`refund_processing_status`、`fulfillment_status`、`close_reason`、`completion_reason` 和 `display_status`。
- 支付回调先写入回调收件箱并幂等处理；超时关单后的成功回调进入迟到支付自动退款，不得调用正常履约与佣金流程。
- 售后创建接口在事务内校验并占用订单项可退数量/服务端计算金额；发货接口只要检测到任一活动占用即整单拒绝。取消、驳回、验货后拒绝、退款失败和重试接口必须遵守占用释放规则。
- 退货审核响应返回地址快照；退货物流、实收验货、异常处置和回库为独立受控写操作。已发货全额退款只写 `COMPLETED + FULL_REFUND_AFTER_SHIPMENT`，不得改写既有履约事实。
- 手机号授权接口只接受 Provider credential 与 `PHONE_AUTHORIZATION` 同意，不接受客户端 Provider；服务端保存验证来源/时间/协议版本，要求 `If-Match` 和幂等且同一客户最多一条未撤回当前记录。常规资料和地址接口不得写账户手机号。
- 账号注销使用 `POST /store/privacy/deletion-requests/preview` 与 `POST /store/privacy/deletion-requests` 同步 confirm；删除旧 current GET。confirm 重检未完成订单/售后、未结清支付/退款和财务异常，无阻断时在单事务撤销全部会话并去标识化；命令使用 `HASH_ONLY`，不得重放完成响应。
- 归因候选创建只接受邀请码和推广物料 ID，目标由服务端解析；candidate token 使用用途隔离 HMAC 保存、30 分钟有效，查询不消费、替换或登录迁移时原子失效。服务代理只返回代理 ID、展示名和绑定时间。
- 邀请码轮换接口使旧码立即失效；旧推广链接解析接口在撤权时返回普通商品目标且不得设置候选。
- 金额使用 `DECIMAL(18,2)`，佣金比例使用 `DECIMAL(7,4)` 且校验 `0.0000-100.0000`；订单项佣金按 `基数 × 比例 / 100`、`HALF_UP` 保留两位后汇总。外部接口金额仍以十进制字符串传输。
- 完整收款账号只允许付款专用接口在本人 TOTP 短时授权内返回，不得复用常规提现详情接口。
- 临时密码、TOTP 绑定 URI/恢复码、邀请码明文、银行卡查看授权、`preview_token`/确认能力令牌和签名文件 URL 仅在签发响应返回一次，并统一 `Cache-Control: no-store`；普通 GET、列表、日志和审计详情不得重放这些值。
- 每类入口使用独立授权守卫或明确的作用域，禁止仅靠前端隐藏菜单。
- 13.4 矩阵中标记“预览/确认”的高风险写操作统一采用“预览 → 确认”协议：预览返回绑定主体、会话、动作、目标、请求哈希和资源版本的短时 `preview_token` 与 `confirmation_hash`；确认请求必须携带两者、`If-Match` 和新的幂等键，任一不匹配、过期、已消费或资源版本变化均拒绝。矩阵未要求原因或预览的动作不得由页面自行强制添加不适用字段。

## 13. 页面与交互规范

### 13.1 统一视觉方向

采用高端、简洁、适合洗化与美妆行业的品牌商城风格。视觉使用白色、炭黑、植物绿、灰蓝、珊瑚和琥珀作为功能色，不使用大面积渐变或装饰性光斑。卡片圆角不超过 8px，状态不仅依赖颜色表达。

### 13.2 小程序

- 商品图与价格优先，首屏不过度解释功能。
- 服务代理确认使用底部弹层，明确“商品价格、发货和售后由总部商城统一负责”，同时提供清晰的确认与拒绝动作；拒绝后清空待确认码。
- 服务代理页只读，不提供改绑、解除或佣金信息。
- 底部购买区尺寸稳定，SKU、数量和加载状态不得导致布局跳动。
- 购物车卡片必须展示具体 SKU 规格；同商品不同 SKU 独立成行，支付取消后从支付结果页可进入订单详情继续支付。
- 首页、分类、搜索和商品详情只渲染 Store 专用 `ACTIVE` 目录投影；不得接收管理状态、版本、锁定库存、成本或审计字段后在客户端隐藏。订单列表行固定展示商品/SKU 摘要、售后摘要、`display_status` 和服务端可用动作。
- 确认订单页不出现消费者订单留言/买家备注；内部审计备注只存在总部端且不回显消费者。
- 支付结果页在现有 MP-09 内承载成功、失败/取消、超时关闭、迟到支付自动退款和退款失败人工处理路径；活动支付意图未知时显示“正在确认结果”并轮询服务端，不允许用户重复创建支付。
- 订单详情以 `display_status` 为主，并在时间线展示支付、退款进度、退款处理和履约事实；未发货全额退款明确显示“退款完成”，已发货全额退款保留原物流时间线并显示完成原因。
- MP-13 只允许选择售后类型、订单项、数量、原因、说明和凭证，金额以服务端试算只读展示；提交按钮 pending 时禁用并复用幂等键。
- MP-14 在现页承载允许阶段取消、退货地址快照、退货物流填写、验货通过/异常及处置、`REFUND_FAILED` 人工重试进度，不新增页面。
- 手机号授权明确为可选操作，未授权不使用错误态；账号删除页先展示资格检查和不可逆影响，再允许二次确认。

### 13.3 一级代理工作台

- 桌面以紧凑侧栏、指标条、筛选表格为主；移动端重排为摘要列表和底部导航。
- 关键金额同时标注口径，预计佣金与可提现余额使用不同标签。
- 负余额使用明确文本和禁用原因，不能只显示红色数字。
- 客户和订单页面始终使用掩码字段，不设计“查看完整信息”按钮。
- 客户昵称只展示服务端脱敏结果，前端不接收原昵称后自行处理；客户列表只加载当前有效绑定和当前归属期聚合，不提供已结束/已转出客户筛选。客户转出后不再出现在当前客户列表，历史订单只能展示支付时冻结的脱敏快照，账号删除后展示不可逆客户代号。
- 订单列表只加载支付成功时冻结当前代理快照的订单，待付款候选不可见；行内展示商品/SKU、客户城市、金额、售后进度和状态，详情展示完整只读状态轴、关闭/完成原因、支付处置与时间线。
- 推广中心按 SKU 显示当前有效预计比例和预计佣金，并标注“以支付时规则为准”；`0%` 使用“无佣金”文本，不能表现为加载失败或继承。
- 佣金详情显示订单项支付快照的 SKU、命中来源、比例、基数和金额；多 SKU 订单按项展开，不展示订单平均比例。
- 推广二维码提供复制/下载反馈，不使用装饰性分享卡片替代实际二维码。
- 推广中心固定说明“白名单只限制可推广商品；已绑定客户购买全店商品仍按统一规则计佣”。客户手机号缺失显示“未绑定”，不得显示地址手机号尾号。
- AGT-01 展示统一的账号/密码错误、停用、限流和重试反馈；AGT-04 从客户详情进入订单时自动携带当前客户筛选；AGT-07/08 展示一笔进行中提现限制、重复提交幂等反馈；AGT-09 完整卡号仅在当次输入时存在，保存后只回显掩码。

## 15. 非功能需求

### 15.1 性能与兼容性

- 设计基线：核心 API 在 50 并发约定负载下 P95 小于 500ms，最终指标需结合真实规模校准。
- 商品列表、订单、客户、佣金和提现均分页，不一次返回全量。
- 图片使用对象存储、缩略图和懒加载；二维码生成失败可重试。
- 代理工作台支持现代 Chrome、Edge、Safari 和微信内置浏览器近两个主版本。

### 15.2 一致性与可靠性

- 库存锁定、支付结转与最终归因、订单完成佣金入账、退款冲正和提现冻结使用事务或可靠事件。
- 支付意图先以稳定 `intent_no + CREATING` 落库，活动状态唯一；主动取消、超时和支付按订单锁串行。活动意图先进入 `CLOSE_PENDING`，确认 Provider 不可支付后才关闭订单并释放库存。支付/退款回调先持久化到回调收件箱，领域事件通过事务 Outbox 投递。
- 对账任务必须收敛超时 `CREATING/OPEN/CLOSE_PENDING`、缺失回调和 Provider/本地差异，失败升级人工财务异常，不允许依赖无限自动重试。
- 售后创建、服务端金额计算、额度占用、整单发货门禁、退款成功回库和额度转已退款必须具备明确事务边界。
- 支付结转必须在同一一致性边界内读取一个确定的佣金规则版本并保存全部订单项快照，不能在同一订单内混用配置变更前后版本。
- 支付、退款、佣金、提现重复回调不得产生重复结果。
- 定时任务可重入，失败有重试、告警和人工补偿入口。
- 汇总余额、日/月报表和排行必须可由事实流水重建。

### 15.3 安全与隐私

- 密码安全哈希、登录限流、会话过期、受控首个管理员、管理员 TOTP/恢复码与敏感操作矩阵。
- 三端角色和数据范围在服务端强制执行。
- 银行卡字段级加密、文件访问鉴权、隐私字段最小化返回；完整收款账号仅允许付款专用接口在本人 TOTP 短时授权内返回一次。
- 短时授权与普通登录会话隔离，绑定单个提现申请，超时或离页自动失效；前端不得持久化、缓存或写日志。
- 完整收款账号响应必须使用 `Cache-Control: no-store, private`，不得写入幂等响应体、业务日志、审计前后值或监控追踪；幂等记录仅可保存状态码与响应摘要哈希，前端不得持久化明文到状态仓库、缓存或截图日志。
- 收款账号短时授权固定 60 秒且单次使用；连续验证失败 5 次锁定 15 分钟，锁定和解除均审计。
- 管理员 TOTP 周期 30 秒、允许 ±1 时间步并禁止重放；恢复码一次一用且只保存哈希。密码/TOTP 重置撤销全部会话，全凭据丢失的离线恢复必须双人审批。
- 账户手机号的授权和更新必须记录协议版本；地址手机号不得作为账户手机号的降级来源。
- 数据传输使用 HTTPS；生产密钥由安全配置管理，不写入仓库。
- 明确数据保留、账号注销权利、隐私授权和代理合作方保密义务。

### 15.4 可观测与审计

- 所有请求具备追踪 ID；关键状态变化记录业务对象、操作人和幂等键。完整收款账号的 TOTP 验证、查看、复制、超时和清除单独记录安全审计，但绝不记录账号内容。
- 对库存负数/锁定大于实物、库存预占未释放、支付意图长期 `CREATING/OPEN/CLOSE_PENDING`、迟到支付自动退款失败、售后额度超占、活动售后整单误发、验货异常久未处置、佣金规则解析失败、订单项无规则版本、重复佣金、退款累计冲减超限、负余额异常扩大、提现久未付款、TOTP 暴力尝试和越权拒绝率设置告警。
- 审计日志仅追加，普通业务操作不能删除。

## 16. 错误与边界处理

| 场景 | 系统处理 |
|---|---|
| 新邀请码不存在、过期或代理停用 | 不覆盖仍有效的待确认码；无有效候选时以直营身份继续，不暴露内部状态 |
| 未绑定游客在 30 分钟内打开多个有效代理码 | 携带有效旧候选 token 时，新码替换该候选并重置 30 分钟期限；未携带时两个匿名事实不可关联，旧候选自然过期 |
| 登录时待确认码已过期或用户拒绝 | 清空候选，不创建绑定，后续订单保持 DIRECT |
| 已登录未绑定用户打开有效代理链接 | 立即展示绑定确认，不强制退出或重新登录；完成后返回原页面 |
| 同一消费者并发确认两个不同代理 | 绑定行锁/版本号串行；首个提交胜出，后到返回当前绑定，不覆盖、不重复建历史 |
| 已绑定用户访问其他代理链接 | 保持原绑定，不出现改绑入口 |
| 提交订单后、支付前候选代理停用 | 支付时最终冻结为 DIRECT，不产生佣金 |
| 代理停用与支付确认并发 | 按代理版本串行；支付先提交保留代理快照，停用先提交则 DIRECT；购买和支付均不被代理失效阻断 |
| 支付成功后代理停用 | 已冻结 EXPECTED 保留，订单完成后仍进入 AVAILABLE |
| 代理重新启用 | 未转移绑定仅对未来提交/支付恢复；邀请码需自身有效；停用期 DIRECT 订单不追溯 |
| 平台/分类/SKU 规则在提交订单后、支付前被修改 | 支付成功时读取当时有效规则版本并逐订单项冻结，以服务端结果为准 |
| SKU 覆盖为空或为 0% | 空值继续继承一级分类；0% 立即命中并明确无佣金，不再继承 |
| 商品在提交订单后、支付前移动一级分类 | 支付时使用商品当时所属一级分类解析；支付后移动不改变快照 |
| 支付过程中规则刚好更新 | 单笔支付只使用一个确定的有效规则版本；成功订单不得出现跨版本订单项 |
| 佣金规则解析异常或缺失平台默认 | 支付不得生成不完整代理佣金；记录错误并进入可重试/人工补偿流程，不相信客户端比例 |
| 客户转移与订单提交并发 | 按绑定行/版本号串行；订单先提交保留旧候选，转移先提交则新订单使用新归属 |
| 客户已从原代理转出 | 从原代理客户列表/详情移除，仅历史订单返回支付时脱敏快照 |
| 白名单商品被移除、商品下架或邀请码轮换 | 代理端不再可生成新物料；既有链接退化为普通商品页且不设置新候选；已有绑定、历史订单及全店计佣不变 |
| 同一商品不同 SKU 加购 | 按 `sku_id` 分行；仅相同 SKU 合并数量，价格、库存和规格分别校验 |
| 单 SKU 购买超过 99 或可售库存 | 服务端拒绝或返回可调整上限 `min(99, 可售库存)`，不得依赖前端截断后静默下单 |
| 商品启用时没有合法公开商品图 | preview 显示缺口；confirm 返回 `PRODUCT_PRIMARY_IMAGE_REQUIRED` 422，不写状态或 `published_at` |
| 商品启用时没有 ACTIVE SKU | preview 显示缺口；confirm 返回 `PRODUCT_ACTIVE_SKU_REQUIRED` 422，不写状态或 `published_at` |
| 软删除商品时仍有 ACTIVE SKU | preview 返回依赖清单；confirm 返回 `ACTIVE_SKU_DEPENDENCY` 422，不消费 preview |
| 软删除商品或 SKU 时存在活动预占 | preview 返回预占影响；confirm 返回 `ACTIVE_INVENTORY_RESERVATION` 422，已有待付款订单保持原事实 |
| 商品下架/软删除时存在待付款预占 | 普通下架阻止新加购/结算但已有有效预占可支付；活动预占阻断商品/SKU 软删除 |
| 用户提交订单后选择稍后支付或取消支付 | 保留待付款订单和库存预占，未过期时可从订单详情继续支付 |
| Provider 创建支付意图返回未知 | 本地保持 `CREATING`，按稳定 `intent_no` 查询恢复；不得创建第二活动意图或向用户显示确定失败 |
| Provider 关闭支付意图返回未知 | 本地保持 `CLOSE_PENDING` 和库存预占，由对账查询/重试；确认不可支付前不得关单释放 |
| 用户主动取消、超时任务与支付确认并发 | 同一订单锁/版本号串行；支付先提交则关单失败，关单先提交则后到成功进入迟到支付退款 |
| 订单支付时限到达 | 无活动意图可本地关单；有 `CREATING/OPEN/CLOSE_PENDING` 时先查询/关闭 Provider，确认不可支付后才关闭订单并幂等释放 |
| 超时关单后收到支付成功 | 保存迟到支付事实，订单/履约/佣金保持关闭，立即自动原路退款；失败进入人工财务异常 |
| 并发售后申请同一订单项 | 仅占用后仍在剩余可退数量/金额内的申请成功，其余返回可退额度不足 |
| 客户端篡改或提交售后金额 | 忽略/拒绝金额字段，服务端按订单项快照、成功退款和活动占用重新计算，只接收数量等允许字段 |
| 售后待处理时总部尝试发货 | 任一订单项存在活动占用即阻断整单发货，并返回占用列表；不得只发未占用商品 |
| 用户取消售后 | 仅待审核或未提交退货物流的待寄回状态允许；成功取消释放可退额度 |
| 退款调用失败 | 售后进入 `REFUND_FAILED`，保留可退额度占用，不更新净额、库存和佣金；新重试使用新幂等键并追加退款尝试，但复用原退款单与商户退款号 |
| 未发货部分/全额退款成功 | 按 SKU 自动回补退款数量；部分退款须等整单活动占用全部解决后按最终剩余数量创建唯一包裹，全额退款关闭订单并取消履约 |
| 退货地址在审核后变更 | 售后继续使用审核通过时地址快照；新地址只用于之后审核通过的售后 |
| 退货验货异常 | 进入 `RETURN_EXCEPTION` 并封存至少一份证据；总部只可一次写入 `CONTINUE_REFUND/REJECT_AFTER_RETURN`，继续退款原因必填，只有明确回库数量生成库存流水；PASS 可零证据但同样封存空清单 |
| 已发货订单全额退款成功 | 订单 `COMPLETED + FULL_REFUND_AFTER_SHIPMENT`，退款进度 FULL；履约、包裹和物流事实不回退 |
| 订单完成与退款成功并发 | 按订单/订单项佣金快照串行；退款先提交只入剩余佣金，完成先提交追加冲正，净值相同且无重复流水 |
| 分类或品牌存在在售商品时停用 | 阻止操作并提供迁移/下架入口；历史记录不删除 |
| 账户手机号未授权 | 显示“未绑定”，不使用地址手机号替代，不阻断下单 |

| 账号删除完成后代理查看历史 | 返回不可逆客户代号且无手机号尾号，仅保留法定交易/审计事实，不返回后续或原始资料 |
| 完成后全额退款且余额不足 | 生成负向流水并允许余额为负，冻结新提现 |

| 提现提交与退款并发 | 事务串行校验余额；只允许一个操作基于同一版本成功 |
| 代理重复点击提交提现 | 幂等返回同一申请，不重复冻结余额 |
| 审核时代理已停用 | 历史申请保留，超级管理员可结合政策审核并记录原因 |
| 付款凭证上传失败 | 保持 `APPROVED`，不得标记 `PAID`，允许重试 |
| 越权访问其他代理客户/订单 | 返回统一无权限或不存在响应并记录安全日志 |
| 银行卡解密或 TOTP 服务不可用 | 禁止完整账号查看与付款确认，不回显密文或降级为明文 |
| 完整账号短时授权过期或离页 | 立即恢复掩码，复制入口失效，再次查看必须重新验证本人 TOTP |
| 完整账号 TOTP 连续失败 5 次 | 当前管理员锁定 15 分钟，期间不得签发新查看授权并记录安全审计 |
| 管理员密码/TOTP 重置或全凭据丢失 | 重置撤销全部旧会话；全丢失只走双人离线恢复，不提供绕过 TOTP 的普通接口 |
| 高风险写操作发生版本冲突或重复提交 | 只允许一个请求成功；其余返回最新状态和可刷新提示，不重复写审计或账务 |
| 销售报告加载失败 | 保留筛选条件，显示错误状态和重试，不以旧缓存冒充最新数据 |

## 19. 延期需求清单

| 延期能力 | 延期原因 | 当前仅保留的边界 |
|---|---|---|
| 多级/二级代理、团队佣金 | 关系链、合规和结算复杂度显著上升 | 当前代理实体严格无业务父级 |
| 代理进货与独立店铺 | 会改变商户、库存、价格、收款和售后主体 | 当前总部统一经营 |
| 自动打款/微信零钱提现 | 需要支付服务商、实名、税务和风控 | 当前线下银行转账与凭证 |
| 代理专属/代理 × SKU、固定金额、阶梯、活动佣金 | 形成组合爆炸并显著增加结算与合同复杂度 | 当前所有一级代理共用平台/分类/SKU 百分比规则 |
| 会员、优惠券、积分、新人优惠 | 需要定价优先级和分摊规则 | 定价/促销扩展边界 |
| 拼团、秒杀 | 活动库存与高并发状态复杂 | 活动领域扩展边界 |
| 商品视频与 AI 客服 | 媒体、模型、审核和隐私成本 | 文件与客服集成边界 |
| Excel 导出和自定义报表中心 | 需异步任务、权限和隐私水印 | 当前已提供固定日/月销售、商品和客户排行 |
| 真实物流轨迹、多仓、多包裹 | 改变库存与履约模型 | 物流 Provider 与包裹实体边界 |

延期能力不得出现对用户可见但不可用的入口。单层代理是当前业务约束，不是界面文案上的临时隐藏。

## 20. 发布与回滚原则

- CH-010 的 B4.0 至 B4.4 development 已在每个子批次 P0/P1 清零后完成；staging 前仍须外部独立复核，生产发布仍需微信、Supabase staging、恢复演练和合规门禁。
- B4 已进入业务实现，不再整体回滚 CH-010 契约；需要回退时只关闭 Product/SKU 模块路由和 ADM-03/04 导航，不执行数据库降级。
- 未来开发环境必须明确区分 development、test、staging、production。
- 数据库发布采用 PostgreSQL 向后兼容迁移；订单、归属、佣金和提现表禁止人工直接修改。
- 发布前执行 migration、构建、单元、集成、E2E、权限与响应式检查。
- 若出现库存、重复佣金、越权访问或提现账实不符，应暂停对应写入口并保留查询与审计。
- CH-020 尚未进入 B9.1 前可整体回滚文档、OpenAPI、generated contracts 和原型；进入业务实现后只关闭 Store Checkout/Order 路由和小程序导航。`0002_b9_inventory_fact_indexes` 为加法索引迁移，代码回退时保留，不执行数据库降级。
- B10.1 已完成，不能再整体回滚 CH-022 基线；当前可关闭支付意图路由、Mock 结果入口和 B10.2 支付结果 Worker handler 回退应用实现。`0003_b10_payment_fact_indexes` 与已部署后的 `0004_b10_commission_position_trigger_fix` 均保留，不恢复旧 `FOR SHARE`，不执行数据库降级。
- B11.1 尚未准入，可在业务代码开始前整体回滚 CH-024 文档、OpenAPI 和 generated contracts；B11 为零迁移阶段，不执行数据库降级。进入业务实现后只能关闭 Store/Admin 履约路由及对应导航回退，历史订单、支付、库存和佣金事实不得回写。
