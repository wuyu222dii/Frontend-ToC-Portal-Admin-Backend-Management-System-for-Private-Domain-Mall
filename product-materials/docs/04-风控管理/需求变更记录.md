## 三、CH-001 变更详情

### 3.1 变更申请

- **申请日期**：2026-08-10
- **申请来源**：业务负责人明确调整
- **变更类型**：新增需求与原有需求修改
- **紧急程度**：高，必须在开发前完成范围纠偏

变更前产品只有消费者小程序和总部管理后台，后台采用两类内部权限，渠道推广与结算能力尚未纳入当前范围。

变更后产品为三个终端和三类人员：

1. 总部管理后台，角色 `SUPER_ADMIN`。
2. 一级代理工作台，角色 `AGENT_ADMIN`，属于外部推广合作方。
3. 消费者微信小程序，角色 `CUSTOMER`。

游客仍为未登录状态，不新增人员角色。原总部最高权限映射为 `SUPER_ADMIN`，原总部内部普通操作角色从当前范围移除。

### 3.2 业务边界

- 代理严格单层，由超级管理员创建，不存在下级代理。
- 总部统一商品、零售价、库存、收款、发货、退款和售后。
- 代理仅推广和只读查看本人脱敏客户、订单、售后进度、佣金与提现。
- 代理不能改价、改库存、代客下单、发货、退款或处理售后。
- 未绑定游客保存 30 分钟有效候选；只有客户端携带有效旧候选 token 时新候选才替换该事实，未携带时旧候选自然过期；登录后确认成功才建立长期绑定，拒绝则清空候选并保持直营。
- 超级管理员可转移到其他 ACTIVE 代理或 DIRECT，但只影响转移后提交的新订单，历史订单与佣金快照不变。
- 提交订单只记录归因候选，支付成功时复核代理 ACTIVE 后最终冻结；支付前停用转 DIRECT，支付后停用不影响已冻结 EXPECTED。
- 佣金按订单项净商品实付金额和支付时有效比例计算；具体比例来源由后续已批准的 CH-002 统一商品规则定义。
- 确认收货或总部兜底完成后，佣金立即转为可提现，不设置额外等待期。
- 完成前全退将 EXPECTED 标记为 CANCELLED；完成后保留 AVAILABLE 并追加 REFUND_DEBIT；余额可为负并阻止提现。
- 提现由代理申请、总部审核、线下银行转账、上传凭证并标记已支付；完整收款账号默认掩码，仅付款环节二次验证后短时查看/复制并全量审计。
- 代理默认授权全部当前及未来在售商品，超级管理员可切换自定义白名单。
- ADM-16 配置默认 100 元最低提现与默认 7 天售后申请期；ADM-02 纳入日/月销售、商品销量和客户消费排行。

变更前，佣金比例配置在代理档案上，同一个代理推广的全部商品使用同一比例。这不能表达不同品类、商品规格的毛利和推广策略差异。

变更后，所有一级代理共用一套由商品维度决定的百分比佣金规则：

1. 平台默认比例提供兜底。
2. 商品所属一级分类可配置分类默认比例。
3. SKU 可配置覆盖比例。
4. 解析优先级固定为 `SKU 覆盖 > 商品一级分类默认 > 平台默认`。
5. 空值表示继承，`0%` 表示明确无佣金并终止继承。
6. 现有商品一级分类直接作为佣金分类来源，不另建运营分类体系。
7. 不再在代理档案维护佣金比例，所有一级代理在同一规则版本下推广相同 SKU 时采用相同比例。

### 4.2 业务边界

- 佣金基数继续使用订单项净商品实付金额，首期不含运费。

- 支付成功时逐订单项冻结规则版本、命中来源、一级分类、商品、SKU、比例、基数和佣金金额。
- 待付款订单按支付成功时有效规则结算；规则修改、商品移动分类或 SKU 覆盖清空不追溯已支付订单。
- 常规退款按原订单项支付快照比例和实际成功退款金额冲减。
- 同一订单项累计冲减不得超过原佣金；最后一笔使订单项全额退清时，直接冲减剩余佣金以消除舍入尾差。

- 当前版本排除代理专属比例、“代理 × SKU”、固定金额、销量/金额阶梯和限时活动佣金。

### 5.2 业务边界

- 超时任务先关闭支付意图和订单，再释放库存。关单后支付成功记录为迟到支付并自动原路退款；失败进入人工财务异常，绝不恢复履约和佣金。
- 订单、支付、退款和履约采用独立状态轴，接口统一返回四状态、`close_reason` 和 `display_status`。
- 未发货部分退款自动回库退款数量并只发剩余数量；未发货全额退款后订单 `CLOSED`、`close_reason=FULL_REFUND_BEFORE_SHIPMENT`、履约 `CANCELLED`。

- 原订单项佣金快照和正向流水不可修改；完成前退款追加预计减少/取消流水，完成后退款追加 `REFUND_DEBIT`。

### 7.2 已冻结业务决策

1. 首期严格单商户、单仓、单包裹。任一未发货订单项存在活动售后占用，整单不得创建或确认发货；全部占用释放或成功退款后，仅按最终剩余数量创建唯一包裹。

3. 佣金公式固定为 `基数 × 比例 / 100`，按订单项 `HALF_UP` 保留两位后汇总；比例使用 `DECIMAL(7,4)`，范围 `0.0000%-100.0000%`（含边界），超范围拒绝。
4. 支付意图先落库稳定 `intent_no + CREATING` 再调用 Provider；`CREATING/OPEN/CLOSE_PENDING` 视为活动状态且每单最多一个。创建/关闭结果未知按 intent_no 查询恢复，不得盲目新建或提前释放库存；对账任务负责补记、关闭、补偿和人工财务异常升级。
5. 用户主动取消、超时任务和支付确认使用同一订单锁/版本号串行。支付先提交则关单失败；关单先提交则后到成功为迟到支付并自动退款。活动意图未确认不可支付前不得释放库存。
6. 退款拆为 `refund_progress_status=NONE/PARTIAL/FULL` 与 `refund_processing_status=IDLE/REFUNDING/FAILED`。前者仅按成功退款派生，后者表达处理/异常；允许 `PARTIAL + FAILED` 并优先提示失败。
7. ADM-16 维护唯一当前总部退货地址，审核通过时保存不可变地址快照。总部验货请求一次精确覆盖全部售后项，逐项记录退货物流、实收、批准退款数量、验货结果 `PASS/ABNORMAL`、证据，以及回库、损坏、报废、退回客户四类处置；逐项满足“批准退款 + 退回客户 = 实收”“批准退款 = 回库 + 损坏 + 报废”。`PASS` 仅允许全量实收/全量批准且不退回客户，可零证据；少件、0 件或不符必须 `ABNORMAL` 且至少一份证据，两类证据清单均在提交时封存。异常只允许一次把类型化 `resolution` 写为 `CONTINUE_REFUND` 或 `REJECT_AFTER_RETURN`，继续退款原因必填且只能使用冻结批准数量，解决事实不可改写。已发货全额退款以 `COMPLETED + completion_reason=FULL_REFUND_AFTER_SHIPMENT` 结束，原包裹、物流和签收事实不回退。

### 8.2 已批准契约决策

1. `BrandCreateRequest.sort_order` 为必填非负整数；`BrandUpdateRequest.sort_order` 为可选非负整数，与一级分类对称。品牌和分类列表固定按 `sort_order ASC,id ASC`。
2. 品牌、分类创建继续携带 `initial_status`，但值固定为 `DRAFT`，不得创建即启用。
3. 新增品牌/分类专用的闭合 `MasterDataLifecycleAction`，动作仅为 `ACTIVATE/DEACTIVATE/SOFT_DELETE`，原因 2-500 字符；商品/SKU 继续使用原 `LifecycleAction`，不得获得 ACTIVATE。
4. 状态机固定为：非删除 `DRAFT/INACTIVE -> ACTIVATE -> ACTIVE`；非删除 `ACTIVE -> DEACTIVATE -> INACTIVE`；非删除 `DRAFT/INACTIVE -> SOFT_DELETE -> ARCHIVED + deleted_at`；`ACTIVE` 不得直接软删除。
5. ACTIVATE、DEACTIVATE、SOFT_DELETE 均先 preview，再以相同请求、未过期 token、新幂等键和 `If-Match` 确认。非法或同状态的新请求返回 409；同幂等键精确重放仍按公共幂等规则返回原结果。
6. restore 仅适用于软删除的 ARCHIVED 记录，保持现有“原因 + `If-Match` + 幂等”接口，不新增 restore-preview；成功后清除 `deleted_at`、状态固定回到 `DRAFT`、版本加一。重新启用必须另走 ACTIVATE preview/confirm。
7. 默认列表排除软删除记录；显式 `status=ARCHIVED` 仅返回软删除归档记录；按 ID 详情允许读取 ARCHIVED 以支持恢复。
8. 品牌/分类存在 ACTIVE 商品时，DEACTIVATE 和 SOFT_DELETE 的 preview 仍返回 200 并列出影响，confirm 以 `ACTIVE_PRODUCT_DEPENDENCY` 422 阻断。软删除业务键全局保留，再次创建返回 `SOFT_DELETED_KEY_RESERVED` 409。
9. `UploadIntentRequest` 增加必填 `sha256`，格式为 64 位小写十六进制；七类 purpose 统一仅接受 `image/jpeg`、`image/png`，单文件最大 5 MiB。
10. complete 请求的 SHA-256 和 size 必须同时匹配 intent 与服务端读取对象后的 MIME、魔数、大小和 SHA-256 实测值，不一致返回 `FILE_CONTENT_MISMATCH` 422。
11. 上传签名有效 15 分钟，私有下载签名有效 5 分钟；PENDING/staging 满 24 小时才进入清理候选。对象键固定使用 staging/public/private 分区且不包含原文件名。
12. bucket 默认私有，只允许 `public/*` 匿名 GET；售后、提现和推广 QR 始终使用 `private/*`，不得由客户端或 purpose 旁路改变可见性。
13. 不新增 `completed_at` 或 `updated_at` 数据库列。complete 成功事实由 `status=READY`、最终对象 key、服务端实测内容、审计与幂等记录表达；首次 `completed_at` 只保存在闭合 `FILE_UPLOAD_COMPLETE` 响应及其幂等正文，同键同请求精确重放，新键重复 complete 返回 409。
14. 上传意图和 lifecycle preview 使用 `HASH_ONLY`，不得把签名 URL、请求头或 preview token 保存到幂等响应正文；下载签名 GET 的幂等语义以 CH-008 勘误为准，不创建幂等记录。

6. Product ACTIVATE 必须同时满足品牌 ACTIVE、分类 ACTIVE、至少一张 `READY/PUBLIC/PRODUCT_IMAGE` 活动图和至少一个 ACTIVE SKU。`published_at` 只在首次 ACTIVATE 时写入，重新启用不得覆盖。
7. Product 与 SKU 的 ACTIVATE、DEACTIVATE、SOFT_DELETE 均须先 preview，再以相同业务字段、未过期 token/确认哈希、新幂等键和 `If-Match` confirm；`reason` 写入既有 `audit_log.reason`。restore 不新增 preview，仍要求原因、新幂等键和 `If-Match`。
8. Product 列表固定 `published_at DESC NULLS LAST,id DESC`；没有 ACTIVE SKU 时 `minimum_active_price=null`。默认列表排除 ARCHIVED，显式归档筛选和按 ID 详情允许读取归档 Product。
9. Product 详情返回全部 SKU，包括 ARCHIVED，固定按 `created_at ASC,id ASC`；图集最多 8 张，活动关系固定按 `sort_order ASC,id ASC` 返回。
10. Product 的 `spu_code` 和 SKU 的 `code` 创建后永不可修改，软删除后继续全局保留，只能恢复原记录。SKU 创建响应为 HTTP 201，并在同一事务创建 `physical_qty=0,locked_qty=0` 的 `inventory_balance`，可售库存派生为 0。
11. 新增四个 422 业务码：`PRODUCT_PRIMARY_IMAGE_REQUIRED`、`PRODUCT_ACTIVE_SKU_REQUIRED`、`ACTIVE_SKU_DEPENDENCY`、`ACTIVE_INVENTORY_RESERVATION`。preview 可返回依赖影响，confirm 才执行阻断并且不得消费失败的 preview。
12. 状态、`published_at`、`deleted_at`、图集关系、SKU 与库存余额均使用现有字段；不新增迁移，Prisma 与 `0001_initial` 必须逐字节不变。

**CH-010 勘误（2026-08-24）**：B4.1 实现审计发现共享 `PositiveMoney` 正则未限制整数位数，与已批准且冻结的 `DECIMAL(18,2)` 存储边界不一致；后台商品 `keyword` 也漏写了实现采用的 200 字符查询上限。现将金额收紧为大于 0、固定 2 位小数、整数部分最多 16 位，并补齐 `keyword.maxLength=200`。这些调整只排除数据库无法存储或超出受控查询边界的输入，不新增需求或数据库变更，不另行登记 CH。
