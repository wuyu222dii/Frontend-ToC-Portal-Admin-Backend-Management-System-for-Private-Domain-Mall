## 三、CH-001 变更详情

### 3.1 变更申请

- **申请日期**：2026-08-10
- **申请来源**：业务负责人明确调整
- **变更类型**：新增需求与原有需求修改
- **紧急程度**：高，必须在开发前完成范围纠偏

变更前产品只有消费者小程序和总部管理后台，后台采用两类内部权限，渠道推广与结算能力尚未纳入当前范围。

变更后产品为三个终端和三类人员：

1. 总部管理后台，角色 `SUPER_ADMIN`。
2. 一级代理工作台，角色 `AGENT_ADMIN`，属于外部推广合作方。
3. 消费者微信小程序，角色 `CUSTOMER`。

游客仍为未登录状态，不新增人员角色。原总部最高权限映射为 `SUPER_ADMIN`，原总部内部普通操作角色从当前范围移除。

### 3.2 业务边界

- 代理严格单层，由超级管理员创建，不存在下级代理。
- 总部统一商品、零售价、库存、收款、发货、退款和售后。
- 代理仅推广和只读查看本人脱敏客户、订单、售后进度、佣金与提现。
- 代理不能改价、改库存、代客下单、发货、退款或处理售后。
- 未绑定游客保存最后一个有效邀请码，TTL 30 分钟；登录后确认成功才建立长期绑定，拒绝则清空候选并保持直营。
- 超级管理员可转移到其他 ACTIVE 代理或 DIRECT，但只影响转移后提交的新订单，历史订单与佣金快照不变。
- 提交订单只记录归因候选，支付成功时复核代理 ACTIVE 后最终冻结；支付前停用转 DIRECT，支付后停用不影响已冻结 EXPECTED。
- 佣金按订单项净商品实付金额和支付时有效比例计算；具体比例来源由后续已批准的 CH-002 统一商品规则定义。
- 确认收货或总部兜底完成后，佣金立即转为可提现，不设置额外等待期。
- 完成前全退将 EXPECTED 标记为 CANCELLED；完成后保留 AVAILABLE 并追加 REFUND_DEBIT；余额可为负并阻止提现。
- 提现由代理申请、总部审核、线下银行转账、上传凭证并标记已支付；完整收款账号默认掩码，仅付款环节二次验证后短时查看/复制并全量审计。
- 代理默认授权全部当前及未来在售商品，超级管理员可切换自定义白名单。
- ADM-16 配置默认 100 元最低提现与默认 7 天售后申请期；ADM-02 纳入日/月销售、商品销量和客户消费排行。

## 四、CH-002 变更详情

### 4.1 变更申请

- **申请日期**：2026-08-11
- **申请来源**：用户明确提出并批准的业务规则调整
- **变更类型**：修改现有佣金配置与计算需求
- **影响程度**：重大
- **执行时机**：设计阶段立即实施，开发前完成基线替换

变更前，佣金比例配置在代理档案上，同一个代理推广的全部商品使用同一比例。这不能表达不同品类、商品规格的毛利和推广策略差异。

变更后，所有一级代理共用一套由商品维度决定的百分比佣金规则：

1. 平台默认比例提供兜底。
2. 商品所属一级分类可配置分类默认比例。
3. SKU 可配置覆盖比例。
4. 解析优先级固定为 `SKU 覆盖 > 商品一级分类默认 > 平台默认`。
5. 空值表示继承，`0%` 表示明确无佣金并终止继承。
6. 现有商品一级分类直接作为佣金分类来源，不另建运营分类体系。
7. 不再在代理档案维护佣金比例，所有一级代理在同一规则版本下推广相同 SKU 时采用相同比例。

### 4.2 业务边界

- 佣金基数继续使用订单项净商品实付金额，首期不含运费。
- 单个订单项佣金 = `订单项净商品实付金额 × 支付时有效比例 / 100`；订单佣金为各订单项逐项舍入后的金额之和。
- 支付成功时逐订单项冻结规则版本、命中来源、一级分类、商品、SKU、比例、基数和佣金金额。
- 待付款订单按支付成功时有效规则结算；规则修改、商品移动分类或 SKU 覆盖清空不追溯已支付订单。
- 常规退款按原订单项支付快照比例和实际成功退款金额冲减。
- 同一订单项累计冲减不得超过原佣金；最后一笔使订单项全额退清时，直接冲减剩余佣金以消除舍入尾差。
- 保留 `EXPECTED`、`CANCELLED`、`AVAILABLE`、`REFUND_DEBIT` 生命周期，以及不可变流水、负余额、提现限制和线下付款规则。
- 当前版本排除代理专属比例、“代理 × SKU”、固定金额、销量/金额阶梯和限时活动佣金。

### 7.2 已冻结业务决策

1. 首期严格单商户、单仓、单包裹。任一未发货订单项存在活动售后占用，整单不得创建或确认发货；全部占用释放或成功退款后，仅按最终剩余数量创建唯一包裹。
2. 商品售后客户端只提交订单项、数量、类型、原因、说明和凭证，不提交金额。服务端按订单项成交/优惠分摊快照、成功退款和活动占用计算金额；尾笔使用剩余可退金额清尾差。纯金额补偿使用总部专属 `AMOUNT_COMPENSATION`，不占数量、不回库但占金额并冲正佣金。
3. 佣金公式固定为 `基数 × 比例 / 100`，按订单项 `HALF_UP` 保留两位后汇总；比例使用 `DECIMAL(7,4)`，范围 `0.0000%-100.0000%`（含边界），超范围拒绝。
4. 支付意图先落库稳定 `intent_no + CREATING` 再调用 Provider；`CREATING/OPEN/CLOSE_PENDING` 视为活动状态且每单最多一个。创建/关闭结果未知按 intent_no 查询恢复，不得盲目新建或提前释放库存；对账任务负责补记、关闭、补偿和人工财务异常升级。
5. 用户主动取消、超时任务和支付确认使用同一订单锁/版本号串行。支付先提交则关单失败；关单先提交则后到成功为迟到支付并自动退款。活动意图未确认不可支付前不得释放库存。
6. 退款拆为 `refund_progress_status=NONE/PARTIAL/FULL` 与 `refund_processing_status=IDLE/REFUNDING/FAILED`。前者仅按成功退款派生，后者表达处理/异常；允许 `PARTIAL + FAILED` 并优先提示失败。
7. ADM-16 维护唯一当前总部退货地址，审核通过时保存不可变地址快照。总部验货请求一次精确覆盖全部售后项，逐项记录退货物流、实收、批准退款数量、验货结果 `PASS/ABNORMAL`、证据，以及回库、损坏、报废、退回客户四类处置；逐项满足“批准退款 + 退回客户 = 实收”“批准退款 = 回库 + 损坏 + 报废”。`PASS` 仅允许全量实收/全量批准且不退回客户，可零证据；少件、0 件或不符必须 `ABNORMAL` 且至少一份证据，两类证据清单均在提交时封存。异常只允许一次把类型化 `resolution` 写为 `CONTINUE_REFUND` 或 `REJECT_AFTER_RETURN`，继续退款原因必填且只能使用冻结批准数量，解决事实不可改写。已发货全额退款以 `COMPLETED + completion_reason=FULL_REFUND_AFTER_SHIPMENT` 结束，原包裹、物流和签收事实不回退。
8. 并发裁决固定为：两个绑定确认首个提交胜出；客户转移与订单提交按绑定版本先提交者决定候选；代理停用与支付按代理版本先提交者决定 `AGENT/DIRECT`；订单完成与退款按订单项佣金快照串行并保证两种顺序净结果一致。
9. 邀请码、代理或候选失效时只把归因降级为 `DIRECT`，不得阻断消费者浏览、下单或支付。撤权旧推广链接不再建候选，但可作为普通商品链接打开。
10. 账号删除除未完成订单/售后外，还阻断未结清支付、退款和财务异常；完成后撤销会话、结束绑定/候选，清空微信主体与资料，硬删除手机号验证、地址、收藏和购物车项的密文/HMAC/尾号/密钥标识，代理投影仅留不可逆代号；交易与审计事实按外部合规策略保留且不再通过当前资料接口关联原主体。
11. 品牌、分类、商品和 SKU 软删除。存在在售商品的品牌/分类禁止停用；商品/SKU 存在活动预占时禁止软删除。普通下架阻止新加购/结算，但下架前合法预占订单可在 `pay_expires_at` 前支付；库存始终满足 `实物 >= 锁定 >= 0`。
12. 代理端昵称只使用服务端脱敏值；当前城市取最近一笔本人归属已支付订单，无订单显示“暂无”。历史订单使用支付时订单城市快照，账号删除后显示不可逆客户代号且无手机号尾号。
13. 首个超级管理员只由受控部署命令创建。管理员使用 30 秒 TOTP，允许前后各一个时间步并防重放；连续失败 5 次锁定 15 分钟，恢复码一次一用且只保存哈希。密码/TOTP 重置撤销全部会话；全凭据丢失只允许双人审批离线恢复。

20. `pay_expires_at` 由数据库固定为订单 `created_at + 30 分钟` 并在创建后不可修改；ADM-16 只读展示，任何角色或配置均不能延长/缩短既有订单期限。

### 8.2 已批准契约决策

1. `BrandCreateRequest.sort_order` 为必填非负整数；`BrandUpdateRequest.sort_order` 为可选非负整数，与一级分类对称。品牌和分类列表固定按 `sort_order ASC,id ASC`。
2. 品牌、分类创建继续携带 `initial_status`，但值固定为 `DRAFT`，不得创建即启用。
3. 新增品牌/分类专用的闭合 `MasterDataLifecycleAction`，动作仅为 `ACTIVATE/DEACTIVATE/SOFT_DELETE`，原因 2-500 字符；商品/SKU 继续使用原 `LifecycleAction`，不得获得 ACTIVATE。
4. 状态机固定为：非删除 `DRAFT/INACTIVE -> ACTIVATE -> ACTIVE`；非删除 `ACTIVE -> DEACTIVATE -> INACTIVE`；非删除 `DRAFT/INACTIVE -> SOFT_DELETE -> ARCHIVED + deleted_at`；`ACTIVE` 不得直接软删除。
5. ACTIVATE、DEACTIVATE、SOFT_DELETE 均先 preview，再以相同请求、未过期 token、新幂等键和 `If-Match` 确认。非法或同状态的新请求返回 409；同幂等键精确重放仍按公共幂等规则返回原结果。
6. restore 仅适用于软删除的 ARCHIVED 记录，保持现有“原因 + `If-Match` + 幂等”接口，不新增 restore-preview；成功后清除 `deleted_at`、状态固定回到 `DRAFT`、版本加一。重新启用必须另走 ACTIVATE preview/confirm。
7. 默认列表排除软删除记录；显式 `status=ARCHIVED` 仅返回软删除归档记录；按 ID 详情允许读取 ARCHIVED 以支持恢复。
8. 品牌/分类存在 ACTIVE 商品时，DEACTIVATE 和 SOFT_DELETE 的 preview 仍返回 200 并列出影响，confirm 以 `ACTIVE_PRODUCT_DEPENDENCY` 422 阻断。软删除业务键全局保留，再次创建返回 `SOFT_DELETED_KEY_RESERVED` 409。
9. `UploadIntentRequest` 增加必填 `sha256`，格式为 64 位小写十六进制；七类 purpose 统一仅接受 `image/jpeg`、`image/png`，单文件最大 5 MiB。
10. complete 请求的 SHA-256 和 size 必须同时匹配 intent 与服务端读取对象后的 MIME、魔数、大小和 SHA-256 实测值，不一致返回 `FILE_CONTENT_MISMATCH` 422。
11. 上传签名有效 15 分钟，私有下载签名有效 5 分钟；PENDING/staging 满 24 小时才进入清理候选。对象键固定使用 staging/public/private 分区且不包含原文件名。
12. bucket 默认私有，只允许 `public/*` 匿名 GET；售后、提现和推广 QR 始终使用 `private/*`，不得由客户端或 purpose 旁路改变可见性。
13. 不新增 `completed_at` 或 `updated_at` 数据库列。complete 成功事实由 `status=READY`、最终对象 key、服务端实测内容、审计与幂等记录表达；首次 `completed_at` 只保存在闭合 `FILE_UPLOAD_COMPLETE` 响应及其幂等正文，同键同请求精确重放，新键重复 complete 返回 409。
14. 上传意图和 lifecycle preview 使用 `HASH_ONLY`，不得把签名 URL、请求头或 preview token 保存到幂等响应正文；下载签名 GET 的幂等语义以 CH-008 勘误为准，不创建幂等记录。

- **申请日期**：2026-08-25。
- **申请来源**：技术限制。B5.0 审计发现现有 Banner DTO 可绕过软删除/恢复、`low_stock` 无存储口径、库存 HR-07 preview 未在公共仓储注册，且库存边界/流水响应和原型存在漂移。
- **变更类型**：修改需求与接口契约，不新增页面、path、operation 或数据库模型。
- **影响程度**：中等，影响 ADM-07/08、9 个现有 operation、生成 contracts、幂等/preview 公共内核和静态原型。
- **审批状态**：用户已明确批准，产品负责人和技术负责人批准立即执行。
- **执行边界**：先完成 B5.0 产品、OpenAPI、生成 contracts、公共幂等/preview 契约、原型和冻结数据库门禁；B5.0 验收暂停前不得实施 B5.1 repository、controller、service 或工程前端。

### 16.2 推荐的最小方案

1. Banner 创建固定 DRAFT；资料更新不接收状态；同一 PATCH operation 以独立闭合 action 分支处理 ACTIVATE/DEACTIVATE。DELETE 是唯一软归档入口，ACTIVE 不得直接归档，restore 固定回 DRAFT。
2. Banner 默认排除 ARCHIVED，稳定排序 `sort_order ASC,id ASC`；公开窗口为 `(starts_at IS NULL OR starts_at <= now) AND (ends_at IS NULL OR now < ends_at)`，起止均非空时 `ends_at > starts_at`。启用、ACTIVE 资料更新与公开投影重查 READY/PUBLIC/BANNER 文件和 ACTIVE PRODUCT/CATEGORY target；HTTPS URL 最长 500 字符且须命中服务端 origin allowlist。
3. Banner 写响应新增代码级闭合 `BANNER_RESOURCE_RESPONSE` 精确重放策略，不新增数据库列。
4. 无迁移删除 `low_stock`、原型预警值、售后占用和独立备注；库存只展示/复算 `physical/locked/available=physical-locked/active_reservation`。
5. `physical_delta` 固定为非零 int32；归档 SKU 只读。preview 使用 `HASH_ONLY` 并注册 `INVENTORY.ADJUST/INVENTORY`，越过 locked 下界仍返回 200 warning，confirm 以 `STOCK_INSUFFICIENT` 422 阻断且不消费 preview；超 PostgreSQL INTEGER 使用 `INVENTORY_QUANTITY_OUT_OF_RANGE` 422。
6. confirm 使用 `COMMAND_RESPONSE`，固定 `resource_type=inventory/resource_id=sku_id/status=SUCCEEDED/version=new balance version`；余额、version、单条 MANUAL 流水、preview、审计、幂等和 outbox 在同一 Serializable 事务完成。
7. 流水响应使用闭合 enum，稳定排序 `occurred_at DESC,id DESC`；B4 零余额不回填 INITIAL 流水。
8. 产品/API 升级至 `v2.4.3 / 2.4.3-ch012`；实测保持 172 paths / 196 operations / 196 unique operationId，并得到 312 schemas / 692 schema refs / 2,578 local refs / 0 dangling refs。Prisma、`0001_initial` 和冻结哈希逐字节不变。

完整状态矩阵、批次、锁序、验收与回退方案见 `../05-开发管理/B5-Banner与库存.md`。

### 16.3 实施与暂停边界

- B5.0 可以修改：产品/技术说明、OpenAPI、生成 contracts、公共幂等与 preview 白名单、静态原型及专项检查。
- B5.0 不可以创建：Banner/Inventory 业务 repository、controller、service、工程路由或导航；这些只属于后续 B5.1-B5.3。
- B5.0 必须证明：统计与闭合 schema 通过、原型回归通过、Prisma/首迁移逐字节不变、migration diff=0，且 `P0=0/P1=0` 后暂停。
- **实施结果**：B5.0 已完成上述允许项并通过本地契约、生成漂移、公共内核、原型、冻结数据库及独立复核门禁；随后经用户逐批明确继续，B5.1 已交付 Banner repository/API，B5.2 已交付 Inventory repository/API、HR-07 preview-confirm 与流水，B5.3 已交付 ADM-07/08 后台与五视口验收，均在 `P0=0/P1=0` 后暂停。B5.4 已完成真实纵向链路、全量回归和同一实现 SHA 的远端双绿，B5 development `GO`；消费者 `/store/home` 仍未实施。

## 十八、CH-014 B6 消费者匿名商城目录契约

### 18.1 变更申请与决策

- **申请日期**：2026-08-25。
- **申请来源**：技术限制。现有公开目录契约将 `is_salable` 固定为 true，未表达零库存可浏览；搜索、综合排序、首页分区降级和匿名限流也未闭合。
- **变更类型**：修改需求与 API 契约，不新增 path、operation、页面、FR、AC、US、HR 或数据库模型。
- **影响程度**：中等；影响 5 个现有 Store 公开 GET、MP-01 至 MP-06、生成 contracts、静态原型和 CI 契约门禁。
- **审批状态**：用户已明确批准，产品负责人和技术负责人批准立即执行。
- **基线**：产品/PRD `v2.4.4 / CH-014`，OpenAPI `2.4.4-ch014`。

### 18.2 已批准契约

1. 仅返回 ACTIVE 商品、品牌、分类和 ACTIVE SKU；所有 ACTIVE SKU 都公开，`StoreSkuView.is_salable` 为布尔值，零库存返回 false。商品摘要同步返回 `is_salable`，全部 SKU 售罄时商品仍可浏览。
2. 新增默认 `COMPREHENSIVE`，固定为 `is_hot DESC,is_new DESC,sales_count DESC,published_at DESC NULLS LAST,product_id ASC`；HOT 按全生命周期净销量，NEWEST 按首次发布时间，价格排序使用 ACTIVE SKU 最低零售价，并以 product ID 打破平局。
3. 搜索只对 trim 后的商品名执行大小写不敏感匹配，长度 1-200；品牌/分类公开接口无 pagination，返回全部 ACTIVE 记录并按 `sort_order,id` 排序。
4. 首页返回 Banner/分类/热销/新品四个数组和各自 `READY|UNAVAILABLE` 分区状态；单区失败返回空数组且总体 200，四区全失败才返回 500。上限分别为 10/8/4/4，无效 PRODUCT Banner target 自动排除。
5. 匿名目录使用 Redis 固定窗口限流，每个 HMAC 来源 IP 每 60 秒 120 次；不保存原始 IP，超限返回 429 和准确 `Retry-After`，Redis 异常不得绕过限流。
6. 仅允许 READY/PUBLIC 且 purpose 正确的图片进入公开投影；不返回管理状态、version、file ID、实物/锁定库存或其他后台字段。
7. 契约统计保持 172 paths / 196 operations / 196 unique operationId / 312 schemas。Prisma、`0001_initial` 与冻结文件逐字节不变，本批已实测 `pnpm db:check-frozen`、`pnpm prisma:validate` 和 `pnpm db:diff` 通过，diff 为 `No difference detected`。
