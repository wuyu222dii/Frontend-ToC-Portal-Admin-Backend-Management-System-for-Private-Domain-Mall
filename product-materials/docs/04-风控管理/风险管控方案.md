# 洗化产品私域商城风险管控方案

## 1. 管理基线

| 项目 | 口径 |
|---|---|
| 文档版本 | v1.1 / CH-006 |
| 更新日期 | 2026-08-13 |
| 适用阶段 | 设计冻结、研发准入、迭代开发与生产上线准备 |
| 风险范围 | 技术、质量、需求、进度、资源、外部、合规与运营 |
| 评估方法 | 概率（1-3）× 影响（1-3） |
| 应对策略 | 按风险采用规避、缓解、转移或接受 |
| 复核频率 | 每个研发迭代评审；高风险触发信号出现时立即复核 |

本方案区分“研发准入”和“生产上线”两个门禁。研发准入只允许在 Mock Provider、开发或测试数据库和脱敏数据条件下实施；真实微信支付、生产 Supabase、银行卡付款和佣金税务不因研发准入自动获批。

## 2. 评级规则

- 概率：低 1（小于 20%）、中 2（20%-50%）、高 3（大于 50%）。
- 影响：低 1（局部且可快速恢复）、中 2（影响迭代或部分业务）、高 3（资金、库存、隐私、合规或主链路失真）。
- 分数：1-2 为低，3-4 为中，6-9 为高。
- 高风险未落实预防控制和验证证据时，不得进入对应开发或生产阶段。

## 4. 阶段门禁

### 4.1 研发准入

CH-005 的历史研发准入证据保留，CH-006 曾重新打开 B3 契约门禁；以下 B3.0 条件均已通过。扩展后的 CH-007 调整整个 B3 的远端证据时序，未取消 B2/B3 云端证据或上线标准：

1. v2.4.1/CH-006 的产品规则、ADM-05/06 原型、API/OpenAPI 和生成 contracts 一致；页面/FR/AC/operation 数不变。
2. `pnpm contracts:check` 校验 172 paths、196 operations、196 unique operationId、306 schemas、0 dangling refs；Redocly 和生成漂移通过。
3. Product/SKU 的闭合生命周期 DTO 拒绝 ACTIVATE；品牌/分类排序、DRAFT 创建、三动作状态机、ARCHIVED 查询和 restore-to-DRAFT 可机器校验。
4. Prisma Schema 和 `0001_initial` 逐字节不变，Prisma validate、冻结检查和 migration diff 为零。
5. CH-006 原型回归覆盖排序、固定草稿、启用预览、归档筛选、恢复草稿、409/422、重复提交和文件校验；所有 P1 阻塞项关闭。
6. B3.0、B3.1 和 B3.2 的本地/一次性环境验收已通过并暂停，B3.3 未开始。
7. B3.3 本地验收后必须另行执行覆盖 B3 repository 的 Supabase development rollback-only smoke；它与 B2 前置证据相互独立，无远端无残留证据不得标记 B3 整体完成。

研发准入不包含真实资金、生产数据或真实银行卡操作。研发环境必须使用 Mock Provider、测试账号和脱敏数据。

下列为 CH-005 历史准入证据；这些证据本身不替代上方已独立完成的 CH-006 门禁：

- 三端原型：78 个响应式渲染、21/9/22 页面契约、14 条小程序流程和 16 条后台/代理流程全部通过，敏感明文、破图、横向溢出和 `pageerror` 为 0。
- API：OpenAPI 172 paths / 196 operations / 305 schemas，与文本接口 196/196 覆盖；Redocly recommended lint 零警告。
- 数据库：Prisma 7.9.1 `format/validate/generate` 通过；PostgreSQL 18.3 空库回放得到 76 表、59 枚举、17 条件唯一索引、165 个 `CHECK`、76 张 RLS 表、76 个 policy 和 24 个用户触发器（45 个事件绑定）。
- 迁移权限：`mall_migrator` 拥有 76 张应用表、59 个枚举和 15 个迁移函数，可执行后续 `ALTER TABLE`；`mall_runtime` 拥有 0 张表，仅可删除收藏、购物车项、客户手机号授权和客户地址四类非交易数据，其他业务表无 `DELETE`。
- 边界 DML：全部通过，覆盖固定 30 分钟支付窗口、验货人/时间/原因完整性、证据封存与追加拒绝、退货验货精确覆盖/数量等式/单次处置、0% 佣金和最小权限。
- Prisma 对最终落库结构执行 `migrate diff` 返回 `No difference detected`；独立复审未发现 P0/P1 准入阻断。

### 4.2 生产上线

下列事项属于生产门禁，即使研发准入通过也不得跳过：

1. 正式微信小程序主体、登录、支付和退款凭据到位并完成签名/回调联调。
2. Supabase 项目区域、套餐、备份、PITR、恢复目标和数据驻留通过评审。
3. 最小权限角色、关闭 Data API、RLS/default grants、密钥轮换和监控告警完成实库验证。
4. 隐私政策、手机号授权、账号删除、银行卡处理、代理合同、佣金税务和付款 SOP 获得专业审批。
5. 容量、故障恢复、对账、退款失败、负余额和提现异常完成演练，并具备回滚方案。

## 5. 监控机制

| 节点 | 动作 | 输出 |
|---|---|---|
| 每日开发 | 监控 CI、契约漂移、迁移失败、资金/库存测试失败和安全扫描 | 缺陷或风险更新 |
| 每次合并 | 对订单、库存、支付、退款、佣金、钱包和认证变更进行领域审查 | 评审记录与测试证据 |
| 每个迭代 | 复核风险概率、影响、责任人和剩余风险，检查范围变更 | 更新后的风险登记表 |
| 联调前 | 复核第三方官方契约、凭据、回调白名单和 Mock/真实环境隔离 | 联调准入清单 |
| 上线前 | 执行生产门禁、恢复演练、安全与合规签字 | Go/No-Go 决策记录 |

## 6. 事件升级

- 任何资金、库存、隐私或银行卡明文异常立即暂停对应写路径并升级为 P0。
- 同一幂等键产生不同业务结果、订单状态轴无法解释或钱包不平，应停止发布并先完成对账。
- 高风险项分数升至 6 以上且无有效控制时，自动撤销对应阶段准入。
- 新需求若改变角色、归因、价格、库存、资金或履约边界，必须先创建新的需求变更记录。

## 7. 当前状态

CH-006/B3.0、B3.1 与 B3.2 本地/一次性环境门禁均已通过并暂停，安全审计 P0/P1=0；B3.3 未开始。B2 Supabase development rollback-only、未来覆盖 B3 repository 的独立 rollback-only、head SHA/审批人与 GitHub 受保护成功运行记录仍按扩展后的 CH-007 延期，缺少这些远端证据时 B3 整体保持 NO-GO。目标 Supabase staging、真实微信支付、完整银行卡付款、恢复演练和外部合规未完成前，生产门禁保持关闭。
