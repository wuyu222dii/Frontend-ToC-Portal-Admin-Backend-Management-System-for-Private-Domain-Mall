## 3. CH-022 冻结决策

CH-022 来源为技术限制与阶段路线，类型为修改需求，中等影响，经产品负责人和技术负责人批准立即执行。

### 3.1 版本与契约目标

- 产品/PRD 基线升级为 `v2.4.8 / CH-022`，OpenAPI 升级为 `2.4.8-ch022`。
- 本地解析实测为 `173 paths / 198 operations / 198 unique operationId / 326 schemas / 705 schema refs / 2,678 local refs / 0 dangling refs`。
- 支付 Provider 由服务端配置决定，消费者不得在请求中选择 Provider。
- 所有 `order_id`、`payment_intent_id` 和 `refund_id` 路径参数统一使用 ULID。
- Mock 调试结果仅接受 `SUCCEEDED | FAILED | CANCELLED`；交易号、事件号和是否迟到均由服务端判定。
- 写操作使用 `HASH_ONLY`，同键重放重新鉴权并返回当前投影；支付 capability、Provider payload、签名和完整响应不得进入幂等缓存。消费者 capability 只在支付发起响应的内存态使用，ADM-10 列表和 reconcile 的 200/202 响应均不得携带 capability。

### 3.2 支付与结果状态

- 每单最多一个活动支付意图；本地先写稳定 `intent_no + CREATING`，事务外调用 Provider，再以短事务收敛。
- Provider 结果闭合为 `OPEN | SUCCEEDED | FAILED | CANCELLED | CLOSED | NOT_FOUND | UNKNOWN`；UNKNOWN 必须 fail closed。
- 支付成功原子完成 attempt、订单已支付/待发货、预占消耗、实物与锁定库存扣减、唯一 `ORDER_PAID_DEDUCT` 流水、最终归因、逐订单项佣金快照、审计和 Outbox。
- 支付前候选代理仍为 ACTIVE 才冻结 AGENT；否则降级 DIRECT，不阻断支付。
- 失败或取消保留待付款订单和有效预占，允许以新幂等键重新支付；处理中禁止重复创建意图。

### 3.3 关单、对账与迟到支付

- 有 `CREATING/OPEN` 意图的取消或超时先写 `CLOSE_PENDING`，事务外 query/close；明确不可支付后才关单并释放库存。消费者取消若尚待 Provider 确认，返回 `202` 和 `CLOSE_PENDING` 当前投影。
- Provider 状态未知时返回当前 pending 投影，保留库存锁定；不得伪造失败或提前释放。
- 关闭后到达的支付成功只写 `SUCCEEDED_LATE` 和唯一全额 `LATE_PAYMENT` refund；订单保持关闭，不恢复库存、履约、归因或佣金。
- 退款尝试初始状态固定为 `INITIATED`，之后才进入 `PROCESSING | SUCCEEDED | FAILED`；自动退款失败或未知进入 `MANUAL_REQUIRED`。
- ADM-10 最小待办类型闭合为 `PAYMENT_INTENT | PAYMENT_SETTLEMENT | LATE_PAYMENT_REFUND`；200 表示已收敛，202 表示仍待 Provider 确认。后台响应不得携带 capability，也不得直接修改支付、订单、库存、退款或佣金状态。
- TR-020 在 B10.3 使用稳定候选游标和页内问题上限收口。

### 3.4 错误、缓存与环境

- 新增闭合错误：`ORDER_PAYMENT_EXPIRED`、`PAYMENT_NOT_ALLOWED`、`PAYMENT_RESULT_CONFLICT`（409），以及 `PAYMENT_PROVIDER_UNAVAILABLE`、`PAYMENT_CONFIGURATION_UNAVAILABLE`（503）。
- CUSTOMER 支付接口继续使用 CUSTOMER+来源 IP 的 120/60 fail-closed 限流，并对成功和 JSON 错误设置 `Cache-Control: no-store, private`、`Pragma: no-cache`。
- development/test 固定使用 Mock Provider；production 配置为 Mock 时必须拒绝启动。
- 微信支付/退款回调仍保留在线协议中，但 B10 development 不注册真实路由，也不要求微信密钥、证书、raw-body 验签或 Provider ACK。

### 3.5 B10.1 实施决策

- Payment Provider port 闭合为 `create/query/close/refund`；所有 Provider 网络或 Redis 调用必须在数据库事务外执行。
- Mock Provider 外部状态在 Redis 保留 7 天，key 使用支付域 HMAC 摘要，不保存原始客户、订单、支付意图或 IP 标识。
- 新建 `CREATING` payment intent 的 `next_reconcile_at` 固定为数据库当前时间后 60 秒，支持 Provider 响应丢失后按稳定 `intent_no` 恢复。
- 任何既有 `CREATING` intent 一律先调用 `query(intent_no)`；只有 Provider 明确返回 `NOT_FOUND` 才允许以同一 `intent_no` 调用 `create`，不得在响应丢失或重试时直接 create。
- Provider 返回 `OPEN` 时，最终短事务必须原子写 intent `OPEN`、订单 `payment_status=PROCESSING` 并递增订单版本；明确 `FAILED/CANCELLED/CLOSED` 终态时原子恢复订单 `payment_status=UNPAID`。完整幂等重放先于 `If-Match`，新命令携带陈旧版本返回 409。
- 超时、Redis 故障或 Provider `UNKNOWN` 统一 fail closed，不完成不安全的幂等事实、不伪造成功或失败，也不进入 B10.2 结算。
- Mock result 路由只在 `development + STORE_PAYMENT_PROVIDER=MOCK` 时注册；验证后仅写 Callback Inbox 并返回 202，不直接更新 intent/订单、消耗预占、扣减库存、冻结归因或佣金。

## 4. 数据库与迁移边界

- 两份 Prisma schema 以及既有两份 `0001_initial`、两份 `0002_b9_inventory_fact_indexes` 必须逐字节不变。
- 新增事务型 `0003_b10_payment_fact_indexes`，只增加：
  - `payment_attempt(payment_intent_id)` 在 `status IN ('SUCCEEDED','SUCCEEDED_LATE')` 时的条件唯一索引；
  - `refund(order_id)` 在 `origin_type='LATE_PAYMENT'` 时的条件唯一索引。
- 建索引前必须检查历史重复事实，发现重复则整个迁移失败；不增表、列、枚举、RLS 或权限能力。
- 0001→0002→0003 空库回放、0002→0003 升级、冻结哈希、权限/所有权、原生指纹、Prisma validate 和 `migration diff=0` 均属于 B10.0 门禁。
- 0003 一旦部署即作为加法索引保留；代码回退不得执行数据库降级。
