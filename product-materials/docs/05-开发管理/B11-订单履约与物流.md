## 4. 履约状态机

### 4.1 发货前置与唯一包裹

B10 支付成功后的合法起点固定为：

```text
order_status=PENDING_SHIPMENT
payment_status=PAID
payment_resolution=NORMAL
fulfillment_status=READY_TO_SHIP
commission_position=EXPECTED（适用时）
```

发货仅在上述状态且不存在活动售后时允许。活动售后精确集合为：`PENDING_REVIEW | REFUNDING | WAITING_RETURN | WAITING_RECEIPT | RETURN_EXCEPTION | REFUNDING_AFTER_RETURN | REFUND_FAILED`；`REJECTED | REJECTED_AFTER_RETURN | COMPLETED | CANCELLED` 不属于活动集合。

请求必须包含非空 `carrier_code`、`carrier_name`、`tracking_no` 和全部剩余可发项目。每个订单项的合法数量固定为：

```text
quantity - pre_shipment_refunded_qty - shipped_qty
```

items 缺失、重复、多出、跨订单或数量不等时整笔返回 `SHIPMENT_ITEMS_MISMATCH`，不落包裹空壳。合法事务原子创建 `shipment=SHIPPED`、全部 `shipment_item`，更新订单项 `shipped_qty`，并推进：

```text
PENDING_SHIPMENT / READY_TO_SHIP
  -> SHIPPING / SHIPPED
```

`shipment.order_id UNIQUE` 保证一个订单整个生命周期最多一个包裹。创建后不提供取消、删除或替换；承运信息纠错只能追加事实。

### 4.2 人工物流

`STATUS` 与 `TRACKING_CORRECTION` 为互斥 DTO：

- `STATUS` 必须且只能携带状态，严格按 `SHIPPED -> IN_TRANSIT -> DELIVERED` 单向推进，并同步订单履约轴。
- `TRACKING_CORRECTION` 必须提交完整新承运商/运单号和必填原因；它只更新当前承运信息并追加不可变纠错事件，不改变物流状态，不覆盖历史。
- 客户端不得提交 `event_key`；服务端从已鉴权幂等事实派生稳定 key，`(shipment_id,event_key)` 保证重放只产生一个事件。
- 时间线固定按 `occurred_at ASC,event_id ASC`，相同发生时间也不得抖动。

### 4.3 确认收货与兜底完成

消费者确认和 Admin 兜底完成只允许：

- `payment_status=PAID`、`payment_resolution=NORMAL`；
- `order_status=SHIPPING`；
- 唯一包裹为 `SHIPPED | IN_TRANSIT | DELIVERED`；
- 不存在活动售后或未解决支付异常。

若包裹尚未 `DELIVERED`，完成事务直接封存 `shipment/fulfillment=DELIVERED`，但不制造缺失的人工 `IN_TRANSIT` 或 `DELIVERED` 事件。随后分别写：

```text
CUSTOMER: order_status=COMPLETED, completion_reason=CUSTOMER_CONFIRMED
ADMIN:    order_status=COMPLETED, completion_reason=ADMIN_FORCED
```

同一事务还必须：

1. 写入数据库当前时间 `completed_at`。
2. 锁定唯一当前 `PUBLISHED BusinessRuleVersion` 并写 `business_rule_version_id`。
3. 依据该规则计算并写 `aftersale_expires_at`。
4. 将每个仍为 `EXPECTED` 的佣金 position 的当前 `expected_remaining` 精确一次结转为 `AVAILABLE`。
5. 追加 `AVAILABLE_CREDIT`，原子更新代理钱包，并写最小审计与 Outbox。

`NONE`、DIRECT、0% 或已减少到零的 position 不制造零金额正向流水。重复、并发或消费者/Admin 竞争只能产生一次完成与一次佣金入账。发货后全额退款形成 `COMPLETED/FULL_REFUND_AFTER_SHIPMENT` 是既有售后状态机的历史兼容路径，不属于 B11 普通售后实现。

## 5. 数据库与事务边界

### 5.1 零迁移

B11 不新增数据库迁移。两份 Prisma schema、两份 `0001_initial` 与既有 `0002_b9_inventory_fact_indexes`、`0003_b10_payment_fact_indexes`、`0004_b10_commission_position_trigger_fix` 必须逐字节不变。

现有模型已经提供：

- `SalesOrder` 的订单、支付、退款进度、退款处理、履约独立状态轴，以及完成原因、业务规则版本、售后期限、完成时间和版本。
- `OrderItem` 的数量、发货前退款量、售后占用量、已发量和边界检查。
- `Shipment.order_id UNIQUE`、包裹状态/版本/送达时间一致性，以及 `ShipmentItem(shipment_id,order_item_id) UNIQUE`。
- `LogisticsEvent(shipment_id,event_key) UNIQUE`、时间排序索引和 STATUS/纠错形状检查。
- 每订单项唯一佣金快照、每快照唯一 position、不可变 ledger 幂等事实和每代理唯一钱包。

B11.0 已通过冻结数据库逐字节检查、Prisma validate 和 remote `migration diff=0`。数据库没有直接强制跨表订单/履约/包裹状态机、包裹项必须属于同一订单或请求精确覆盖集合；这些规则必须由应用层在 Serializable 事务内锁定重验，不能只依赖唯一约束。

### 5.2 固定锁序

发货命令使用：

```text
idempotency -> admin actor -> order -> order_items ASC
-> active aftersales ASC -> existing/insert shipment -> audit/outbox
```

完成命令使用：

```text
idempotency -> actor/customer -> order -> order_items ASC
-> active refunds/aftersales ASC -> shipment
-> current PUBLISHED business rule
-> commission snapshots/positions ASC -> agent wallets ASC
-> commission ledgers -> audit/outbox
```

候选 ID 只可无锁定位，锁内必须重新校验主体、版本、状态、集合与金额。完整幂等重放先于 `If-Match`，但必须重新鉴权并返回当前投影；新命令的陈旧版本返回 409。所有唯一冲突都必须重读赢家事实并按幂等/状态语义收敛，不得映射为 500。
