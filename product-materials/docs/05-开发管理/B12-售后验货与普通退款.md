### 4.2 Store 售后契约

| 方法 | 路径 | CH-026 约束 |
|---|---|---|
| `POST` | `/store/aftersales` | 同一 operation 使用闭合 `PREVIEW -> CONFIRM` 两阶段命令；只允许 `REFUND_ONLY | RETURN_REFUND`，订单、订单项、文件均为 ULID；PREVIEW 返回服务端试算和短时凭证但不占用，CONFIRM 重验后计价并占用；两阶段使用不同幂等键和 `HASH_ONLY` |
| `GET` | `/store/aftersales` | 本人隔离、稳定分页、闭合状态/动作与退款进度 |
| `GET` | `/store/aftersales/{aftersale_id}` | 本人详情、冻结地址/物流/验货/退款尝试和稳定时间线；跨客户统一 404 |
| `POST` | `/store/aftersales/{aftersale_id}/cancel` | 仅 `PENDING_REVIEW` 或未提交退货物流的 `WAITING_RETURN`；`Idempotency-Key + If-Match + HASH_ONLY` |
| `POST` | `/store/aftersales/{aftersale_id}/return-shipment` | 仅本人 `WAITING_RETURN`；`carrier_code` 为 1-40 位 ASCII 字母/数字及 `._-`，`carrier_name` 为 1-80 字符且无控制字符，`tracking_no` 为 1-120 位 ASCII 字母/数字及 `._/-`；`Idempotency-Key + If-Match + HASH_ONLY` |

五个 Store 接口统一使用 CUSTOMER 鉴权和已有 CUSTOMER+来源 IP `120/60` Redis 固定窗口限流；Redis 只保存域隔离 HMAC 摘要，故障时 fail-closed。全部成功和 JSON 错误响应都必须返回 `Cache-Control: no-store, private` 与 `Pragma: no-cache`。

`CreateAftersaleRequest` 是以 `action` 判别的闭合联合。`PREVIEW` 和 `CONFIRM` 携带完全相同的业务字段；`CONFIRM` 额外必填 `preview_token` 与 64 位小写十六进制 `confirmation_hash`。`items` 固定为 1-100 个不重复订单项，数量为正整数且不超过剩余可退数量；`evidence_file_ids` 最多 9 个不重复 ULID，服务端必须校验 READY/PRIVATE、purpose、当前客户和业务引用边界。`reason_code=OTHER` 在生成类型和运行时都强制非空 `reason_text`，客户端不得提交退款金额、库存处置、佣金影响或内部状态。

PREVIEW 使用 Repeatable Read 试算并返回逐项申请数量、剩余可退数量/金额、服务端分配金额、总申请金额和闭合 blockers：`ORDER_NOT_ELIGIBLE | ITEM_UNAVAILABLE | AFTERSALE_QUOTA_EXCEEDED | EVIDENCE_UNAVAILABLE`。`can_submit=false` 仍返回 200，但 token/hash/expiry 必须全部为 `null`；可提交时使用现有幂等密钥环经 HKDF 域 `qingxu:store-aftersale-preview:v1` 派生密钥，签发 5 分钟无状态 HMAC，绑定 CUSTOMER、session、规范请求、订单/订单项版本、退款与售后占用、证据事实、服务端金额和 expiry。CONFIRM 必须使用不同于 PREVIEW 的新幂等键，并在 Serializable 事务内重验全部绑定事实；过期、不匹配或事实漂移分别返回 `AFTERSALE_PREVIEW_EXPIRED | AFTERSALE_PREVIEW_MISMATCH | AFTERSALE_REQUOTE_REQUIRED` 409。消费者 `available_actions` 不包含 `RETRY_REFUND`，退款失败只可查看进度，由总部受控重试。

本人售后列表固定按 `created_at DESC,aftersale_id DESC` 分页。每项必须返回闭合 `available_actions`、`refund_progress_status=NONE|PARTIAL|FULL` 和 `refund_processing_status=IDLE|REFUNDING|FAILED`，客户端不得从售后主状态自行合成动作或退款结论。

订单列表和详情同步解除旧 B9 的“售后固定为空”限制。`APPLY_AFTERSALE` 的闭合矩阵为：`payment_status=PAID`、`payment_resolution=NORMAL`，订单为 `PENDING_SHIPMENT|SHIPPING` 时允许 `aftersale_expires_at=null`，订单为 `COMPLETED` 时必须具有非空期限且数据库当前时间不晚于该期限，`CLOSED` 永不允许；同时至少一个订单项的剩余可退数量和金额都大于 0。活动售后只通过逐项占用减少剩余额度，不得在仍有其他可退项时全局隐藏动作。详情 `aftersales` 返回本人关联售后摘要，`refund_attempts` 可返回普通退款和金额补偿的安全尝试投影。客户端不得按状态、时间或数量自行推导申请资格，也不得看到 Provider 原文或 Admin 专属动作。

Admin 写操作使用 ULID、`Idempotency-Key`、对已有资源使用 `If-Match`、`HASH_ONLY`和最小审计。高风险 preview 只存 token 哈希并绑定 actor、session、action、target、规范请求与资源版本；不缓存预览正文、退款 Provider 能力或退货地址明文。409 后必须刷新并重新预览，不得自动覆盖或复用旧 token。

### 4.4 纯金额补偿

`POST /admin/orders/{order_id}/manual-compensations/preview` 和 `POST /admin/orders/{order_id}/manual-compensations` 继续使用 HR-09 preview-confirm。请求必须指向单一订单项，由服务端检查：

```text
amount <= line_paid_amount - refunded_amount - aftersale_reserved_amount
```

确认只增加金额占用，不改变数量占用、验货或回库事实，并返回稳定 `refund_id/refund_no` 与 `origin_type=MANUAL_COMPENSATION`。成功退款后才更新净退款额和佣金；Provider 失败保留占用并进入统一 `/admin/refunds/{refund_id}/retry-preview -> retry` 受控重试，不允许另建补偿单绕过。迟到支付退款不进入该通用重试，继续只走 ADM-10 对账。

### 4.5 闭合错误与安全

CH-026 新增/固化 422：

- `AFTERSALE_QUOTA_EXCEEDED`：请求数量或服务端计算金额超过订单项剩余可退范围。
- `RETURN_ADDRESS_NOT_CONFIGURED`：`RETURN_REFUND` 初审时不存在唯一当前 PUBLISHED 总部退货地址。

CH-026 同时闭合 Store 售后预览 409：`AFTERSALE_PREVIEW_EXPIRED`、`AFTERSALE_PREVIEW_MISMATCH`、`AFTERSALE_REQUOTE_REQUIRED`。Admin 普通退款和金额补偿的额度失败必须在响应 schema 中将 `AFTERSALE_QUOTA_EXCEEDED` 固化为真实 wire code，不得只写在描述中仍引用任意字符串错误。

版本冲突、非法状态、preview 过期/篡改/重放、退款结果冲突和 Provider 不可用继续使用已冻结通用错误；不将内部异常、Provider payload、地址明文或证据存储键暴露给客户端。

## 5. 售后、验货与退款状态机

### 5.1 申请和占用

创建售后必须在 Serializable 事务内按订单项锁定后重算：

```text
remaining_qty = quantity - refunded_qty - aftersale_reserved_qty
remaining_amount = line_paid_amount - refunded_amount - aftersale_reserved_amount
```

服务端按成交快照为请求数量分配金额，尾笔退清直接使用剩余可退金额消除舍入尾差。同一订单项的并发申请只能在剩余数量/金额内成功，不得依赖前端顺序。成功创建后进入 `PENDING_REVIEW`，任一活动占用继续阻断 B11 整单发货。

### 5.2 初审、退货和验货

```text
PENDING_REVIEW
  -> REJECTED
  -> REFUNDING                         (REFUND_ONLY 通过)
  -> WAITING_RETURN                    (RETURN_REFUND 通过并冻结地址)

WAITING_RETURN
  -> WAITING_RECEIPT                   (客户提交退货物流)
  -> CANCELLED                         (未提交物流时允许)

WAITING_RECEIPT
  -> REFUNDING_AFTER_RETURN            (PASS)
  -> RETURN_EXCEPTION                  (ABNORMAL)

RETURN_EXCEPTION
  -> REFUNDING_AFTER_RETURN            (CONTINUE_REFUND)
  -> REJECTED_AFTER_RETURN             (REJECT_AFTER_RETURN)
```

验货请求必须精确覆盖该售后全部项，且每个订单项恰好一次。逐项必须满足：

```text
approved_refund_qty + return_to_customer_qty = received_qty
approved_refund_qty = restock_qty + damaged_qty + scrap_qty
```

`PASS` 要求全量实收、全量批准且 `return_to_customer_qty=0`，可以封存空证据清单；少件、0 件或任何数量异常必须为 `ABNORMAL`，并封存至少一份合法证据。验货 `evidence_file_ids` 同样最多 9 个不重复 ULID。验货结果、逐项处置、处理人、时间和 canonical 证据清单提交后均不可追加、删除、换序、替换或改绑。

### 5.3 退款处理

售后或金额补偿经 preview-confirm 后创建唯一稳定 `refund`和第一条 `refund_attempt`。Provider 调用必须在数据库事务外执行；回传结果先保存到 Inbox，Worker 再以 Serializable 事务收敛业务事实。development/test 只使用 Mock Provider，真实微信退款 callback 不注册。

```text
REFUNDING | REFUNDING_AFTER_RETURN
  -> COMPLETED                         (Provider 明确成功)
  -> REFUND_FAILED                     (Provider 明确失败)

REFUND_FAILED
  -> REFUND_FAILED                     (重试失败，追加 attempt)
  -> COMPLETED                         (重试成功)
```

Provider 失败或未知不得更新成功退款数量/金额、不得回库、不得冲正佣金，且必须保留可退占用。重试使用新幂等键与新 preview，复用稳定 `refund_id/refund_no/provider_refund_id/items`，不得创建第二条 refund。

### 5.4 退款成功的原子收敛

退款成功事务必须精确一次：

1. 固化成功 attempt 与 refund，更新售后/补偿和订单项成功退款数量、金额及占用。
2. 重算 `refund_progress_status=NONE|PARTIAL|FULL` 和 `refund_processing_status=IDLE`；历史成功进度不得被后续失败回退。
3. 未发货数量按 SKU 写唯一 `REFUND_RESTOCK` 流水并增加实物库存；已发货退货只按验货冻结的 `restock_qty` 写 `RETURN_RESTOCK`，不根据退款金额或申请数量自动回库。
4. 按原订单项支付时佣金快照逐项计算冲正。完成前追加 `EXPECTED_REDUCED/EXPECTED_CANCELLED`；完成后保留原 `AVAILABLE/AVAILABLE_CREDIT` 并追加 `REFUND_DEBIT`。
5. 未发货全额退款收口为 `CLOSED/FULL_REFUND_BEFORE_SHIPMENT`且履约为 `CANCELLED`；已发货全额退款保留包裹/物流事实，收口为 `COMPLETED/FULL_REFUND_AFTER_SHIPMENT`。
6. 写入最小审计、Outbox 和幂等完成事实；不得在任何载体中保存 Provider payload、完整地址、客户标识或预览 token。

订单完成与退款成功并发时必须锁定相同订单项佣金快照/position：退款先提交则只结转减少后的剩余 EXPECTED；完成先提交则追加 `REFUND_DEBIT`。两种顺序必须得到相同净佣金，且不得重复流水或扩大负余额。

## 6. `0005_b12_aftersale_refund_guards`

### 6.1 迁移目标

`0005` 为事务型前向数据防护迁移，不新增表、列或枚举。两份 Prisma schema 的数据模型形状不变，两份 `0001_initial`与既有 `0002`至`0004` 必须逐字节不变；`prisma/migrations` 和产品材料镜像中的两份 `0005` 必须逐字节一致。

2. 增加部分唯一索引，保证每个 refund 同时最多一个 `INITIATED|PROCESSING` attempt，且整个生命周期最多一个 `SUCCEEDED` attempt。

## 7. 事务、Provider 与锁序

### 7.1 固定事务边界

- 查询/试算使用 Repeatable Read 快照批量读取订单、订单项、售后、退款、库存、佣金和文件，不使用 N+1 查询或应用内分页后过滤。
- 占用、释放、审核、验货、异常解决、退款创建/结果收敛和补偿确认使用 Serializable 与统一重试，所有状态、主体、版本、数量和金额在锁内重验。
- Provider `refund/query` 只在事务外执行。超时、网络断开、结果未知和 Redis 异常均 fail-closed，不得推定退款成功或发起第二条 refund。
- Inbox 消费、退款 attempt、库存流水、佣金流水、审计、Outbox 和幂等事实必须具备稳定业务键，Worker 在业务提交后、Inbox 标记完成前崩溃也只能重放收敛，不能重复回库、退款或冲正。

### 7.2 固定锁序

写命令统一使用：

```text
idempotency/preview -> actor/customer -> order -> order_items ASC
-> aftersales/aftersale_items ASC -> return shipment/inspection
-> refund/refund attempts -> SKU ASC -> inventory balances ASC
-> commission snapshots/positions ASC -> agent wallets ASC
-> audit/outbox
```

候选 ID 只可在无锁查询中定位，事务内必须重读并锁定。完整幂等重放先于 `If-Match` 检查，但每次重放都要重新鉴权并返回当前投影；无法安全重放时返回 409 并要求刷新。
