## 2. 已实现能力

### 2.1 受控 bootstrap

- 根命令为 `pnpm admin:bootstrap`。命令先构建共享包，保证全新检出安装依赖后可运行；CLI 使用 `mall_runtime` 和串行化事务，只创建一名 `SUPER_ADMIN` 密码主体及不可变审计。
- 登录名通过 `ADMIN_BOOTSTRAP_LOGIN_NAME` 提供，或由终端交互读取；密码默认通过不可回显 TTY 输入并二次确认，不接受命令行参数或明文 `ADMIN_BOOTSTRAP_PASSWORD` 环境变量。
- 自动化受控环境只能设置 `ADMIN_BOOTSTRAP_PASSWORD_FILE`。密码文件必须是当前有效用户拥有、硬链接计数为 1、权限不宽于 `0600` 的普通文件；CLI 以拒绝符号链接的单一文件描述符完成检查和读取，避免检查/读取竞态。内容必须是一行有效 UTF-8，可有一个结尾换行，大小不超过 4096 字节。
- 命令失败只输出固定消息，不输出登录名、密码、连接串、密钥、数据库错误或堆栈。成功仅输出新账户 ULID；密码只以 Argon2id 哈希持久化。

安全示例：

```bash
umask 077
export ADMIN_BOOTSTRAP_LOGIN_NAME='admin.operator'
export ADMIN_BOOTSTRAP_PASSWORD_FILE='/run/secrets/qingxu-admin-bootstrap-password'
pnpm admin:bootstrap
unset ADMIN_BOOTSTRAP_LOGIN_NAME ADMIN_BOOTSTRAP_PASSWORD_FILE
```

不得把密码写入 `.env`、shell 参数、命令历史、CI 日志或仓库；执行后立即销毁临时密码文件。CLI 不自动加载 `.env`，所有 B0/B2 运行配置应由受控 Secret Store 注入进程环境。

### 2.2 密码、TOTP 与恢复码

- `POST /admin/auth/login` 对未知账号和错误密码返回相同错误，并执行等成本密码校验；密码成功只签发短时 pre-auth，不签业务 access token。
- 无 ACTIVE TOTP 时只允许 enroll/verify，现场验证成功后才原子激活因子、生成 10 个一次性恢复码并创建首个 MFA 会话。已有因子时创建 LOGIN challenge，TOTP 或恢复码成功后才创建业务会话。
- TOTP secret 使用 AES-256-GCM 信封加密并绑定 `totp_factor:<ULID>:secret_ciphertext` 认证上下文；新写入使用 FIELD current key，读取按 envelope `keyId` 从 current + 最多 3 把 previous key 中解析，支持无停机密钥轮换。
- 恢复码仅签发当次展示，数据库保存独立 AUTH secret-hash key 的 HMAC；使用即原子消费。恢复码轮换要求当前 MFA 会话和本人 TOTP。
- 登录、enroll、verify、recovery、refresh、密码修改及恢复码轮换等敏感响应统一 `Cache-Control: no-store, private` 和 `Pragma: no-cache`；幂等记录仅保存哈希，不缓存一次性凭据正文。

### 2.3 token、会话与锁定

- 签名 key 和认证 secret-hash key 各自使用 current + previous keyring，且与 FIELD、审计 IP、幂等密钥跨用途独立。access、pre-auth、refresh、challenge 和恢复码不可共享密钥用途。
- access token 默认 15 分钟，pre-auth 最长 5 分钟，会话默认 7 天；issuer、audience、TTL 和所有 keyring 在 API 启动及 CI 环境门禁中严格验证。
- pre-auth 携带签发时的 `account.version`，guard 与当前账户代际比对；TOTP enroll/login/recovery、恢复码轮换、密码修改和 logout-all 在账户 advisory lock 内再校验 expected version。密码修改和 logout-all 递增代际，过期 pre-auth 或并发敏感操作不得继续提交。
- refresh 每次使用都生成新 session material；旧 refresh 被不同幂等请求重放时撤销整个 session family。refresh 和 logout 都按 account-sessions → session-family 的固定顺序取 advisory lock，无论 rotate 或 logout 先提交，同一 family 都不得留下 ACTIVE 成员。密码修改和 logout-all 撤销其他会话；单会话 logout 立即失效。
- 已知账户的密码/TOTP/恢复码失败在 PostgreSQL 事务内计数，连续 5 次锁 15 分钟。未知账户入口另以 Redis 对规范化账号指纹连续 5 次失败锁 15 分钟，并对同一来源设置 20 次容量阈值，防止通过变换不存在账号绕开入口控制；Redis 不保存登录名或密码正文。
- 登录入口先在 Redis 原子申请 idempotency-key、subject 和 source 三维 owner lease，5 分钟内同一尝试或同 subject/source 的并发请求只有一个 owner，其余返回 409；释放时必须匹配 owner。失败落账再以 `SET NX` 的 24 小时 attempt marker 去重，相同 `Idempotency-Key` 只增加一次计数；PostgreSQL 幂等记录裁决同 key 同请求重放和同 key 异请求冲突。
- API 与 Worker 在需要数据库的 runtime 中同时要求 `REDIS_URL`。本机/CI 回环可用带至少 12 字符密码的 `redis://`，远程或 production 必须 `rediss://`；query、fragment、缺失 host/密码一律失败关闭。

## 3. 前端交付

总部后台只开放认证和账户安全所需页面：

| 页面/状态 | B2 行为 |
|---|---|
| ADM-01 登录 | 账号/密码、统一失败提示、锁定倒计时、加载与重复提交保护 |
| TOTP 登录 | 6 位验证码；可切换一次性恢复码；challenge 与 pre-auth 只保存在内存 |
| 首次 TOTP 绑定 | 展示 otpauth QR/手工密钥，验证后一次性展示恢复码 |
| 账户安全 | 修改密码、轮换恢复码、注销当前会话、注销全部会话 |
| 空工作台 | 仅表示认证成功；B3 及以后业务导航不提前展示 |

access、refresh、pre-auth、TOTP URI/secret 和恢复码均只保存在页面内存，不写入 localStorage、sessionStorage、IndexedDB、URL 或普通缓存。刷新或离页后一次性值不可恢复；需要时重新登录或重新发起受控流程。

## 5. 环境与密钥轮换

除 B0 配置外，API 需要：

```text
FIELD_PREVIOUS_ENCRYPTION_KEYS_JSON=[]
AUTH_SIGNING_KEY_BASE64=<32-byte canonical base64 from Secret Store>
AUTH_SIGNING_KEY_ID=<current signing key id>
AUTH_PREVIOUS_SIGNING_KEYS_JSON=[]
AUTH_SECRET_HASH_KEY_BASE64=<independent 32-byte canonical base64 from Secret Store>
AUTH_SECRET_HASH_KEY_ID=<current secret-hash key id>
AUTH_PREVIOUS_SECRET_HASH_KEYS_JSON=[]
AUTH_TOKEN_ISSUER=qingxu-api
AUTH_TOKEN_AUDIENCE=qingxu-admin-web
AUTH_ACCESS_TOKEN_TTL_SECONDS=900
AUTH_PREAUTH_TOKEN_TTL_SECONDS=300
AUTH_SESSION_TTL_SECONDS=604800
```

JSON keyring 条目只允许 `{"id":"previous-key-id","key_base64":"canonical-base64"}`，最多 3 把。轮换顺序必须是先部署“新 current + 旧 current 放 previous”，确认旧 token/密文和哈希保留期结束并完成重加密/会话自然过期后，再删除旧钥。禁止跨 FIELD、AUTH signing、AUTH secret hash、audit 和 idempotency 复用字节相同的密钥。

1. clean checkout 可安装、构建并运行 bootstrap；密码文件成功、宽权限、符号链接、硬链接、多行和非法 UTF-8 均按预期失败关闭。

## 7. 剩余风险与后续边界

- GitHub `supabase-development` Environment、main-only 策略、环境 secrets 和成功 Actions 记录已补齐；独立 required reviewer 因单人维护按 CH-009 仅在 development 例外，不能描述为已完成独立审批。
- Supabase development 已取得 repository rollback-only 证据；B2 API + Redis 云端运行烟测仍未接线，不能把该工作流描述为端到端云联调。
- TOTP 依赖客户端和服务器时钟；部署环境必须持续校时，监控时钟漂移，不能通过放宽长期窗口掩盖漂移。
- 浏览器端内存会话会在刷新后丢失，这是 B2 的安全取舍；不得为改善体验把 refresh、pre-auth 或一次性值持久化。
- 双人离线全凭据恢复只在冻结契约中定义，B2 不提供绕过 TOTP 的 HTTP 或单人 CLI；正式恢复 SOP 属于生产准备阶段。
- B2 完成后仍只有安全入口和空工作台，不代表商品、订单、资金或生产上线能力完成。本节 Supabase development rollback-only 已通过，但 CH-009 只允许继续脱敏 development；不得据此进入 staging、production 或处理真实客户数据。
