## 2. B3.0 当前交付

### 2.1 品牌与分类契约

- `BrandCreateRequest.sort_order` 为必填非负整数，update 为可选；Category 保持同样约束。两类列表固定 `sort_order ASC,id ASC`。
- 创建 `initial_status` 固定为 `DRAFT`，禁止创建即启用。
- 品牌/分类使用闭合 `MasterDataLifecycleAction`，动作仅 `ACTIVATE/DEACTIVATE/SOFT_DELETE`，原因 2-500 字符；Product/SKU 原 `LifecycleAction` 保持 `DEACTIVATE/SOFT_DELETE`。
- 状态机固定：`DRAFT/INACTIVE -> ACTIVE`；`ACTIVE -> INACTIVE`；`DRAFT/INACTIVE -> ARCHIVED + deleted_at`。ACTIVE 不得直接软删除，非法或同状态的新请求返回 409。
- 三个动作均先 preview，再提交相同业务字段、短时 token/确认哈希、新幂等键和 `If-Match`。preview 发现 ACTIVE 商品仍返回 200 影响清单，confirm 返回 `ACTIVE_PRODUCT_DEPENDENCY` 422。
- restore 保持原因、幂等键和 `If-Match`，只接受 soft-deleted ARCHIVED，清除 `deleted_at`、固定回 DRAFT、版本加一；不新增 restore-preview，重新启用必须另走 preview-confirm。
- 默认列表排除归档；显式 `status=ARCHIVED` 只返回软删除记录；详情允许读取归档。软删除名称全局保留，再次创建返回 `SOFT_DELETED_KEY_RESERVED` 409。

### 2.2 文件契约

- 七类 purpose 统一只接受 `image/jpeg`、`image/png`，最大 5 MiB；`UploadIntentRequest.sha256` 必填且为 64 位小写十六进制。
- complete 请求的 SHA-256/size 必须同时匹配 intent 和服务端对象 MIME、魔数、大小、SHA-256 实测结果；不匹配返回 `FILE_CONTENT_MISMATCH` 422。
- 上传签名 15 分钟，私有下载签名 5 分钟；对象 key 固定使用不含原文件名的 `staging/`、`public/`、`private/` 分区。
- bucket 默认私有，仅 `public/*` 匿名 GET；售后、提现和推广 QR 固定 `private/*`。PENDING/staging 满 24 小时才进入清理候选，删除前二次确认无 READY 和业务引用。
- 不新增 `completed_at`。完成事实由 READY、`updated_at`、对象元数据、审计和幂等记录联合表达。
- 上传 intent、download URL、lifecycle preview 使用 `HASH_ONLY`。`FILE_UPLOAD_COMPLETE` 是 B3.1 必须实现的闭合响应缓存策略：同键同请求精确重放，新键重复 complete 返回 409；B3.0 只冻结契约，不宣称已实现。

## 3. 后续实现要求

### 3.1 B3.1 文件基础

- intent 在短事务内创建 PENDING、预期内容事实、审计和幂等记录，再返回受控 presigned PUT。
- complete 使用 Redis owner lease；数据库事务外读取和校验对象，幂等复制到最终 key，再以短事务写 READY、审计和幂等结果，最后尽力删除 staging。
- copy 成功但数据库失败必须可重试收敛；清理 Worker 只能删除满 24 小时且二次复核无引用的候选。
- 真实 MinIO 验收覆盖匿名访问边界、签名过期、伪 MIME、哈希不符、超限、并发 complete 与故障恢复。

### 3.2 B3.2 品牌与分类

- 实现文件挂接、CRUD、稳定排序、乐观锁、软删除名称保留、归档查询、恢复和审计。
- lifecycle preview 只存 token 哈希并绑定 actor/session/action/target/request/version；confirm 在同一串行化事务内消费 preview、重查依赖、更新状态/version、写审计和幂等结果。
- 与未来商品发布统一使用 `brand -> category -> product IDs ASC` 锁序；同一幂等键精确重放，新键非法状态返回 409。

### 3.3 B3.3 总部后台

- 只开放品牌、分类和既有账户安全导航，不显示未完成模块。
- ADM-05/06 完成 Logo/Icon 上传、固定草稿创建、排序、编辑、筛选、preview-confirm、归档和恢复为草稿。
- 409 丢弃旧 preview、刷新最新记录并要求重新确认；不得自动覆盖。页面不展示编码、分类说明、佣金来源、商品/SKU 数等 API 不支持字段。
- 五视口覆盖 375/390/414/1024/1440，并验证加载、空、500、403、409、422、重复提交与成功状态。
- B3.3 本地验收后，必须在受保护的 Supabase development 环境以 `mall_runtime` 对 B3 repository 执行独立 rollback-only smoke；测试事务最终 ROLLBACK，并复核无测试数据、DDL、权限或 migration history 残留。该证据不同于进入 B3.1 前的 B2 smoke；缺少 B3 专项远端证据时不得把 B3 整体标记为完成。

## 4. B3.0 验收命令

在 Node.js 22 和冻结 pnpm 版本下执行：

```bash
pnpm contracts:lint
pnpm contracts:check
cp packages/contracts/src/generated/openapi.ts /tmp/ch006-openapi.ts
pnpm contracts:generate
cmp /tmp/ch006-openapi.ts packages/contracts/src/generated/openapi.ts
pnpm prisma:validate
pnpm db:check-frozen
pnpm db:migrate:baseline
pnpm db:test-permissions
pnpm db:diff
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm build:miniapp
pnpm scan:sensitive
```

上面的 `cmp` 用于含本轮预期契约改动的本地工作树；CI 或 CH-006 已提交后的干净检出仍在生成后执行 `git diff --exit-code -- packages/contracts/src/generated`。两种方式都必须证明二次生成没有漂移，不得用工作树相对旧 HEAD 的预期差异误判失败或放宽 CI。

数据库三条命令必须依次指向同一个一次性空 PostgreSQL：先以 owner 连接执行 `db:migrate:baseline`，再用门禁脚本注入并回滚权限故障，最后以 `mall_migrator` 连接执行 `db:diff`。不得指向共享开发库，也不得用已有数据库替代空库回放。

原型验证使用仓库既有 CH-006/三端验收入口，实测通过 84 个响应式渲染、21/9/22 页面契约、14 条小程序流程和 16 条后台/代理流程；ADM-05/06 在 375/390/414/1024/1440 五视口均非空且无页面级横向溢出。

门禁必须确认：

1. `pnpm contracts:check` 输出 172 paths、196 operations、196 unique IDs、306 schemas、0 dangling refs，原始 schema refs 685。
2. `MasterDataLifecycleAction` 仅被品牌/分类四个 lifecycle operation 引用；Product/SKU ACTIVATE 请求被闭合 schema 拒绝。
3. 三项新错误码、排序、DRAFT 创建、状态矩阵、ARCHIVED 查询、restore-to-DRAFT 和文件约束在文本、OpenAPI、生成类型和原型中一致。
4. Prisma 与冻结迁移无字节变化；一次性空库完整回放和权限故障注入通过，Prisma validate 与 migration diff 为零。
5. 页面/FR/AC/US 与 path/operation 数量不变，敏感 URL/token 不进入缓存、日志或生成物。
